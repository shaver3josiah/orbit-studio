Orbit Capture — Solutions Architecture

Three interworking views of the Android room-scanning app that feeds Orbit Studio: how it runs, how it stays secure, and how a scan actually flows from a sketch to a 3D model.

Reflects Orbit Capture v0.5.0 · native Kotlin / Jetpack Compose / CameraX · drawn from the shipping source

01

How the app runs

A four-layer on-device stack — Compose UI over a domain/engine layer over data & memory over the Android platform — plus the two-file bridge (bundle.zip out, artifact.splat back) to the user's laptop and a free Colab GPU. The heavy GPU work lives in the cloud; capture, planning, review, and viewing stay on hardware the user already owns.

02

How it stays secure & private

The design is secure by subtraction: there is no network permission, no account, and no third-party SDK, so the app has no way to send a photo anywhere. Room imagery stays in private storage until the user personally hands the bundle to their own laptop. Three boundaries — a permission gate, an explicit share gate, and a user-owned cloud — are the only ways data moves, and each is under the user's control.

Trusted (on device) Boundary / user-controlled gate User-owned, opt-in cloud Sensitive data
03

The expected user workflow

One coherent journey in three phases: sketch the space before walking it, capture each room with live coaching, then reconstruct on the laptop. The plan the user draws in phase 1 actively steers the capture in phase 2 — shot targets, a walk path, and window/obstacle warnings all come from the sketch. Up to five rooms loop through capture; learnings from the final 3D model feed the next scan.
