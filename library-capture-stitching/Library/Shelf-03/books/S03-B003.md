# Splitting the Sphere: Perspective Rigs for Panorama SfM in Practice

How do you hand twenty spherical photographs to a pose solver that thinks in pinholes? That is the whole question this book answers, and in mid-2026 the answer is still, deliberately, to split the sphere. COLMAP 4.1.0 gained a native spherical camera model in June 2026, and its own release notes describe that path as generally faster but less accurate than rendering perspective views. When you have thousands of video frames, faster wins. When you have twenty stills of a bridge and every match counts, accuracy wins, and accuracy means exploding each equirectangular image into a rig of overlapping virtual pinhole views before structure-from-motion ever runs. The reasons overlap matters at all are covered back on Shelf 01 in "Overlap as the Currency of Structure-from-Motion"; this book is about manufacturing that overlap from a sphere.

Three rig conventions dominate practice. The classic cubemap slices the sphere into 6 faces at 90 degrees each, and practitioners widen the field of view slightly so adjacent faces share roughly 10 percent of their pixels, because faces that merely touch produce no matches across the seam. Nerfstudio's `ns-process-data` tool encodes the second convention: `--images-per-equirect` accepts 8 planes at 120 degree FOV, or 14 planes at 110 degrees spread across pitch bands of -45, 0, and +45 degrees. The third is the ring-plus-poles rig that a practitioner writeup on turning 360 footage into clean splat data converged on independently: around 18 virtual cameras per panorama, a ring of yaws at one or two pitch bands plus dedicated zenith views. Orbit Studio's own reframe stage already ships an 18-view variant of this: 8 yaws at pitch -15, 8 at +20, and 2 zenith views, each rendered at 100 degree FOV into a 1280 by 1280 frame. For a bridge, keep the upward band and the zenith; girders and trusses overhead are exactly the geometry a real-estate-style rig throws away.

The code below implements a rig-based splitter in plain Python. It depends only on NumPy and Pillow, doing the reprojection with an explicit ray-to-equirect lookup rather than pulling in a heavier dependency; `py360convert` does the same math if you prefer a library, and ffmpeg's `v360` filter does it if you prefer a subprocess.

```python
from dataclasses import dataclass
from pathlib import Path
import numpy as np
from PIL import Image

@dataclass(frozen=True)
class View:
    yaw_deg: float
    pitch_deg: float
    fov_deg: float

CUBEMAP_6 = [View(y, 0, 95) for y in range(0, 360, 90)] + [View(0, 90, 95), View(0, -90, 95)]
NERFSTUDIO_14 = (
    [View(y, 45, 110) for y in range(0, 360, 90)]
    + [View(y, 0, 110) for y in range(0, 360, 60)]
    + [View(y, -45, 110) for y in range(0, 360, 90)]
)
RING_18 = (
    [View(y, -15, 100) for y in range(0, 360, 45)]
    + [View(y, 20, 100) for y in range(0, 360, 45)]
    + [View(0, 75, 100), View(180, 75, 100)]
)

def view_rays(size: int, fov_deg: float) -> np.ndarray:
    half = np.tan(np.radians(fov_deg) / 2)
    lin = np.linspace(-half, half, size)
    xs, ys = np.meshgrid(lin, -lin)
    rays = np.stack([xs, ys, np.ones_like(xs)], axis=-1)
    return rays / np.linalg.norm(rays, axis=-1, keepdims=True)

def rotate(rays: np.ndarray, yaw_deg: float, pitch_deg: float) -> np.ndarray:
    yaw, pitch = np.radians(yaw_deg), np.radians(pitch_deg)
    rp = np.array([[1, 0, 0],
                   [0, np.cos(pitch), -np.sin(pitch)],
                   [0, np.sin(pitch), np.cos(pitch)]])
    ry = np.array([[np.cos(yaw), 0, np.sin(yaw)],
                   [0, 1, 0],
                   [-np.sin(yaw), 0, np.cos(yaw)]])
    return rays @ (ry @ rp).T

def sample_equirect(pano: np.ndarray, rays: np.ndarray) -> np.ndarray:
    h, w = pano.shape[:2]
    lon = np.arctan2(rays[..., 0], rays[..., 2])
    lat = np.arcsin(np.clip(rays[..., 1], -1, 1))
    u = ((lon / (2 * np.pi) + 0.5) * (w - 1)).astype(np.int32)
    v = ((0.5 - lat / np.pi) * (h - 1)).astype(np.int32)
    return pano[np.clip(v, 0, h - 1), np.clip(u, 0, w - 1)]

def split_panorama(src: Path, out_dir: Path, rig: list[View], size: int = 1280) -> list[Path]:
    pano = np.asarray(Image.open(src).convert("RGB"))
    out_dir.mkdir(parents=True, exist_ok=True)
    written = []
    for view in rig:
        rays = rotate(view_rays(size, view.fov_deg), view.yaw_deg, view.pitch_deg)
        img = sample_equirect(pano, rays)
        name = f"{src.stem}_y{int(view.yaw_deg):03d}_p{int(view.pitch_deg):+03d}.jpg"
        Image.fromarray(img).save(out_dir / name, quality=95)
        written.append(out_dir / name)
    return written
```

The geometry is compact enough to reason about. `view_rays` builds a bundle of unit rays through an ideal pinhole of the requested field of view. `rotate` aims that bundle with a pitch-then-yaw rotation, matching the yaw and pitch conventions of ffmpeg's v360 filter so rigs transfer between the two implementations. `sample_equirect` converts each ray to longitude and latitude and reads the panorama directly. Nearest-neighbor sampling keeps the example honest and short; production code should interpolate, which is one argument for delegating this exact step to `v360` with cubic interpolation, as Orbit Studio's existing reframe stage does.

Two practical notes carry more weight than the projection math. First, the nadir. Every tripod-mounted station has a hole at the bottom of the sphere where the tripod and often the operator's shadow sit. Do not feed that region to the matcher. The practitioner pipelines that handle this well reproject to perspective views, run detector plus segmenter masking there, dilate the masks by roughly 15 percent to catch soft edges and shadows, and hand the masks to COLMAP through `ImageReader.mask_path` so no features are ever extracted on tripod pixels. Sky deserves the same treatment on an outdoor scene, for a different reason: features matched on moving clouds are worse than no features at all. The full masking and training treatment lives in "Twenty Stations, One Bridge: A Sparse-View Playbook for Outdoor Splats".

Second, the arithmetic of view counts. Twenty panoramas times 14 views is 280 images; times 18 is 360. That is still within reach of exhaustive matching, which COLMAP's documentation recommends only up to a few hundred images, so a 20-station capture sits right at the boundary. If matching time hurts, prefer trimming the rig to trimming match pairs: the 8-view 120 degree rig cuts image count by almost half while keeping full horizontal coverage, at the price of thinner pitch coverage. What you should not do, on current evidence, is skip the split entirely. The native equirectangular path exists in COLMAP 4.1 and will only improve, and the newer pose solvers described in "The Year SfM Collapsed Inward: COLMAP 4, the GLOMAP Merger, and the New Pose Baseline" may eventually make rigs a historical curiosity. For a sparse outdoor capture in July 2026, the split-then-solve recipe remains the one every working pipeline agrees on, and it is the one the reference implementation in this shelf's closing volume builds on.

One last habit worth stealing from the video workflows: cull before you match. A Laplacian-variance sharpness score per virtual view, batched per station, catches the rare soft face caused by stitch ghosting or motion in the original capture. With only twenty stations there is no budget for a bad view poisoning the pose graph; with 280 to 360 virtual images, dropping the worst handful costs nothing. The check is a dozen lines on top of the splitter above:

```python
LAPLACIAN = np.array([[0, 1, 0], [1, -4, 1], [0, 1, 0]], dtype=np.float64)

def sharpness(path: Path) -> float:
    gray = np.asarray(Image.open(path).convert("L"), dtype=np.float64)
    interior = (
        LAPLACIAN[0, 1] * (gray[:-2, 1:-1] + gray[2:, 1:-1]
                           + gray[1:-1, :-2] + gray[1:-1, 2:])
        + LAPLACIAN[1, 1] * gray[1:-1, 1:-1]
    )
    return float(interior.var())

def cull_soft_views(views: list[Path], keep_fraction: float = 0.95) -> list[Path]:
    scored = sorted(views, key=sharpness, reverse=True)
    keep = max(1, round(len(scored) * keep_fraction))
    for soft in scored[keep:]:
        soft.rename(soft.with_suffix(".culled"))
    return scored[:keep]
```

The threshold is relative rather than absolute on purpose. Every writeup of the Laplacian-variance technique warns that a fixed cutoff is subjective to image content, so ranking within the capture and dropping the bottom slice is the version that transfers between a sunlit deck and an overcast one without retuning.
