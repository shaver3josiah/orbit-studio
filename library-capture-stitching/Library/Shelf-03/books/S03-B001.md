# The Year SfM Collapsed Inward: COLMAP 4, the GLOMAP Merger, and the New Pose Baseline

If you were building a splat pipeline in early 2026, one line of advice showed up in every writeup: install GLOMAP separately, because it recovers camera poses far faster than COLMAP's default incremental mapper, and COLMAP still can't touch a 360 photo without help. Neither half of that sentence survived the year. GLOMAP is gone as a standalone project, and COLMAP grew a spherical camera model of its own. For a solo operator turning twenty bridge panoramas into a fly-through, the question this book answers is simple: what actually changed in COLMAP 4.x, and which of those changes should touch your pipeline versus which are traps dressed up as upgrades.

## The merger

GLOMAP was a genuine result. Its paper, "Global Structure-from-Motion Revisited," described a general-purpose global SfM system that matched or beat COLMAP's incremental mapper in accuracy while running orders of magnitude faster, by folding translation averaging and triangulation into a single global positioning step instead of growing the reconstruction one image at a time. For two years it lived as a separate binary that power users bolted onto a COLMAP database. That arrangement ended on 2026-03-09, when the colmap/glomap repository was archived by its own maintainers. The notice is direct: the project "is no longer maintained and has been fully migrated to COLMAP, where GLOMAP functionality is exposed as the 'global' mapper." Five days later, COLMAP 4.0.0 shipped (2026-03-14) with exactly that: GLOMAP's global mapper folded in as a first-class alternative to the incremental mapper, selectable through COLMAP's own tooling with no second binary to build, version-pin, or keep in sync.

This is the headline of the whole year: COLMAP stopped being one tool among several in a hand-assembled SfM stack and started absorbing the stack. The same 4.0.0 release added native ALIKED feature extraction (via ONNX) and LightGlue matching (via ONNX, for both SIFT and ALIKED descriptors), which had previously meant reaching for the separate hloc toolbox. That matters because hloc has been quietly stalling: its last tagged release, v1.4, dates to July 2024, and its ALIKED and XFeat support has been sitting on an unreleased master branch rather than shipping. COLMAP absorbing that functionality natively isn't just convenience, it's COLMAP becoming the more current path where the specialist tool had stopped moving.

COLMAP 4.1.0 followed on 2026-06-26 with three more additions worth knowing by name: native spherical (equirectangular) camera models, the Enhanced Unified Camera Model (EUCM), and Caspar, a GPU-accelerated bundle adjustment backend that COLMAP's release notes describe as one to two orders of magnitude faster than the existing Ceres CUDA backend. It also robustified gravity-aligned rotation averaging "against 180-degree flips," a direct nod to global SfM's known Achilles' heel on small, tightly looped scenes, which is exactly the shape of a walk around a bridge. COLMAP 4.1.1, released 2026-07-17, is the current stable point release, mostly fixing a matching slowdown and renaming a pycolmap enum.

Read across the wider 2026 landscape and the pattern holds. OpenMVG's "Spherical" camera still isn't true equirectangular projection by its own maintainers' account, with the fix (a distinct Spherical_Equirectangular model) an open GitHub issue for years running. OpenSfM has a real, production-heritage spherical projection type, but its own `export_colmap.py` script hard-errors with `Can't convert {camera.projection_type} to COLMAP` the moment it meets a spherical camera, so there's no bridge from OpenSfM's panorama poses into the COLMAP-format world that Orbit Studio's trainers expect. Meshroom's mrGSplat plugin is still developer-preview, with its own README admitting pose optimization "didn't really work" for some nodes. Against that field, COLMAP consolidating GLOMAP, ALIKED, LightGlue, and now a native spherical camera into one maintained binary isn't just tidy, it's the only path that didn't stall, fork off into a niche fork of uncertain license, or hit a hard wall converting formats.

## What the global mapper means for a bridge loop

The practical upside for a 20-panorama capture is speed and a second opinion. Run the global mapper first: it's fast, and on a well-textured, well-overlapped set it should converge cleanly. But the same global SfM literature that GLOMAP's paper draws on, and that COLMAP's own 4.1.0 changelog implicitly acknowledges by patching the 180-degree flip case, flags a specific failure mode on small, structured loop scenes. Twenty stations walked around a bridge and back is precisely that shape: a short loop with limited viewpoint diversity, where a global rotation-averaging step can lock onto a degenerate solution before it ever sees enough constraints to correct itself. The sane default is to treat the global mapper as the fast first attempt and keep COLMAP's incremental mapper as the automatic retry if the global result looks torn or folds back on itself. Neither mapper is "the right one" in the abstract. The right one is whichever produces a coherent bridge, and checking is cheap next to redoing a capture.

## The tempting shortcut: native spherical, and why it's not the day-one answer

The most seductive line in the 4.1.0 release notes is the one that says the spherical camera model enables reconstruction of 360 images "without first rendering perspective views," and a companion writeup on the release frames it as eliminating "the perspective cropping and re-stitching step that previously stood between a panoramic capture and a COLMAP reconstruction." For anyone who has built or maintained a cubemap-splitting script, that sentence reads like a whole pipeline stage getting deleted for free. It's real: COLMAP can now take an equirectangular JPG directly, no reframing, no cube faces, no `ns-process-data` step.

But COLMAP's own documentation is equally direct about the tradeoff: the native spherical path is "generally faster but less accurate than rendering perspective views." Speed is not the constraint on a 20-photo capture. Accuracy is. With only twenty panoramas covering a bridge and its surrounding roadways, every matched feature is doing more work than it would in a video-derived dataset with thousands of overlapping frames to spare, and the areas most likely to suffer under equirectangular pole distortion (thin railings, truss members, anything near the top or bottom of the sphere) are exactly the structures a bridge capture cares about most. For this dataset, the traditional split-then-reconstruct workflow, covered in full in "Splitting the Sphere: Perspective Rigs for Panorama SfM in Practice," remains the safer choice, and native spherical is worth prototyping alongside it rather than in place of it.

There's also real uncertainty around how finished this feature is. One COLMAP GitHub issue notes that as of August 2025 the spherical camera model worked well from the command line via the `panorama_sfm` script and through pycolmap, but wasn't yet selectable in the COLMAP GUI, and whether that has changed by 4.1.1 is not confirmed in the available record. Whether the pycolmap build installable in a fresh Google Colab notebook today already wraps 4.1.x's spherical model and Caspar backend, versus lagging behind the C++ release, is likewise unconfirmed. Treat native spherical as a live experiment worth running, not a foundation to build on sight unseen.

## What actually changes in the notebook

Strip the year down to what should move in an actual Colab cell and the list is short. Pin COLMAP to 4.0.0 or later, ideally 4.1.1, and drop any separate GLOMAP install step entirely, since the standalone project is archived and its functionality now lives inside COLMAP as the global mapper. Keep the existing ffmpeg reframe step rather than switching to native equirectangular input, at least until native spherical proves itself on this exact dataset shape. Let feature extraction and matching default to COLMAP's native ALIKED and LightGlue path, since it replaces a stalled external toolbox with something the same project maintains, but keep classic SIFT with exhaustive matching wired up as a fallback in case ALIKED and LightGlue produce a broken reconstruction on the repetitive asphalt and pavement texture that surrounds a bridge deck. Run the global mapper first for speed and fall back to the incremental mapper if the loop closes badly.

None of this is the last word on how COLMAP fits into a 2026 splat pipeline. It's a mapper doing pose recovery from matched features, which is a specific and increasingly optional stage: "Feed-Forward Geometry: VGGT, MapAnything, and the End of Mandatory Feature Matching" covers the emerging case for skipping feature matching altogether. And the concrete, working version of everything above, wired into an actual Colab notebook against a real T4 budget, lives in "The 2026 Orbit Studio Upgrade: A Reference Pipeline from Twenty Panoramas to Fly-Through." What this volume gives you is the reason to trust that pipeline's choices: COLMAP didn't just add features this year, it absorbed the field around it, and knowing which absorbed feature is ready for a 20-photo bridge and which is still a bet is what keeps a solo capture from becoming a debugging session.
