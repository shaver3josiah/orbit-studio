# Shipping a World: SOG, SPZ 4, and the New Web Splat Stack

By mid-2026 the web-splat delivery stack has consolidated. The old antimatter15-lineage viewer, mkkellogg's `GaussianSplats3D`, shipped its last tag (v0.4.7) back on January 25, 2025, and its own README now tells users the repo "is no longer in active development" and to move to Spark instead. That's the same generational handoff described on the training side in *The Trainer Field in Mid-2026: Brush, LichtFeld Studio, and the Quiet Stall of Nerfstudio* — tools that were fine a year ago are now dead ends, and the reference pipeline in *The 2026 Orbit Studio Upgrade: A Reference Pipeline from Twenty Panoramas to Fly-Through* already assumes you're not using them. On the viewer side, Spark (sparkjs.dev, MIT, backed by World Labs) is the maintained target. On the format side, PlayCanvas's SOG — "the WebP of Gaussian Splatting," announced September 2025 — has become the default browser-delivery container, with Niantic Spatial's SPZ 4 (May 5, 2026) as the interchange format for everything that isn't a browser tab.

This volume covers three working pieces for the twenty-photo bridge scene: converting a trained PLY into a web bundle, loading and LOD-scaling that bundle in Spark, and driving a keyframed fly-through camera authored in SuperSplat.

## Archive to bundle: splat-transform

PlayCanvas's open-source `splat-transform` CLI (`@playcanvas/splat-transform` on npm) reads PLY, Compressed PLY, SOG, Streamed SOG, SPZ, SPLAT, KSPLAT and more, and writes PLY, Compressed PLY, SOG, Streamed SOG, SPZ, GLB, CSV, an HTML viewer, LOD, and voxel-collision output. It also does the housekeeping a Colab-trained PLY needs before it ever reaches a browser: NaN/Inf stripping, box/sphere/harmonic-band/floater filtering, and Morton reordering — the spatial sort SOG's GPU-ready decode depends on. It's a Node tool, so the Python glue below just shells out to it, matching the recommendation to keep `.ply` as the archival master and add one conversion step rather than hand-rolling a format writer:

```python
#!/usr/bin/env python3
from __future__ import annotations
import shutil
import subprocess
import sys
from pathlib import Path

def _cli() -> list[str]:
    exe = shutil.which("splat-transform")
    return [exe] if exe else ["npx", "@playcanvas/splat-transform"]

def convert_scene(source_ply: Path, out_dir: Path, gaussian_count: int) -> dict[str, Path]:
    out_dir.mkdir(parents=True, exist_ok=True)
    cli = _cli()
    archive_ply = out_dir / "scene.archive.ply"
    interchange_spz = out_dir / "scene.spz"
    web_target = out_dir / (
        "scene.streamed.sog" if gaussian_count > 1_000_000 else "scene.sog"
    )

    subprocess.run(
        [*cli, str(source_ply), str(archive_ply),
         "--filter-nan", "--filter-floaters", "--morton-reorder"],
        check=True,
    )
    subprocess.run([*cli, str(archive_ply), str(web_target)], check=True)
    subprocess.run([*cli, str(archive_ply), str(interchange_spz)], check=True)

    return {"archive": archive_ply, "web": web_target, "interchange": interchange_spz}

if __name__ == "__main__":
    result = convert_scene(Path(sys.argv[1]), Path(sys.argv[2]), int(sys.argv[3]))
    for label, path in result.items():
        assert path.exists(), f"{label} export missing: {path}"
    print(result)
```

The `gaussian_count > 1_000_000` branch is a house rule, not a vendor spec: it routes anything bigger than a modest single-structure scene to Streamed SOG instead of monolithic SOG, since Streamed SOG is the variant meant for range-request loading. Twenty leveled equirectangular stills of a bridge deck won't usually clear that bar, but the branch keeps the pipeline correct if a future capture adds more panoramas or a wider roadway sweep. `splat-transform` is also usable without Node at all, in-browser via WebAssembly at `superspl.at/convert`, if you'd rather not add it to the Colab environment — check `splat-transform --help` for the current flag names before wiring this into CI, since the exact CLI surface wasn't fully captured in the README excerpt this is grounded in.

## Loading and LOD in Spark

Spark auto-detects `.sog` (and `.ply`, `.splat`, `.ksplat`, `.spz`, `.zip`, `.rad`) by extension, so the viewer side of the swap is just pointing `SplatMesh` at the new file. `SparkRenderer` requires a WebGL2 `THREE.WebGLRenderer` — there's no WebGPU path — and antialiasing is disabled because it doesn't help splat rendering:

```js
import * as THREE from "three";
import { SparkRenderer, SplatMesh } from "@sparkjsdev/spark";

const renderer = new THREE.WebGLRenderer({ antialias: false });
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(
  60, window.innerWidth / window.innerHeight, 0.05, 500,
);

const spark = new SparkRenderer({ renderer });
scene.add(spark);

const isMobile = /Android|iPhone|iPad/i.test(navigator.userAgent);
const bridge = new SplatMesh({
  url: "/scenes/bridge-deck/scene.sog",
  lodSplatScale: isMobile ? 1_250_000 : 2_500_000,
});
scene.add(bridge);

renderer.setAnimationLoop(() => {
  spark.updateSort(camera);
  renderer.render(scene, camera);
});
```

`lodSplatScale` is the documented lever for target splat counts on Spark's LOD splat tree: roughly 500K-750K for WebXR, 1-1.5M for mobile, up to 2.5M on desktop. That tree, added in Spark 2.0 (April 14, 2026), traverses in O(N log N) time against a default 16M-splat GPU memory pool, which is built for the 100M-to-1B-splat scenes far larger than a single bridge — for this reader's scene it mostly buys headroom, not necessity. Spark 2.1.0 (May 18, 2026) followed with PLY point-cloud enhancements and a Chrome 149 fix; check `sparkjs.dev` for anything past that tag, since the research behind this volume couldn't confirm whether a newer release has shipped since. Don't reach for `GaussianSplats3D` here even though its API is more familiar — it's the tool its own maintainer is retiring.

## The page around it

Both snippets above assume a page that resolves the bare `three` and `@sparkjsdev/spark` specifiers and survives a window resize. That shell is small enough to show whole, and having it whole matters: the single most common integration failure with Spark is an import map that pins a different three.js build than the one Spark was resolved against, which produces a blank canvas and no error. Pin both specifiers in one map, serve everything from one origin, and the failure mode disappears:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <title>Bridge Deck Fly-Through</title>
  <style>
    html, body { margin: 0; height: 100%; overflow: hidden; background: #000; }
    #hud { position: fixed; inset: auto auto 12px 12px; color: #fff;
           font: 13px/1.4 system-ui; opacity: 0.7; }
  </style>
  <script type="importmap">
  {
    "imports": {
      "three": "/vendor/three-0.180.0/three.module.js",
      "@sparkjsdev/spark": "/vendor/spark-2.1.0/spark.module.js"
    }
  }
  </script>
</head>
<body>
  <div id="hud">loading scene…</div>
  <script type="module">
    import { viewer } from "/js/bridge-viewer.js";

    const hud = document.getElementById("hud");
    const app = await viewer("/scenes/bridge-deck/scene.sog", {
      onProgress: (pct) => { hud.textContent = `loading scene… ${pct}%`; },
      onReady: () => { hud.textContent = "drag to look, K toggles fly-through"; },
    });

    addEventListener("resize", () => {
      app.camera.aspect = innerWidth / innerHeight;
      app.camera.updateProjectionMatrix();
      app.renderer.setSize(innerWidth, innerHeight);
    });
  </script>
</body>
</html>
```

The two vendored module paths are the deliberate choice here, not a shortcut. Orbit Studio already serves its viewer from a local server at a fixed port precisely because splat viewers need real HTTP, not `file://`, and vendoring Spark and three.js beside the scene files keeps the whole bundle self-contained and offline-friendly, the same property `splat-transform`'s own standalone HTML viewer export aims for. The `onProgress` hook is worth the few lines: a bridge-scale SOG is tens of megabytes, and a silent black screen during download is indistinguishable from the import-map failure described above, so giving the two states different on-screen text saves real debugging time.

## Keyframed fly-throughs via SuperSplat

Don't build a timeline UI inside the Orbit Studio viewer. PlayCanvas's SuperSplat editor (`superspl.at/editor`) already has one: its Timeline panel (v2.0, Feb 2025) sets per-frame camera keyframes and can import COLMAP camera poses to auto-seed a path that retraces the real capture — exactly the poses the *Reference Pipeline* volume already computes via `pycolmap` for the twenty bridge panoramas. Load the archive PLY into SuperSplat, let it seed keyframes from the COLMAP poses, then hand-adjust for a cleaner sweep down the roadway and across the deck. From there you have two delivery paths, not one:

SuperSplat 2.2's Render menu bakes the Timeline directly to an MP4, entirely locally in-browser with no upload — the zero-engineering option for a shareable clip. For the interactive, walkable version, export the keyframe list and drive the camera yourself. Spark is explicitly camera-control-agnostic — any THREE.js-compatible control scheme works — so this is a small adapter, not a new subsystem:

```js
import * as THREE from "three";

class FlythroughPath {
  constructor(keyframes) {
    this.duration = keyframes.at(-1).time;
    this.positions = new THREE.CatmullRomCurve3(
      keyframes.map((k) => new THREE.Vector3(...k.position)),
    );
    this.targets = new THREE.CatmullRomCurve3(
      keyframes.map((k) => new THREE.Vector3(...k.lookAt)),
    );
  }

  apply(camera, elapsedSeconds) {
    const t = THREE.MathUtils.clamp(elapsedSeconds / this.duration, 0, 1);
    camera.position.copy(this.positions.getPointAt(t));
    camera.lookAt(this.targets.getPointAt(t));
  }
}

const keyframes = await fetch("/scenes/bridge-deck/flythrough.json").then((r) => r.json());
const path = new FlythroughPath(keyframes);
const clock = new THREE.Clock();

renderer.setAnimationLoop(() => {
  path.apply(camera, clock.getElapsedTime() % path.duration);
  spark.updateSort(camera);
  renderer.render(scene, camera);
});
```

`flythrough.json` here is just `[{time, position: [x,y,z], lookAt: [x,y,z]}, ...]` — the shape this thin adapter expects once you've exported SuperSplat's authored path, not a format SuperSplat itself guarantees byte-for-byte, so treat the export step as "serialize whatever the Timeline gives you into this list" rather than a fixed file format. `CatmullRomCurve3` is stock three.js, so there's no new spline-fitting code to maintain. This reuses the same `spark` and `camera` objects from the loading snippet above — same render loop, one added `path.apply()` call per frame.

## SPZ as the interchange, not the delivery format

SPZ 4 (Niantic Spatial, May 5, 2026, dual-licensed Apache-2.0/MIT) compresses 3-5x faster and loads 1.5-2.1x faster than SPZ 3 — a 34M-point dataset dropped from 3 minutes 26 seconds to 1 minute 8 seconds to encode — by replacing the old single GZip stream with six parallel ZSTD streams, and it now supports SH degree 4 with configurable 3/5/8-bit quantization and no point-count cap. Files still land around 10x smaller than uncompressed PLY. SOG currently wins for raw in-browser decode because it's WebP-backed and needs no per-splat unpack, so keep it as the primary web format; export SPZ alongside it, as the conversion script above already does, for anyone pulling the bridge scene into Unity, a robotics stack, or another engine entirely.

SPZ is also the format named in Khronos's `KHR_gaussian_splatting` glTF extension contributor list (Autodesk, Bentley/Cesium, Esri, Huawei, Niantic Spatial, NVIDIA), which hit release-candidate status February 3, 2026 with ratification "expected Q2 2026." As of today, no ratification announcement has turned up — worth rechecking before building anything against it, and a detail *What the Industry Shipped While You Were Capturing: Marble, Scaniverse, and the Open Lane* touches from the other side: none of the big consumer tools it covers do multi-still photogrammetry at all, so this whole SOG/SPZ delivery question is specific to pipelines like this one that actually produce a metric reconstruction to ship.

Two more open ends worth flagging rather than papering over: whether Babylon.js v9's native SOG loader and Spark's SOG loader accept byte-identical `.sog` files hasn't been independently verified, and SuperSplat 2.2's local video export mechanism (WebCodecs versus MediaRecorder) wasn't confirmed either — neither blocks the pipeline above, but both are worth a spot-check before you depend on cross-viewer file sharing or scripted video export.
