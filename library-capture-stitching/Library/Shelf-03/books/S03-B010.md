# The 2026 Orbit Studio Upgrade: A Reference Pipeline from Twenty Panoramas to Fly-Through

This volume is the assembly manual. Twenty leveled equirectangular JPGs from an Insta360 X4 Air come in one end; a splat world you can fly through in a browser comes out the other. Every stage below is a decision point with a documented fallback, because a 20-station capture is sparse enough that any single stage can degrade, and the pipeline needs to keep going without a human rerunning cells by hand. The orchestrator is plain Python 3.11, calls out to real CLIs (COLMAP, splat-transform) and one browser-side JS snippet for the viewer, and every version number below is pinned to what shipped as of 2026-07-23.

## The orchestrator skeleton

```python
from __future__ import annotations

import shutil
import subprocess
from dataclasses import dataclass, field
from pathlib import Path


@dataclass(frozen=True)
class PipelineConfig:
    panoramas_dir: Path
    workdir: Path
    faces_per_pano: int = 14
    face_fov_deg: float = 110.0
    pitch_bands_deg: tuple[float, ...] = (-45.0, 0.0, 45.0)
    min_registered_ratio: float = 0.85


def run_pipeline(cfg: PipelineConfig) -> Path:
    crops_dir = reframe_panoramas(cfg)
    sparse_dir = recover_poses(cfg, crops_dir)
    ply_path = train_splat(cfg, crops_dir, sparse_dir)
    web_dir = package_for_web(cfg, ply_path, sparse_dir)
    return web_dir
```

`run_pipeline` is the whole story at a glance: reframe, recover poses, train, package. Each function below owns one decision point and one fallback, so the top-level flow never needs its own branching.

## Stage 1: twenty panoramas into perspective crops

No production feed-forward reconstruction model (VGGT, MapAnything, Pi3, AnySplat) or open splat trainer (Brush, LichtFeld Studio, gsplat) ingests equirectangular images directly, and COLMAP's own native spherical camera model, added in 4.1.0, is documented by its authors as "generally faster but less accurate than rendering perspective views." With only twenty stations, accuracy beats speed, so every panorama gets split into perspective crops first. This follows nerfstudio's `ns-process-data` convention — 8 faces at 120° FOV or 14 faces at 110° FOV, sampled at pitches of -45°, 0°, and 45° — implemented directly with `py360convert` so the split stays inside Orbit Studio's own code instead of pulling in all of nerfstudio as a dependency.

```python
import py360convert
from PIL import Image
import numpy as np


def reframe_panoramas(cfg: PipelineConfig) -> Path:
    crops_dir = cfg.workdir / "crops"
    crops_dir.mkdir(parents=True, exist_ok=True)
    panoramas = sorted(cfg.panoramas_dir.glob("*.jpg"))
    if not panoramas:
        raise FileNotFoundError(f"no equirect stills in {cfg.panoramas_dir}")

    yaws_per_band = cfg.faces_per_pano // len(cfg.pitch_bands_deg)
    for pano_path in panoramas:
        equirect = np.array(Image.open(pano_path))
        face_id = 0
        for pitch in cfg.pitch_bands_deg:
            for i in range(yaws_per_band):
                yaw = i * (360.0 / yaws_per_band)
                crop = py360convert.e2p(
                    equirect,
                    fov_deg=cfg.face_fov_deg,
                    u_deg=yaw,
                    v_deg=pitch,
                    out_hw=(1024, 1024),
                )
                out_name = f"{pano_path.stem}_f{face_id:02d}.jpg"
                Image.fromarray(crop).save(crops_dir / out_name)
                face_id += 1
    return crops_dir
```

Twenty panoramas at 14 faces each yield roughly 280 perspective images with enough shared overlap for a matcher to close the loop around the bridge — the same overlap budget "Twenty Stations, One Bridge: A Sparse-View Playbook for Outdoor Splats" builds its regularization case around.

## Stage 2: COLMAP 4.1.1 first, MapAnything as the low-overlap fallback

COLMAP absorbed the field this year. GLOMAP was archived on 2026-03-09 and folded into COLMAP 4.0.0 (2026-03-14) as the `global` mapper; that same release added native ALIKED and LightGlue matching via ONNX. COLMAP 4.1.1 (2026-07-17) is current stable. Run the global mapper first for speed, retry with the incremental mapper if it looks degenerate — a known failure mode on small, tightly looped scenes — and only then reach for MapAnything (facebookresearch/map-anything, v1.1.3, 2026-07-17) as a genuinely different pose source when too few crops register. MapAnything wraps VGGT/DUSt3R/MASt3R/Pi3-X behind one interface and exports straight to COLMAP's cameras/images/points3D format, so nothing downstream needs to know which path produced the poses. Use the `facebook/map-anything-apache` checkpoint specifically — the default checkpoint, and the base VGGT-1B, Pi3, DUSt3R, and MASt3R weights it can wrap, are all CC-BY-NC, non-commercial only.

```python
def recover_poses(cfg: PipelineConfig, crops_dir: Path) -> Path:
    poses_dir = cfg.workdir / "poses"
    poses_dir.mkdir(parents=True, exist_ok=True)
    db_path = poses_dir / "database.db"
    sparse_dir = poses_dir / "sparse"
    sparse_dir.mkdir(exist_ok=True)

    subprocess.run(
        ["colmap", "feature_extractor", "--database_path", str(db_path),
         "--image_path", str(crops_dir), "--FeatureExtraction.type", "aliked"],
        check=True,
    )
    subprocess.run(
        ["colmap", "feature_matcher", "--database_path", str(db_path),
         "--FeatureMatching.type", "lightglue"],
        check=True,
    )
    subprocess.run(
        ["colmap", "mapper", "--database_path", str(db_path),
         "--image_path", str(crops_dir), "--output_path", str(sparse_dir),
         "--Mapper.ba_global_use_pba", "1"],
        check=False,
    )
    if not _reconstruction_is_healthy(sparse_dir, crops_dir, cfg):
        subprocess.run(
            ["colmap", "mapper", "--database_path", str(db_path),
             "--image_path", str(crops_dir), "--output_path", str(sparse_dir)],
            check=False,
        )
    if not _reconstruction_is_healthy(sparse_dir, crops_dir, cfg):
        sparse_dir = _recover_poses_with_mapanything(crops_dir, poses_dir)
    return sparse_dir


def _reconstruction_is_healthy(sparse_dir: Path, crops_dir: Path, cfg: PipelineConfig) -> bool:
    images_bin = next(sparse_dir.rglob("images.bin"), None)
    if images_bin is None:
        return False
    registered = images_bin.read_bytes().count(b".jpg")
    total = len(list(crops_dir.glob("*.jpg")))
    return total > 0 and registered / total >= cfg.min_registered_ratio


def _recover_poses_with_mapanything(crops_dir: Path, poses_dir: Path) -> Path:
    out_dir = poses_dir / "sparse_mapanything"
    subprocess.run(
        ["python", "-m", "mapanything.infer",
         "--checkpoint", "facebook/map-anything-apache",
         "--images", str(crops_dir), "--export-format", "colmap",
         "--output", str(out_dir)],
        check=True,
    )
    return out_dir
```

`_reconstruction_is_healthy` is a coarse registered-image ratio check, not a real quality metric — good enough to trigger the fallback, not good enough to certify a reconstruction. Whether MapAnything's Apache checkpoint matches the default checkpoint's quality is not yet confirmed in the published record, so treat this branch as a rescue path, not the default.

## Stage 3: regularized training, Brush by default, gsplat on the Colab T4

For a Windows laptop of unknown GPU vendor, Brush (ArthurBrussee/brush, Apache-2.0) is the sane default: it runs on NVIDIA, AMD, or Apple GPUs, and even in a WebGPU browser, via wgpu and Burn, with no CUDA install required. It still consumes COLMAP or nerfstudio-format poses rather than estimating its own, so Stage 2 never becomes optional. When a CUDA GPU is confirmed — the Colab T4 fallback, or a laptop with an NVIDIA card — switch to gsplat and turn on the regularizers that 2025-2026 sparse-view papers (Pi-GS, DropAnSH-GS) converge on: a monocular-depth Pearson-correlation loss standing in for real multi-view overlap, per-image appearance embeddings for exposure drift between stations, and masked-out sky and transient regions so the optimizer never spends capacity on cars or moving pedestrians on the roadway.

```python
def train_splat(cfg: PipelineConfig, crops_dir: Path, sparse_dir: Path) -> Path:
    output_dir = cfg.workdir / "splat"
    output_dir.mkdir(exist_ok=True)
    if shutil.which("nvidia-smi") is None:
        subprocess.run(
            ["brush_app", "--source", str(sparse_dir), "--images", str(crops_dir),
             "--export-ply", str(output_dir / "scene.ply")],
            check=True,
        )
        return output_dir / "scene.ply"

    subprocess.run(
        [
            "python", "examples/simple_trainer.py",
            "--data-dir", str(sparse_dir), "--data-factor", "1",
            "--result-dir", str(output_dir),
            "--app-opt", "--app-embed-dim", "16",
            "--post-processing", "ppisp",
            "--mask-dir", str(cfg.workdir / "masks"),
            "--antialiased", "false",
        ],
        check=True,
    )
    return output_dir / "ply" / "scene.ply"
```

`--antialiased false` is a deliberate choice, not an oversight: gsplat's Mip-Splatting-style antialiasing has an open issue (#840) documenting that it deletes thin high-frequency structure like bicycle spokes, and a bridge's cables and railings are exactly that kind of geometry. PPISP is preferred over the classic bilateral grid because spirulae-splat reports less color shift from it, and it directly targets the exposure and white-balance drift you'd expect across twenty stations shot at different times of day.

## Stage 4: packaging with splat-transform

Whichever branch produced `scene.ply`, packaging is identical: keep the PLY as the archival master and emit a browser-ready format with PlayCanvas's open-source `splat-transform` CLI.

```python
def package_for_web(cfg: PipelineConfig, ply_path: Path, sparse_dir: Path) -> Path:
    web_dir = cfg.workdir / "web"
    web_dir.mkdir(exist_ok=True)
    subprocess.run(
        ["npx", "@playcanvas/splat-transform",
         str(ply_path), str(web_dir / "scene.sog"),
         "--filter-nan", "--reorder-morton"],
        check=True,
    )
    subprocess.run(
        ["npx", "@playcanvas/splat-transform",
         str(ply_path), str(web_dir / "scene.spz")],
        check=True,
    )
    return web_dir
```

SOG (Spatially-Ordered Gaussians) is the primary web target — WebP-textured and Morton-ordered, decoding GPU-ready with no per-splat CPU unpack, and natively read by both Spark and Babylon.js v9. PlayCanvas's own showcase shrinks a 1GB, 4-million-gaussian PLY down to 42MB. The `.spz` export rides along as a secondary interchange format: SPZ 4 (Niantic Spatial, 2026-05-05) compresses 3-5x faster than SPZ 3 and drops the old 10-million-point cap, and it's the format named in Khronos's `KHR_gaussian_splatting` glTF extension, whose release candidate shipped 2026-02-03 with ratification expected in Q2 2026 — not yet confirmed complete as of today, so treat it as a bet on portability, not a dependency.

## Stage 5: the Spark fly-through

Camera keyframes come from SuperSplat, not from custom code: its editor (superspl.at/editor) can import the COLMAP poses already sitting in `sparse_dir` and auto-seed a timeline that retraces the real capture walk around the bridge, which a human then nudges into a clean fly-through path and exports as JSON. Spark (sparkjs.dev, MIT, v2.1.0) renders the `.sog` file itself and is explicitly camera-agnostic, so playing that exported path back is a small interpolator, not a new viewer.

```javascript
import * as THREE from "three";
import { SparkRenderer, SplatMesh } from "@sparkjsdev/spark";

const renderer = new THREE.WebGLRenderer({ antialias: false });
const spark = new SparkRenderer({ renderer });
const scene = new THREE.Scene();
scene.add(spark);

const splat = new SplatMesh({ url: "/web/scene.sog" });
scene.add(splat);

const keyframes = await fetch("/web/flythrough.json").then(r => r.json());
const camera = new THREE.PerspectiveCamera(60, innerWidth / innerHeight, 0.01, 1000);

function playAt(t) {
  const i = Math.min(Math.floor(t * (keyframes.length - 1)), keyframes.length - 2);
  const localT = t * (keyframes.length - 1) - i;
  camera.position.lerpVectors(
    new THREE.Vector3(...keyframes[i].position),
    new THREE.Vector3(...keyframes[i + 1].position),
    localT,
  );
  camera.quaternion.slerpQuaternions(
    new THREE.Quaternion(...keyframes[i].quaternion),
    new THREE.Quaternion(...keyframes[i + 1].quaternion),
    localT,
  );
}
```

## Tying it together, and what's still open

`run_pipeline` never needs to know which branch fired at Stage 2 or Stage 3 — every fallback resolves to the same shape of output, which is what makes the top-level function stay four lines. The one thing worth checking without spinning up COLMAP or a GPU is the decision logic itself:

```python
def demo() -> None:
    healthy_bin = b"a.jpg" * 18 + b"b.jpg" * 2
    unhealthy_bin = b"a.jpg" * 5 + b"b.jpg" * 15

    def ratio(data: bytes, total: int) -> float:
        return data.count(b".jpg") / total

    assert ratio(healthy_bin, 20) >= 0.85
    assert ratio(unhealthy_bin, 20) < 0.85


if __name__ == "__main__":
    demo()
```

Two things stay explicitly unresolved rather than papered over. First, whether MapAnything or a feed-forward model like VGGT actually fits a free Colab T4's memory budget for ~280 perspective crops has not been confirmed in any source found — the only published figure is MapAnything's 2000-view mode on 140GB of datacenter GPU memory, an upper bound, not a T4 answer, so budget a real test before trusting that fallback in production. Second, panorama-native successors — PanoVGGT, VGGT-360, 360-GeoGS — would delete Stage 1 entirely by reconstructing straight from equirectangular panoramas, but as of 2026-07-23 their code and weights are not confirmed released; they're a Q4 2026 revisit, not a component of this pipeline today. Everything else here — the COLMAP/GLOMAP consolidation, the sparse-view regularization recipe, and the SOG/SPZ packaging split — is covered in depth in "The Year SfM Collapsed Inward: COLMAP 4, the GLOMAP Merger, and the New Pose Baseline," "Twenty Stations, One Bridge: A Sparse-View Playbook for Outdoor Splats," and "Shipping a World: SOG, SPZ 4, and the New Web Splat Stack," respectively. This volume is just where those three decisions meet a single runnable script.
