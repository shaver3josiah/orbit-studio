# A First Pass: Feeding a Bundle Straight Through COLMAP

Before tuning anything, run the bundle exactly as the phone or the X4 Air handed it to you. `automatic_reconstructor` is COLMAP's one-command path from a folder of images to a sparse (and optionally dense) model, and it exists precisely for this: a baseline you can point at, compare later tuning against, and use to decide whether the capture itself needs work before the pipeline does ("Command-line Interface — COLMAP (official docs)").

This book assumes you already have a working COLMAP + gsplat environment (see "Setting Up a COLMAP + gsplat Environment in Python 3.11") and a folder of JPGs from one room walkthrough, phone stills or stitched-equirectangular crops from the Insta360 X4 Air, it does not matter which for this pass. The point of this book is narrow: run the bundle through unmodified, read what comes back, and decide if it is good enough to move on.

## The command

`automatic_reconstructor` takes `--workspace_path` and `--image_path` and runs the full sparse-plus-dense pipeline in a single invocation. It also exposes `--quality` (`LOW`, `MEDIUM`, `HIGH`, `EXTREME`) and `--data_type` (`INDIVIDUAL`, `VIDEO`, `INTERNET`) to bias its internal defaults toward the kind of capture you fed it, plus `--feature` (`SIFT` or `ALIKED`), `--mapper` (`INCREMENTAL`, `HIERARCHICAL`, or `GLOBAL`), and `--mesher` (`POISSON`, `DELAUNAY`, `ADVANCING_FRONT`) ("Command-line Interface — COLMAP (official docs)"). For a first pass on a single-room bundle of a few dozen to a couple hundred images, `INDIVIDUAL` data type and `INCREMENTAL` mapper (the defaults) are the right choice, this is what "Running COLMAP Feature Extraction and Matching from a Script" builds on when it breaks the same steps out by hand.

```python
"""baseline_run.py

First pass: feed an unmodified image bundle through COLMAP's
automatic_reconstructor and capture the console output for inspection.
No parameter tuning here, this is the control run everything else
gets compared against.
"""

import subprocess
import sys
import time
from pathlib import Path


def run_automatic_reconstructor(
    workspace_path: Path,
    image_path: Path,
    quality: str = "MEDIUM",
    data_type: str = "INDIVIDUAL",
    mapper: str = "INCREMENTAL",
    dense: bool = False,
) -> subprocess.CompletedProcess:
    workspace_path.mkdir(parents=True, exist_ok=True)

    cmd = [
        "colmap", "automatic_reconstructor",
        "--workspace_path", str(workspace_path),
        "--image_path", str(image_path),
        "--quality", quality,
        "--data_type", data_type,
        "--mapper", mapper,
        "--dense", "1" if dense else "0",
    ]

    log_path = workspace_path / "baseline_run.log"
    start = time.time()

    with open(log_path, "w", encoding="utf-8") as log_file:
        result = subprocess.run(
            cmd,
            stdout=log_file,
            stderr=subprocess.STDOUT,
            check=False,
        )

    elapsed = time.time() - start
    print(f"exit_code={result.returncode} elapsed_s={elapsed:.1f} log={log_path}")
    return result


if __name__ == "__main__":
    workspace = Path(sys.argv[1]) if len(sys.argv) > 1 else Path("./workspace")
    images = Path(sys.argv[2]) if len(sys.argv) > 2 else Path("./images")

    result = run_automatic_reconstructor(workspace, images, dense=False)
    if result.returncode != 0:
        sys.exit(result.returncode)
```

`--dense` is left off (`0`) for this first pass. Dense reconstruction (fusion and meshing) takes real wall-clock time and is not what a gsplat pipeline consumes anyway, gsplat trains on the sparse point cloud and the source images, not a fused mesh ("3D Gaussian Splatting for Real-Time Radiance Field Rendering"). Running sparse-only gets you the registration signal you actually need from a baseline pass in a fraction of the time.

The command writes a `database.db`, a `sparse/` folder (one subfolder per reconstructed model, `0`, `1`, and so on if the bundle split), and, since `--dense` is off here, no `dense/` folder. Everything downstream, including gsplat initialization, reads out of `sparse/0/`.

## What runs underneath, in order

`automatic_reconstructor` is not a black box, it is feature extraction, then matching plus geometric verification, then incremental mapping, chained for you ("Tutorial — COLMAP (official docs)"). Incremental mapping seeds the reconstruction from one initial image pair, then registers additional images one at a time, triangulating new 3D points as each image comes in. This matters for reading the log: the mapper is not solving everything at once, it is growing a model image by image, and a bad initial pair or a stubborn hold-out image shows up as a stall in the registration count rather than a hard failure.

Feature extraction defaults to the `SIMPLE_RADIAL` camera model, with `--ImageReader.single_camera` and `--ImageReader.single_camera_per_folder` both off (`0`) by default, meaning COLMAP will estimate separate intrinsics per image unless told otherwise ("Command-line Interface — COLMAP (official docs)"). For a single-room bundle shot on one phone or one X4 Air at a fixed setting, that default is wasteful, but it is also harmless for a baseline run: the point of this pass is to see how the bundle behaves untouched, not to pre-optimize it. `--SiftExtraction.max_num_features` defaults to 8192 per image, and descriptor normalization defaults to `l1_root` (RootSIFT) rather than plain `l2` normalization, both are defaults worth knowing exist even though this run does not touch them.

## Reading the log

The incremental mapper's console output is the most useful thing this run produces. Post the PR that reworked its verbosity, the default log only prints high-level milestones, "Finding good initial image pair," "Registering image #X," rather than a statistics line for every image ("COLMAP incremental mapper console log format (PR #2420 discussion)"). Verbose per-image statistics ("Registering image #241 (230)" followed by "=> Image sees 3755 / 8696 points") require turning on verbose logging explicitly, via `GLOG_v=1`, `--v=1`, or, if you are driving COLMAP through pycolmap, `pycolmap.logging.verbose_level = 1`.

For a baseline pass, grab that verbose signal, it is the fastest way to see whether the bundle is registering cleanly or fighting itself:

```python
import os
import subprocess

env = os.environ.copy()
env["GLOG_v"] = "1"

subprocess.run(
    ["colmap", "automatic_reconstructor",
     "--workspace_path", "./workspace",
     "--image_path", "./images",
     "--quality", "MEDIUM"],
    env=env,
    check=False,
)
```

With verbose logging on, each registered image reports how many of its own detected points ended up sharing a triangulated 3D point with the rest of the model, the ratio itself is a per-image registration health signal that "Reading a Registration Health Score: <60% Warning, ~95% Healthy" builds a full framework around. For this first pass, just eyeball it: a run where most images report ratios in the same rough neighborhood is a healthy sign, one where a handful of images plunge far below the rest is worth a second look before you move past the baseline.

## What the workspace holds when it is done

Sparse output lands as `cameras.bin`, `images.bin`, and `points3D.bin` (plus `rigs.bin` and `frames.bin` if a multi-camera rig configuration is in play, not relevant for a single phone or a single X4 Air) ("Tutorial — COLMAP (official docs)"). Converting to the text format makes a quick manual check easy:

```python
import subprocess
from pathlib import Path


def to_text(sparse_model_dir: Path, output_dir: Path) -> None:
    output_dir.mkdir(parents=True, exist_ok=True)
    subprocess.run(
        ["colmap", "model_converter",
         "--input_path", str(sparse_model_dir),
         "--output_path", str(output_dir),
         "--output_type", "TXT"],
        check=True,
    )
```

`cameras.txt` gives one line per camera (ID, model, width, height, intrinsic params). `images.txt` gives two lines per image, a pose line (quaternion plus translation plus camera ID and filename) and a 2D-point line where every detected keypoint either points at a triangulated 3D point ID or carries `-1` for unmatched. `points3D.txt` gives one line per 3D point, including a reprojection-error column, that error is only meaningful after a full bundle adjustment has run, which the incremental mapper does as part of its normal operation ("Output Format — COLMAP (official docs)"). COLMAP also logs summary statistics on exit, images registered, mean observations per image, points triangulated, mean track length, that log line alone is often the fastest baseline sanity check available.

One thing this first pass will not tell you, and should not be expected to: whether the bundle split into more than one disconnected model. If not every image ends up registered into the same model, COLMAP reconstructs separate ones instead of forcing them together ("Tutorial — COLMAP (official docs)"). Finding a `sparse/1/` folder next to `sparse/0/` after a run is itself useful diagnostic information, it means something in the bundle, probably a texture-poor stretch of hallway or a big lighting jump between rooms, broke the incremental chain. That is a tuning problem for a later pass, not something to fix here. The job of this book is just to establish what "unmodified, first pass" looks like, so that every tuning decision afterward has something to be measured against.
