# Running Incremental Mapping and Reading the Reconstruction Stats

By the time you get here, `feature_extractor` and one of the matchers have already filled the COLMAP database with keypoints and verified pairs (see *Running COLMAP Feature Extraction and Matching from a Script*). Mapping is the step that turns those pairwise matches into an actual set of camera poses and 3D points. This book covers running `colmap mapper` from Python, capturing its console output, and turning that output into a summary you can act on: how many of your images actually made it into the model, and where the reconstruction is weak.

## Why incremental, not global

COLMAP's incremental mapper seeds the reconstruction from a single well-matched initial image pair, then grows the model one image at a time: register the next image against the existing 3D points, triangulate any new points it sees, periodically re-run bundle adjustment to keep drift in check (per *Tutorial — COLMAP*). This is COLMAP's default and most battle-tested pipeline, and it is why the Orbit Capture pipeline uses it: it is well understood, and its failure modes (an image refusing to register) show up explicitly in the log instead of silently degrading a global solve.

The alternative is global mapping, which solves all camera rotations via rotation averaging before touching positions, avoiding the sequential growth entirely (per *What is the difference between incremental and global SfM in COLMAP?* and *Global and Hierarchical Mapping — colmap/colmap*). Global mapping (GLOMAP-based in recent COLMAP) can be substantially faster on large collections because it skips the repeated bundle-adjustment calls that are incremental mapping's bottleneck, but it wants better focal-length priors and more peak memory. For a single room-by-room walkthrough of a few hundred to a couple thousand images, incremental is the safer default; this book sticks to it. `colmap automatic_reconstructor` exposes `--mapper` as INCREMENTAL, HIERARCHICAL, or GLOBAL if you ever want to swap strategies without hand-assembling the pipeline (per *Command-line Interface — COLMAP*).

## Running the mapper

`colmap mapper` needs the database populated by extraction/matching, the path to the source images, and an empty output directory it will fill with one or more numbered sub-model folders (`0/`, `1/`, ...). If not every image ends up in one connected model, COLMAP simply reconstructs multiple separate models side by side (per *Tutorial — COLMAP*) rather than forcing a bad merge, which is the first thing your stats reader needs to check for.

```python
import subprocess
from pathlib import Path

def run_mapper(database_path: Path, image_path: Path, sparse_path: Path, verbose: bool = True) -> subprocess.CompletedProcess:
    sparse_path.mkdir(parents=True, exist_ok=True)
    env = {}
    if verbose:
        import os
        env = {**os.environ, "GLOG_v": "1"}

    cmd = [
        "colmap", "mapper",
        "--database_path", str(database_path),
        "--image_path", str(image_path),
        "--output_path", str(sparse_path),
        "--Mapper.min_num_matches", "15",
        "--Mapper.ba_local_num_images", "6",
    ]
    return subprocess.run(
        cmd, env=env or None, capture_output=True, text=True, check=False,
    )
```

The `GLOG_v=1` (equivalently `--v=1`, or `pycolmap.logging.verbose_level = 1` if you drive mapping through Python bindings instead) matters. As of the change discussed in *COLMAP incremental mapper console log format*, COLMAP's default logging only prints high-level milestones like "Finding good initial image pair" and "Registering image #X". The detailed per-image line you actually want to parse, of the form:

```
Registering image #241 (230)
=> Image sees 3755 / 8696 points
```

only appears at verbose level 1. The first number after `#` is the image ID; the number in parentheses is the running count of images registered so far; the ratio on the following line is points this image sees versus total triangulated points in the model at that moment. That ratio, per-image, is the raw material for everything in the rest of this book. `--Mapper.min_num_matches 15` and `--Mapper.ba_local_num_images 6` are shown explicitly above because they are the documented defaults (per *colmap-parameters: parameter defaults cheatsheet*) worth pinning in a script rather than trusting whatever ships with the next COLMAP release; that cheatsheet is community-maintained, not official, so cross-check against `colmap mapper --help` on your installed version if a number looks surprising.

If registration is stalling badly (few images going in, most left unregistered), the documented remedies are denser matching or manually specifying the initial pair (per *Frequently Asked Questions — COLMAP*); this book assumes you are past that stage and mapping is producing a model, just not necessarily a complete one.

## Parsing the log into per-image records

The mapper writes its log to stdout, so `subprocess.run(..., capture_output=True)` is enough to capture it; no need to tail a file. The parser below extracts one record per "Registering image" block.

```python
import re
from dataclasses import dataclass

REGISTER_RE = re.compile(r"Registering image #(\d+) \((\d+)\)")
SEES_RE = re.compile(r"=> Image sees (\d+) / (\d+) points")

@dataclass
class ImageRegistration:
    image_id: int
    order_registered: int
    points_seen: int
    points_total_at_time: int

    @property
    def coverage_ratio(self) -> float:
        return self.points_seen / self.points_total_at_time if self.points_total_at_time else 0.0

def parse_mapper_log(log_text: str) -> list[ImageRegistration]:
    records: list[ImageRegistration] = []
    pending: tuple[int, int] | None = None
    for line in log_text.splitlines():
        reg_match = REGISTER_RE.search(line)
        if reg_match:
            pending = (int(reg_match.group(1)), int(reg_match.group(2)))
            continue
        sees_match = SEES_RE.search(line)
        if sees_match and pending is not None:
            image_id, order = pending
            records.append(ImageRegistration(
                image_id=image_id,
                order_registered=order,
                points_seen=int(sees_match.group(1)),
                points_total_at_time=int(sees_match.group(2)),
            ))
            pending = None
    return records
```

This is a small state machine, not a full grammar, and that is deliberate: the log format is two adjacent lines per image, so a one-slot `pending` variable is enough to pair them without a parser generator. If a future COLMAP version reorders or renames these lines, this function is the one place that breaks, which is the point of keeping it isolated from whatever calls `run_mapper`.

## Cross-checking the log against the model on disk

The log tells you what happened during the run; the model on disk tells you what actually survived. Both matter, because a mapper log can show an image registering and then later getting filtered out (COLMAP does discard poorly-conditioned registrations during bundle adjustment), so the ground truth is `images.bin`/`images.txt` in the output sparse folder, not just the log.

```python
import pycolmap
from pathlib import Path

def registered_image_names(sparse_model_path: Path) -> set[str]:
    reconstruction = pycolmap.Reconstruction(str(sparse_model_path))
    return {image.name for image in reconstruction.images.values()}

def build_registration_summary(all_image_names: list[str], sparse_model_path: Path,
                                mapper_records: list[ImageRegistration]) -> dict:
    registered = registered_image_names(sparse_model_path)
    total = len(all_image_names)
    registered_count = len(registered)
    unregistered = sorted(set(all_image_names) - registered)

    ratios = [r.coverage_ratio for r in mapper_records]
    mean_ratio = sum(ratios) / len(ratios) if ratios else 0.0
    weak = sorted(
        (r for r in mapper_records if r.coverage_ratio < 0.3),
        key=lambda r: r.coverage_ratio,
    )

    return {
        "total_images": total,
        "registered_count": registered_count,
        "registered_pct": 100.0 * registered_count / total if total else 0.0,
        "unregistered_images": unregistered,
        "mean_points_seen_ratio": mean_ratio,
        "weakly_registered": [(r.image_id, round(r.coverage_ratio, 3)) for r in weak],
    }
```

`pycolmap.Reconstruction(path)` loads the sparse model and exposes `.images`, `.points3D`, and `.cameras` as Python objects (per *pycolmap Python bindings*), which is a much sturdier way to enumerate what actually registered than re-parsing `images.txt` by hand. That file format is documented in *Output Format — COLMAP*: each image gets two lines, the first with its quaternion, translation, camera ID, and name, the second with its 2D-point-to-3D-point correspondences (a `-1` marking a 2D feature with no triangulated 3D point). COLMAP itself logs summary statistics, images registered and mean observations per image, points and mean track length, at the end of a run (same source), so the numbers above are the same shape of thing COLMAP already reports, just captured programmatically instead of read off the console.

Two things worth flagging explicitly in the code rather than glossing over: the `weakly_registered` threshold of 0.3 above is an arbitrary cutoff this book is choosing for illustration, not a value COLMAP or its docs define. The notes behind this library found real-world registration percentages ranging from roughly 46% up to 92-100% depending on dataset and parameters, and no authoritative source ties a specific health percentage to "healthy" versus "in trouble." Treat any such threshold, including this one, as a knob to tune against your own captures, and see *Scripting a Registration Health Report from COLMAP Output* for a more complete treatment of turning these ratios into a pass/warn/fail summary.

## Turning it into a readable report

```python
def print_report(summary: dict) -> None:
    print(f"Registered {summary['registered_count']}/{summary['total_images']} images "
          f"({summary['registered_pct']:.1f}%)")
    print(f"Mean points-seen ratio across registered images: {summary['mean_points_seen_ratio']:.3f}")

    if summary["unregistered_images"]:
        print(f"\n{len(summary['unregistered_images'])} image(s) never registered:")
        for name in summary["unregistered_images"][:20]:
            print(f"  - {name}")
        if len(summary["unregistered_images"]) > 20:
            print(f"  ... and {len(summary['unregistered_images']) - 20} more")

    if summary["weakly_registered"]:
        print(f"\n{len(summary['weakly_registered'])} image(s) registered but see few of the model's points:")
        for image_id, ratio in summary["weakly_registered"][:20]:
            print(f"  - image #{image_id}: ratio {ratio}")
```

Unregistered images are the loudest signal: a room COLMAP never connected into the model, usually from insufficient overlap between shots or a lighting change harsh enough to break matching, the same illumination sensitivity the descriptor literature documents for gradient-based features like SIFT (per *Descriptor matching sensitivity to illumination change*). Weakly-registered images (present in the model but seeing few of its points) tend to sit at the edges of the capture, a room's far corner, or a doorway shot that only barely bridges two spaces.

Multiple sub-models are the other thing to check for before trusting a single report: if `mapper` wrote `sparse/0/` and `sparse/1/`, your building split into two disconnected reconstructions, and no per-image stats reader will tell you that on its own. Check for it with a plain directory listing before parsing:

```python
def find_sub_models(sparse_path: Path) -> list[Path]:
    return sorted(
        (p for p in sparse_path.iterdir() if p.is_dir() and (p / "cameras.bin").exists()),
        key=lambda p: p.name,
    )
```

More than one entry here means you have a merge decision to make (`model_merger`, then a full `bundle_adjuster` pass on the result, is the documented path, per *COLMAP model_merger usage and limitations*) before the health report even means anything, since the two sub-models are two separate coordinate frames. That merge step, and the refinement pass COLMAP runs afterward, is the subject of *Bundle Adjustment: Refining Pose and Points Together*.

## Putting it together

```python
def main(database_path: str, image_path: str, sparse_path: str) -> None:
    db, imgs, sparse = Path(database_path), Path(image_path), Path(sparse_path)
    result = run_mapper(db, imgs, sparse)

    records = parse_mapper_log(result.stdout + result.stderr)
    sub_models = find_sub_models(sparse)
    if not sub_models:
        print("No sub-models produced; mapper likely failed outright. Check stderr:")
        print(result.stderr[-2000:])
        return

    all_names = sorted(p.name for p in imgs.iterdir() if p.is_file())
    for i, model_dir in enumerate(sub_models):
        print(f"\n=== Sub-model {i} ({model_dir}) ===")
        summary = build_registration_summary(all_names, model_dir, records)
        print_report(summary)

    if len(sub_models) > 1:
        print(f"\nWarning: {len(sub_models)} disconnected sub-models produced; "
              "consider model_merger before trusting a single health number.")
```

This is deliberately not trying to be a general COLMAP wrapper: it runs one mapper invocation, parses its own log, cross-checks against the model pycolmap actually loaded, and prints what it finds. That is the whole job of this stage in the pipeline. Feeding the sparse point cloud into Gaussian-splat training and deciding what "enough" registration looks like before you spend GPU time training gsplat comes after this.
