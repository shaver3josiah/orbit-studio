# Validating an Equirectangular Export: 2:1 Ratio and Width > 3840px

A stitched Insta360 X4 Air export is just a JPG until something checks it. The camera's own stitching pipeline (see "Stitching Dual-Fisheye to Equirectangular with Insta360 Tools") produces the file, but nothing stops a bad export from making it into your capture bundle: a partial stitch, a cropped frame from an editing tool, a re-encode that quietly changed dimensions. The gate for the Orbit Capture pipeline is simple and mechanical: is this file true 2:1, and is it wide enough to be worth feeding to COLMAP. This book writes that gate as a single validation function you can drop into the ingestion step described in "Building the Bundle Ingestion Module: manifest.json to a COLMAP Project."

## Why 2:1, specifically

Equirectangular projection maps longitude to the horizontal pixel coordinate and latitude to the vertical one, linearly, with no further transform ("Equirectangular Projection," PanoTools.org Wiki). A full sphere is 360 degrees of longitude and 180 degrees of latitude, exactly a 2:1 ratio of angular coverage. Because the mapping is linear, that angular ratio has to show up as an exact pixel ratio too: width must equal precisely twice height. The PanoTools wiki gives a concrete cautionary example: a panorama exported at 1650x824 (one pixel short of true 2:1) is enough to confuse downstream panorama-viewing software. Google's Photo Sphere metadata spec gives the positive example instead: a full, uncropped photo sphere at exactly 4000x2000 ("Photo Sphere XMP Metadata (GPano)," Google for Developers). The lesson from both sources is the same: 2:1 is not a rough guideline, it is a hard integer relationship, and off-by-one exports exist in the wild and do cause real downstream breakage. See "Equirectangular Projection: Mapping a Sphere onto a 2:1 Rectangle" for the deeper geometry of why the linear mapping demands this.

## Why a width floor

The research notes for this shelf do not document a specific pixel-count threshold for equirectangular usability in a COLMAP/gsplat pipeline; 3840px is an Orbit Capture pipeline convention, not a figure the sourced literature independently justifies, and this book states that plainly rather than dressing it up as a cited fact. The reasoning behind picking a floor at all is defensible from the notes even though the exact number isn't: COLMAP's feature_extractor defaults to extracting up to 8192 features per image, and its default max_image_size is documented at 3200px in the community parameter cheatsheet ("colmap-parameters: parameter defaults cheatsheet"). An equirectangular frame that arrives below a reasonable width has less pixel budget to spread those features around a full 360-degree sweep before COLMAP's own internal downsampling kicks in, so a floor above COLMAP's default working resolution is a sane place to draw the line. Treat 3840 as a tunable pipeline constant, not a law of physics.

## What the check actually validates

Two independent things, and the function keeps them independent so a caller can tell which one failed:

1. **Aspect ratio is exactly 2:1.** Not "close to." The PanoTools example shows that even a one-pixel deviation is a real failure mode, so the check compares `width == height * 2` on decoded integers, no tolerance band.
2. **Width clears the floor.** A simple numeric comparison against the configured minimum.

Both checks need the image's pixel dimensions. Rather than pull in Pillow for a read that only needs two integers, the code below reads them straight out of the JPEG's own SOF (Start of Frame) marker using `struct` from the standard library. A JPEG is a sequence of markers, each starting with `0xFF` followed by a marker byte; the SOF0/SOF2 markers (`0xC0`/`0xC2`, covering baseline and progressive JPEGs, which covers what camera stitching pipelines and re-encoders typically produce) carry a fixed-layout segment with height and width as two big-endian 16-bit integers. Walking markers until you hit one of those is a well-known, dependency-free way to get image dimensions.

```python
"""
equirect_validate.py

Validates a stitched equirectangular JPG export before it enters the
Orbit Capture bundle-ingestion / COLMAP pipeline:
  1. width must equal exactly 2x height (true 2:1, PanoTools.org Wiki)
  2. width must be >= MIN_WIDTH_PX (Orbit Capture pipeline convention,
     not an externally sourced threshold -- tune to taste)
"""

from __future__ import annotations

import struct
from dataclasses import dataclass
from pathlib import Path

MIN_WIDTH_PX = 3840

# JPEG markers with no payload length prefix -- skip past these
# without trying to read a length field.
_NO_LENGTH_MARKERS = {0xD8, 0xD9, 0x01, *range(0xD0, 0xD8)}

# Start-Of-Frame markers that carry width/height (baseline + progressive).
_SOF_MARKERS = {0xC0, 0xC1, 0xC2, 0xC3, 0xC5, 0xC6, 0xC7,
                0xC9, 0xCA, 0xCB, 0xCD, 0xCE, 0xCF}


@dataclass
class ValidationResult:
    path: Path
    width: int
    height: int
    is_2to1: bool
    meets_width_floor: bool

    @property
    def ok(self) -> bool:
        return self.is_2to1 and self.meets_width_floor

    def reasons(self) -> list[str]:
        problems = []
        if not self.is_2to1:
            ratio = self.width / self.height if self.height else float("inf")
            problems.append(
                f"not 2:1 -- {self.width}x{self.height} (ratio {ratio:.4f})"
            )
        if not self.meets_width_floor:
            problems.append(
                f"width {self.width}px below floor of {MIN_WIDTH_PX}px"
            )
        return problems


def read_jpeg_dimensions(path: Path) -> tuple[int, int]:
    with open(path, "rb") as f:
        data = f.read(2)
        if data != b"\xff\xd8":
            raise ValueError(f"{path}: not a JPEG (bad SOI marker)")

        while True:
            marker_prefix = f.read(1)
            if not marker_prefix:
                raise ValueError(f"{path}: ran off end of file before SOF")
            if marker_prefix != b"\xff":
                continue

            marker_byte = f.read(1)
            if not marker_byte:
                raise ValueError(f"{path}: truncated marker")
            marker = marker_byte[0]

            if marker in _NO_LENGTH_MARKERS:
                continue

            length_bytes = f.read(2)
            if len(length_bytes) < 2:
                raise ValueError(f"{path}: truncated segment length")
            (segment_length,) = struct.unpack(">H", length_bytes)

            if marker in _SOF_MARKERS:
                sof_body = f.read(segment_length - 2)
                # SOF layout: precision(1) height(2) width(2) ...
                _precision, height, width = struct.unpack(">BHH", sof_body[:5])
                return width, height

            # Not the marker we want -- skip its payload and keep scanning.
            f.seek(segment_length - 2, 1)


def validate_equirect(path: Path, min_width_px: int = MIN_WIDTH_PX) -> ValidationResult:
    width, height = read_jpeg_dimensions(path)
    return ValidationResult(
        path=path,
        width=width,
        height=height,
        is_2to1=(width == height * 2),
        meets_width_floor=(width >= min_width_px),
    )


def validate_bundle(image_dir: Path, min_width_px: int = MIN_WIDTH_PX) -> list[ValidationResult]:
    results = []
    for jpg_path in sorted(image_dir.glob("*.jpg")):
        results.append(validate_equirect(jpg_path, min_width_px))
    return results


def demo() -> None:
    import io

    def _fake_jpeg_bytes(width: int, height: int) -> bytes:
        sof_payload = struct.pack(">BHH", 8, height, width) + b"\x01\x11\x00"
        segment_length = len(sof_payload) + 2
        return (
            b"\xff\xd8"
            + b"\xff\xc0" + struct.pack(">H", segment_length) + sof_payload
            + b"\xff\xd9"
        )

    def _check_from_bytes(raw: bytes) -> ValidationResult:
        import tempfile
        with tempfile.NamedTemporaryFile(suffix=".jpg", delete=False) as tmp:
            tmp.write(raw)
            tmp_path = Path(tmp.name)
        try:
            return validate_equirect(tmp_path)
        finally:
            tmp_path.unlink()

    good = _check_from_bytes(_fake_jpeg_bytes(7680, 3840))
    assert good.ok, good.reasons()

    too_narrow = _check_from_bytes(_fake_jpeg_bytes(3200, 1600))
    assert not too_narrow.ok
    assert too_narrow.meets_width_floor is False
    assert too_narrow.is_2to1 is True

    off_ratio = _check_from_bytes(_fake_jpeg_bytes(7680, 3839))
    assert not off_ratio.ok
    assert off_ratio.is_2to1 is False
    assert off_ratio.meets_width_floor is True

    print("all equirect validation checks passed")


if __name__ == "__main__":
    demo()
```

## Reading the failure modes, not just the pass/fail

`ValidationResult` deliberately keeps `is_2to1` and `meets_width_floor` as separate booleans instead of collapsing straight to a single pass/fail flag. In practice these two failures point at different upstream problems. A ratio failure almost always means the stitch itself was wrong: a dual-fisheye frame that never finished stitching, or that got cropped by an editing step after export, will drift off 2:1 even when it's otherwise a fine-looking image. A width-floor failure usually means someone exported at a lower quality preset, or a resize step ran somewhere in a transfer pipeline. Reporting both independently, via `reasons()`, means the bundle-ingestion step can log something actionable ("frame 0047: not 2:1, ratio 1.98") instead of a bare rejection.

The `demo()` function is the whole test surface this validator needs: it builds three minimal synthetic JPEGs entirely in memory (correct dimensions, correct-ratio-but-too-narrow, and wide-enough-but-off-ratio) using the same SOF marker layout the reader expects, and asserts the validator classifies each one correctly. That is enough to catch a regression in the marker-walking logic without needing a folder of real camera exports checked into the test suite.

## Wiring it into ingestion

`validate_bundle` is the entry point "Building the Bundle Ingestion Module: manifest.json to a COLMAP Project" should call before any equirectangular frame gets copied into a COLMAP working directory. Fail the whole bundle, or just drop and log the offending frame and continue: that policy choice belongs to the ingestion module, not to this check. What this check owns is a narrow, honest guarantee: by the time an image reaches COLMAP's feature extractor, it is provably 2:1 and provably above the configured width floor, both verified from the file's own JPEG header rather than trusted from a filename or a manifest field.
