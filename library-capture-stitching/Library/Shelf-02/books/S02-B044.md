# Automating a Reshoot Request from a Failed Registration

A registration health check is only useful if something acts on it. "Scripting a Registration Health Report from COLMAP Output" builds the number; this book wires that number to a decision: below a warning threshold, name the room and fire a reshoot request instead of quietly shipping a bad splat. The notes for this shelf are explicit that the exact thresholds (a warning line and a healthy line) are Orbit Capture product conventions, not something COLMAP itself defines, so treat the numbers below as tunable defaults, not physics.

## What COLMAP actually gives you to work with

COLMAP's incremental mapper can end up with images left unregistered, and it will happily produce multiple disconnected models rather than force everything into one ("Tutorial — COLMAP official docs"). The per-image console line during mapping looks like `Registering image #241 (230)` followed by `=> Image sees 3755 / 8696 points`, which is a directly parseable registered-vs-total-points ratio per image, though by default only high-level milestones print unless verbose logging is turned on via `GLOG_v=1`, `--v=1`, or `pycolmap.logging.verbose_level = 1` ("COLMAP incremental mapper console log format (PR #2420 discussion)"). The more durable source of truth, though, is the sparse model itself: `images.bin`/`images.txt` records which images actually made it into the reconstruction, and `points3D.txt` records the mean track length and reprojection error once bundle adjustment has run ("Output Format — COLMAP official docs"). Rather than scrape stdout, this book loads the model through pycolmap and computes registration ratio per room directly from the reconstruction object, which is the same approach the health-report book uses so the two share one data model.

## The core signal: registered images per room

Orbit Capture organizes a scan folder by room, so image filenames carry room identity (e.g. `kitchen_003.jpg`). The registration health for a room is simply the fraction of that room's captured images that pycolmap actually placed in the model.

```python
from pathlib import Path
from dataclasses import dataclass
import pycolmap

WARN_THRESHOLD = 0.60
HEALTHY_THRESHOLD = 0.95

@dataclass
class RoomHealth:
    room: str
    captured: int
    registered: int

    @property
    def ratio(self) -> float:
        return self.registered / self.captured if self.captured else 0.0

    @property
    def status(self) -> str:
        if self.ratio < WARN_THRESHOLD:
            return "fail"
        if self.ratio < HEALTHY_THRESHOLD:
            return "warn"
        return "healthy"


def room_of(image_name: str) -> str:
    return Path(image_name).stem.rsplit("_", 1)[0]


def compute_room_health(sparse_path: str, capture_manifest: dict[str, int]) -> list[RoomHealth]:
    reconstruction = pycolmap.Reconstruction(sparse_path)
    registered_by_room: dict[str, int] = {}
    for image in reconstruction.images.values():
        room = room_of(image.name)
        registered_by_room[room] = registered_by_room.get(room, 0) + 1

    return [
        RoomHealth(room=room, captured=captured, registered=registered_by_room.get(room, 0))
        for room, captured in capture_manifest.items()
    ]
```

`capture_manifest` is a plain `{room_name: image_count}` dict built at capture time, since that count has to come from the operator's own frame log, not from COLMAP (COLMAP only knows what it registered, never what was shot and dropped). `pycolmap.Reconstruction("path/to/sparse/model")` loading a model and exposing `.images`, `.points3D`, and `.cameras` as Python objects is the documented entry point for this kind of scripting ("pycolmap Python bindings — COLMAP docs / DeepWiki"). Note that if COLMAP produced multiple disconnected sub-models for the same scan, you need to run `compute_room_health` against each sparse model and merge the per-room registered counts, since a room split across two disconnected models still needs to be pooled to reflect its true registration count.

## From a failing ratio to a named reshoot request

The reshoot request itself is a small, boring state machine: walk the per-room health list, and for anything below `WARN_THRESHOLD`, emit one structured request that names the room, the ratio, and a suggested cause. It deliberately does not try to fix anything or infer camera settings; it hands a human (or a scheduling system) enough information to act.

```python
import json
import time
from dataclasses import asdict, dataclass, field

@dataclass
class ReshootRequest:
    room: str
    registered_ratio: float
    captured: int
    registered: int
    reason: str
    created_at: float = field(default_factory=time.time)


def build_reshoot_requests(rooms: list[RoomHealth]) -> list[ReshootRequest]:
    requests = []
    for r in rooms:
        if r.status != "fail":
            continue
        reason = "low registration ratio"
        if r.ratio == 0.0:
            reason = "room fully unregistered, likely a disconnected sub-model or missed capture pass"
        requests.append(
            ReshootRequest(
                room=r.room,
                registered_ratio=round(r.ratio, 3),
                captured=r.captured,
                registered=r.registered,
                reason=reason,
            )
        )
    return requests


def emit_reshoot_requests(requests: list[ReshootRequest], out_path: str) -> None:
    payload = [asdict(r) for r in requests]
    Path(out_path).write_text(json.dumps(payload, indent=2))
```

This is intentionally thin. "When to Trust a Low Registration Score and Reshoot Instead" is the book that argues for the judgment call underneath the threshold; this book assumes that call has already been made in policy (the two constants at the top of the file) and just automates the mechanical follow-through. Likewise, "Common Failure Signatures: Texture-Poor Rooms in the Sparse Model" catalogs why a room fails (blank walls, repeated tile, mirrors), but this script doesn't need to know why, only that it happened, because the fix is the same regardless of cause: send the operator back with a camera.

## Wiring it to a notification instead of a file

A JSON file on disk is a fine handoff for a batch pipeline, but a solo operator standing in the building wants a phone notification the moment registration fails, not a file to remember to check after driving home. Swap the sink for a lightweight webhook post; the pycolmap-and-threshold logic above is untouched.

```python
import urllib.request

def notify_reshoot(requests: list[ReshootRequest], webhook_url: str) -> None:
    if not requests:
        return
    lines = [
        f"{r.room}: {r.registered}/{r.captured} registered ({r.registered_ratio:.0%}) - {r.reason}"
        for r in requests
    ]
    body = json.dumps({"text": "Reshoot needed:\n" + "\n".join(lines)}).encode("utf-8")
    req = urllib.request.Request(
        webhook_url, data=body, headers={"Content-Type": "application/json"}
    )
    urllib.request.urlopen(req, timeout=10)
```

This uses only `urllib.request` from the standard library because a single JSON POST to a webhook (Slack-style incoming webhooks and most paging tools accept this shape) doesn't justify pulling in an HTTP client dependency.

## Putting it together as a post-mapper hook

The natural place to run this is right after `colmap mapper` (or `automatic_reconstructor`) finishes, before the pipeline moves on to dense reconstruction or Gaussian training. Failing fast here saves the GPU-hours that gsplat training would otherwise burn on a bad model.

```python
def check_and_reshoot(sparse_path: str, capture_manifest: dict[str, int],
                       out_path: str, webhook_url: str | None = None) -> list[ReshootRequest]:
    rooms = compute_room_health(sparse_path, capture_manifest)
    requests = build_reshoot_requests(rooms)
    emit_reshoot_requests(requests, out_path)
    if webhook_url:
        notify_reshoot(requests, webhook_url)
    return requests
```

A capture tool's orchestrator calls `check_and_reshoot` right after the mapper step exits, using the same `capture_manifest` it already tracked during the room-by-room walkthrough, and the same sparse model path it's about to hand to the health-report book or to dense reconstruction.

## Self-check

```python
def demo() -> None:
    manifest = {"kitchen": 40, "hallway": 25, "bathroom": 18}
    rooms = [
        RoomHealth(room="kitchen", captured=40, registered=39),
        RoomHealth(room="hallway", captured=25, registered=10),
        RoomHealth(room="bathroom", captured=18, registered=0),
    ]
    requests = build_reshoot_requests(rooms)
    assert {r.room for r in requests} == {"hallway", "bathroom"}
    assert all(r.registered_ratio < WARN_THRESHOLD for r in requests)
    bathroom = next(r for r in requests if r.room == "bathroom")
    assert "disconnected" in bathroom.reason
    print("ok:", [asdict(r) for r in requests])


if __name__ == "__main__":
    demo()
```
