# Setting Up a gsplat Training Run from a COLMAP Sparse Model

By the time you reach this step, a room (or a merged multi-room scene) already has a COLMAP sparse
model on disk: `cameras.bin`, `images.bin`, `points3D.bin`, produced by the mapper and refined by
bundle adjustment. The job in this book is narrow and mechanical: turn that sparse model plus the
original JPGs into a running gsplat training process, with the right launch flags for a single-room
capture versus a merged scene. Environment setup and the export/format conversion of the sparse
model are covered in "Setting Up a COLMAP + gsplat Environment in Python 3.11" and "Exporting COLMAP
Poses and Point Clouds for gsplat Training" respectively; this book assumes both are already done and
picks up at the point where you have a directory that looks like a valid gsplat dataset.

## What gsplat expects on disk

gsplat (the open-source library described in "gsplat: An Open-Source Library for Gaussian
Splatting", arXiv 2409.06765) trains a set of 3D Gaussians seeded from an SfM point cloud rather than
starting from an implicit neural field, following the original 3D Gaussian Splatting paper (Kerbl et
al., ACM TOG 42(4), 2023). That seeding is not optional in practice: the nerfstudio Splatfacto docs
note that their 3DGS implementation "works much better when initialized from pre-existing SfM
geometry... than from random initialization, which yields lower quality." A gsplat-style training
run therefore needs three things pointed at each other correctly:

- The undistorted (or distortion-aware) images directory.
- The COLMAP sparse model directory containing `cameras`, `images`, and `points3D` (binary or text).
- A camera model gsplat's rasterizer can actually consume.

That last point matters for Orbit Capture specifically. Splatfacto's own documentation states plainly
that "Gaussian rasterization assumes a perspective camera," and that fisheye and equirectangular
camera models are not currently supported by the rasterization pipeline. That means an Insta360 X4
Air capture cannot go into training as raw dual-fisheye or as a stitched 2:1 equirectangular JPG; it
must already have been split into perspective-camera crops (or otherwise reprojected) before it
reaches this stage. If your capture pipeline hands this script equirectangular frames, treat that as
a hard stop upstream, not something to patch here.

## Dataset layout and a config object

Rather than stringing together a wall of CLI flags, it's worth building a small dataclass that
represents one training job. This keeps room-by-room and merged-scene runs expressed as the same
object with different fields, which matters once Orbit Capture is launching several of these per
building.

```python
from dataclasses import dataclass, field
from pathlib import Path


@dataclass
class GsplatRunConfig:
    data_dir: Path
    result_dir: Path
    scene_name: str
    max_steps: int = 30_000
    strategy: str = "default"  # "default" (ADC) or "mcmc"
    sh_degree: int = 3
    data_factor: int = 1
    extra_args: list[str] = field(default_factory=list)

    def __post_init__(self) -> None:
        sparse = self.data_dir / "sparse" / "0"
        required = ["cameras.bin", "images.bin", "points3D.bin"]
        missing = [f for f in required if not (sparse / f).exists()]
        if missing:
            raise FileNotFoundError(
                f"{sparse} is missing {missing}; export the COLMAP model "
                "before starting a training run"
            )
        self.result_dir.mkdir(parents=True, exist_ok=True)
```

The `__post_init__` check is deliberately blunt: it does not validate that the sparse model is
*good*, only that the three files exist where gsplat's data loader expects them
(`data_dir/sparse/0/`, matching the COLMAP sparse output layout described in the COLMAP tutorial
docs). Whether the reconstruction is healthy (registration ratio, point density, reprojection error)
is a decision made earlier in the pipeline, not something worth re-deriving here.

## Building the launch command

gsplat's reference training entry point (`examples/simple_trainer.py` in the gsplat repository)
takes a data directory and a set of strategy/step flags. Rather than shelling out blind, wrap the
invocation so the same function handles a single room or a merged scene, the only difference being
which `data_dir` was pointed at a merged versus per-room sparse model.

```python
import subprocess
import sys


def build_gsplat_command(cfg: GsplatRunConfig) -> list[str]:
    cmd = [
        sys.executable,
        "-m",
        "gsplat.examples.simple_trainer",
        "default" if cfg.strategy == "default" else "mcmc",
        "--data-dir", str(cfg.data_dir),
        "--result-dir", str(cfg.result_dir),
        "--data-factor", str(cfg.data_factor),
        "--max-steps", str(cfg.max_steps),
        "--sh-degree", str(cfg.sh_degree),
    ]
    cmd.extend(cfg.extra_args)
    return cmd


def launch_training(cfg: GsplatRunConfig) -> subprocess.Popen:
    cmd = build_gsplat_command(cfg)
    log_path = cfg.result_dir / "train.log"
    log_file = open(log_path, "w", encoding="utf-8")
    return subprocess.Popen(
        cmd,
        stdout=log_file,
        stderr=subprocess.STDOUT,
        cwd=str(cfg.data_dir.parent),
    )
```

Using `subprocess.Popen` instead of `subprocess.run` matters here because a 30k-step training run can
take tens of minutes; the caller (a capture-tool UI, or a batch runner working through a building
room by room) needs the process handle back immediately so it can poll status rather than block. Log
redirection to a file, rather than piping through Python, is the cheap way to keep a persistent
record without holding the whole stdout stream in memory. Reading that log while training is running
is the subject of "Monitoring gsplat Training Loss and Point Cloud Growth"; this book only needs to
get the process started with the log going somewhere findable.

## Choosing a densification strategy

gsplat exposes the densification/pruning behavior as a swappable `Strategy` rather than baking it
into the trainer, per the Strategy API docs. Two are relevant here:

- `DefaultStrategy` implements the original adaptive density control: it splits or duplicates
  Gaussians whose accumulated 2D gradient exceeds `grow_grad2d` (default 0.0002), using
  `grow_scale3d` (default 0.01) to decide split-versus-duplicate, and prunes anything under
  `prune_opa` (default 0.005) opacity or over `prune_scale3d`/`prune_scale2d` (0.1 / 0.15). Refinement
  runs between `refine_start_iter` (500) and `refine_stop_iter` (15000), every `refine_every` (100)
  steps, with an opacity reset every `reset_every` (3000) steps.
- `MCMCStrategy` reframes the same densification as stochastic-gradient Langevin dynamics with
  injected noise, and instead of open-ended growth it enforces a hard `cap_max` (default 1,000,000
  Gaussians), with its own `refine_stop_iter` of 25000.

For a single interior room, the point-count ceiling on MCMC is usually a non-issue and either
strategy converges to comparable quality; the "gsplat" arXiv writeup reports MCMC using roughly 1.98
GB versus DefaultStrategy's 5.6 GB, with about a third the primitive count, on benchmark outdoor
scenes. For a merged multi-room scene, where an unbounded ADC run can balloon Gaussian count room by
room, `mcmc` with an explicit `cap_max` is the safer default: it keeps memory bounded regardless of
how many rooms got stitched into the merged model. Setting `cfg.strategy = "mcmc"` for merged-scene
configs and leaving single-room configs on the default strategy is a reasonable starting split; treat
it as a tuning knob, not a fixed rule, since the notes available do not give a documented threshold
for exactly when to switch.

## Room-by-room versus merged-scene runs

Nothing above changes between the two cases except which sparse model `data_dir` points at. A
per-room run points at that room's own `sparse/0/` (as produced directly by the mapper for that
room's image set). A merged-scene run points at the output of COLMAP's `model_merger`, which
combines two reconstructions that share common registered images by computing a similarity
transform between them, followed by a full `bundle_adjuster` pass to refine the merged alignment (per
the model_merger usage notes). Whichever sparse model was exported for gsplat training is what
"Exporting COLMAP Poses and Point Clouds for gsplat Training" hands off, and this book's config object
simply takes that path as `data_dir` without caring how the model was assembled upstream.

```python
def demo() -> None:
    room_cfg = GsplatRunConfig(
        data_dir=Path("captures/living-room/colmap"),
        result_dir=Path("runs/living-room"),
        scene_name="living-room",
        strategy="default",
    )
    merged_cfg = GsplatRunConfig(
        data_dir=Path("captures/full-house/colmap-merged"),
        result_dir=Path("runs/full-house"),
        scene_name="full-house",
        strategy="mcmc",
        extra_args=["--strategy.cap-max", "1500000"],
    )
    assert build_gsplat_command(room_cfg)[3] == "default"
    assert build_gsplat_command(merged_cfg)[3] == "mcmc"
    assert "--data-dir" in build_gsplat_command(room_cfg)
    print("config and command construction OK")


if __name__ == "__main__":
    demo()
```

That `demo()` is the whole verification story this book needs: it does not launch real training (too
slow for a sanity check), it just proves the config validation and command-building logic produce the
arguments you think they do, for both the single-room and merged-scene shapes. If `__post_init__`'s
file check or `build_gsplat_command`'s flag ordering ever regresses, this is what catches it before a
30-minute training run silently points at the wrong strategy or the wrong data directory.
