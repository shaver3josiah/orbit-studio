# Handling Multi-Session Buildings: Merging Separate Scans

You cannot always walk a building in one pass. A house has three floors and your phone battery has one charge. An office suite gets scanned wing by wing because tenants are still working in half of it. A warehouse takes two visits because the light changes too much between morning and afternoon to keep a single locked exposure. The question this book answers is simple to state and easy to get wrong in practice: how do you take several independent scanning sessions of the same building and end up with one coherent 3D model instead of several disconnected islands?

The naive hope is that COLMAP will just figure it out. Feed it every image from every session, run the pipeline, done. Sometimes this works, because COLMAP's incremental mapper is happy to register images from different sessions into the same model as long as it can find enough shared visual content between them (per the COLMAP tutorial's description of incremental SfM: registration and triangulation grow the model one image at a time from wherever the feature matches lead). But the tutorial is also explicit that COLMAP will reconstruct multiple separate models if not all images end up registered into one connected model. That is the failure mode you are actually planning for. Session boundaries are exactly where connectivity breaks: different lighting, a slightly different path through the same rooms, gaps in overlap where session one stopped and session two started from a different doorway. Two scans of the same building can produce two solid, well-registered, completely separate COLMAP models that share not one common camera pose.

Once you have two separate sparse models of the same physical space, COLMAP has a dedicated tool for stitching them back together: `model_merger`. The mechanics, per the COLMAP GitHub discussion on its usage and limitations, are worth understanding precisely because the tool is narrower than it sounds. `model_merger` merges two disconnected reconstructions that share common registered images, by computing a similarity transform from the shared images' poses. Read that carefully: it does not re-examine the raw pixels, it does not re-run matching between the two models, it looks at images that appear (by identifier) in both sub-models and computes the rotation, translation, and scale that best aligns one model's copies of those poses onto the other's. The command is straightforward: `colmap model_merger --input_path1 <sub-model1> --input_path2 <sub-model2> --output_path <merged-model>`. The output is a single merged sparse model sitting in one coordinate frame.

This is where the practical requirement becomes obvious: for `model_merger` to have anything to work with, your two sessions need overlapping images that both reconstructions actually registered, and those images need to carry the same identifiers across both sub-models, since the same GitHub source notes that `model_merger` assumes consistent image identifiers across the two sub-models. In an Orbit Capture workflow this has a direct operational consequence. If you scan a building in two sessions, do not treat the sessions as sealed compartments. Walk back through two or three rooms you already covered, or better, shoot a short bridging pass at the boundary between sessions before you leave. Those bridging shots need to end up processed as part of both reconstructions (or as shared images between the sub-models you feed into `model_merger`) so the tool has real, matched poses to compute a transform from. Skip the overlap and `model_merger` has nothing to align on: no shared registered images means no similarity transform, means no merge.

Even when the merge succeeds, the same source flags why you should not treat its output as final: `model_merger` can produce large alignment errors since it uses only the two models' poses, not full re-triangulation or re-matching. It is a geometric alignment step, not a bundle adjustment. It trusts the poses each sub-model already computed and rotates/translates/scales one onto the other. Any small residual disagreement between how session one and session two independently estimated those shared cameras' poses gets baked into the merge as-is. This is why the documented best practice, per the same discussion, is to run a full global `bundle_adjuster` pass on the merged model after merging. Bundle adjustment is the general-purpose refinement step described in the bundle adjustment literature (Hartley and Zisserman's treatment, as summarized on Wikipedia): it jointly refines 3D point coordinates and camera parameters against reprojection error across the whole model, and it is almost always the final step of a feature-based reconstruction pipeline for exactly this reason. Running it after a merge lets the optimizer smooth out the seam rather than leaving two locally-consistent but globally-misaligned halves glued together at one transform.

There is a second, more principled path if you know ahead of time that you are doing a multi-session capture, and it borrows from COLMAP's rig-support machinery even though a "rig" and a "revisited building" are not obviously the same thing. COLMAP's rig documentation describes a workflow for cases where relative sensor poses aren't known upfront: reconstruct without rig constraints first, then run `rig_configurator` against the existing reconstruction to average the relative poses from all registered images. The underlying idea, averaging a relative transform from many independent observations rather than trusting a single pairwise computation, is the same idea worth carrying into a multi-session merge: the more genuinely shared, well-matched images you have between sessions, the more `model_merger`'s similarity transform is effectively an average over many pose pairs rather than a fragile computation resting on two or three marginal matches. Bring more overlap, not less.

It is also worth being honest about where the global-versus-incremental mapper choice interacts with this problem, and where the notes run out. COLMAP's own comparison of incremental and global SfM (and GLOMAP, the global pipeline folded into recent COLMAP versions) describes global mapping as solving all camera poses simultaneously through rotation averaging rather than growing the model image by image, which in principle is more tolerant of a view graph with a complex, revisit-heavy topology like a multi-session building scan. But the notes available here do not document a case study of running global mapping specifically across multi-session captures versus running incremental mapping plus `model_merger`, so that comparison is a reasonable engineering hypothesis to test on your own data, not a claim this book can back with a citation. Test both if timing allows.

What this means for you as the operator is a planning discipline, not a repair procedure. Do not scan a building in disconnected chunks and hope alignment sorts itself out afterward. Plan every multi-session capture with deliberate overlap at the seams: re-shoot the last room of session one at the start of session two, or dedicate a short walk specifically to bridging the two. Keep those overlap images consistently identified if you are assembling sub-models by hand. Run `model_merger` to get one coordinate frame, then always follow it with `bundle_adjuster` before you trust the merged model enough to feed it into gsplat training. The seam between sessions is the same fundamental problem this shelf keeps returning to from different angles, discussed elsewhere in this library as Loop Closure and Why COLMAP Needs to Recognize Return Visits, Merging Overlapping Room Scans into One Coordinate Frame, and Handling Repeating Geometry: Avoiding False Loop Closures in COLMAP. A multi-session building is just that seam problem stretched across days instead of rooms.
