# Exporting a Trained Splat for a Walkable Viewer

A gsplat training run does not end with a viewer. It ends with a checkpoint: a
dictionary of tensors sitting in GPU memory, one row per Gaussian, with no
notion of "file" or "scene" at all. Closing the loop from captured frames to
an explorable scene is a separate, mechanical step, and it is the one solo
operators most often skip past, assuming the training script will hand them
something a browser can load. It will not. This book covers the export step:
what a trained Gaussian actually is, what a walkable viewer expects to read,
and a Python script that bridges the two.

## What the checkpoint actually holds

A trained gsplat scene is not a mesh and not a point cloud in the COLMAP
sense, though it starts from one. Per "3D Gaussian Splatting for Real-Time
Radiance Field Rendering," the scene is represented as a set of 3D Gaussians,
each one seeded from an SfM point and then optimized: it gains an anisotropic
covariance (so it can stretch into a thin disk or needle rather than staying
a sphere), a color response modeled as spherical harmonics so it looks
different from different viewing angles, and an opacity. The gsplat library's
Strategy API confirms the same per-Gaussian shape indirectly, through the
densification thresholds it exposes: `grow_scale3d` and `prune_scale3d`
operate on a Gaussian's 3D scale, `grow_grad2d` operates on its image-plane
gradient, and `prune_opa` operates on its opacity, all documented in "gsplat
documentation — Strategy API (DefaultStrategy / MCMCStrategy)." That tells
you the tensors you're exporting, even before you've opened a checkpoint:
means (xyz), scales (xyz), rotation (a quaternion), opacity (scalar), and
spherical-harmonic color coefficients (one DC term plus higher-order terms
if you trained with more than degree 0).

None of that is secret or exotic. It is exactly the same information
COLMAP's own sparse model stores in a cruder form. Per "Output Format —
COLMAP (official docs)," `points3D.txt` already carries `X, Y, Z, R, G, B`
per point; gsplat training just replaces the flat RGB with view-dependent
spherical harmonics and adds scale, rotation, and opacity around each point.
If you've been following the training loss and Gaussian counts as covered in
"Monitoring gsplat Training Loss and Point Cloud Growth," or you understand
why those parameters get optimized in the first place from "From Point Cloud
to Splat: What Training Actually Optimizes," this export step is where all
of that finally becomes a single portable file.

One caution carries over directly from training: per "Splatfacto —
nerfstudio documentation," Gaussian rasterization assumes a perspective
camera model, and fisheye or equirectangular cameras are not supported by the
rasterization pipeline. That constraint doesn't just affect training input,
it affects what "walkable" means downstream: your exported scene renders
correctly from perspective viewpoints inside a browser viewer, not by
re-projecting back through your Insta360's stitched equirectangular frames.

## What the notes don't cover

Here is the honest gap: the research notes for this shelf document COLMAP's
formats and gsplat's training-time parameters in detail, but they contain no
sourced description of the specific binary/PLY schema that popular splat
viewers (browser-based Gaussian splat viewers, PlayCanvas SuperSplat, and
similar) expect on load, so the property layout in the exporter below is a
reasonable, widely-used convention rather than a claim traceable to a source
in these notes.

## A minimal exporter

The shape below treats the trained scene as a dictionary of numpy arrays,
which is what you get after pulling tensors off the GPU regardless of which
training script produced them. Splat viewers overwhelmingly load a PLY file,
so the exporter writes PLY's ASCII header format with one vertex per
Gaussian and a binary little-endian payload, the same header/payload split
"Output Format — COLMAP (official docs)" describes for COLMAP's own dense
`fused.ply` output.

```python
import struct
import zipfile
from dataclasses import dataclass
from pathlib import Path

import numpy as np


@dataclass
class SplatScene:
    means: np.ndarray      # (N, 3) float32 xyz
    scales: np.ndarray     # (N, 3) float32, stored as log-scale
    quats: np.ndarray      # (N, 4) float32, wxyz, unnormalized ok
    opacities: np.ndarray  # (N,) float32, stored as inverse-sigmoid logit
    sh0: np.ndarray        # (N, 3) float32, DC spherical-harmonic term
    shN: np.ndarray        # (N, K, 3) float32, higher-order SH terms, K may be 0

    @property
    def count(self) -> int:
        return self.means.shape[0]


def _ply_header(scene: SplatScene) -> bytes:
    sh_rest = scene.shN.shape[1] * 3
    props = ["x", "y", "z"]
    props += [f"f_dc_{i}" for i in range(3)]
    props += [f"f_rest_{i}" for i in range(sh_rest)]
    props += ["opacity"]
    props += [f"scale_{i}" for i in range(3)]
    props += [f"rot_{i}" for i in range(4)]
    lines = [
        "ply",
        "format binary_little_endian 1.0",
        f"element vertex {scene.count}",
    ]
    lines += [f"property float {name}" for name in props]
    lines.append("end_header")
    return ("\n".join(lines) + "\n").encode("ascii")


def write_splat_ply(scene: SplatScene, path: Path) -> None:
    n = scene.count
    rest_flat = scene.shN.reshape(n, -1) if scene.shN.size else np.zeros((n, 0), dtype=np.float32)
    rows = np.concatenate(
        [
            scene.means.astype(np.float32),
            scene.sh0.astype(np.float32),
            rest_flat.astype(np.float32),
            scene.opacities.reshape(n, 1).astype(np.float32),
            scene.scales.astype(np.float32),
            scene.quats.astype(np.float32),
        ],
        axis=1,
    )
    with open(path, "wb") as f:
        f.write(_ply_header(scene))
        f.write(rows.tobytes())


def bundle_for_viewer(ply_path: Path, manifest: dict, out_zip: Path) -> None:
    import json

    with zipfile.ZipFile(out_zip, "w", zipfile.ZIP_DEFLATED) as zf:
        zf.write(ply_path, arcname="scene.ply")
        zf.writestr("manifest.json", json.dumps(manifest, indent=2))
```

The manifest is worth pausing on. A single PLY tells a viewer nothing about
where the walkable camera should start, what units the scene is in, or which
capture bundle it came from. Per "zipfile — Work with ZIP archives — Python 3
official documentation," a zip archive's `namelist()` and `read()` make it
trivial for a viewer to pull `manifest.json` out alongside `scene.ply` in one
request, so bundling both into a single `.zip` rather than shipping two
loose files keeps the scene and its metadata from drifting apart on disk:

```python
def export_trained_scene(scene: SplatScene, room_name: str, out_dir: Path) -> Path:
    out_dir.mkdir(parents=True, exist_ok=True)
    ply_path = out_dir / "scene.ply"
    write_splat_ply(scene, ply_path)

    manifest = {
        "room": room_name,
        "gaussian_count": scene.count,
        "sh_degree": int(round((scene.shN.shape[1] + 1) ** 0.5)) - 1 if scene.shN.size else 0,
        "up_axis": "y",
        "coordinate_convention": "colmap_world",
    }
    out_zip = out_dir / f"{room_name}.orbit-splat.zip"
    bundle_for_viewer(ply_path, manifest, out_zip)
    return out_zip
```

`coordinate_convention` is not decorative. Your Gaussians live in whatever
world frame COLMAP's bundle adjustment settled on, per the pose convention in
`images.txt` described in "Output Format — COLMAP (official docs)" (rotation
quaternion plus translation per registered image). A viewer that assumes a
different up-axis or handedness will load the file without error and render
a scene tipped on its side, which is a much harder bug to spot than a load
failure. Recording the convention explicitly in the manifest, rather than
assuming the viewer guesses right, is the cheap insurance.

## Where this fits

If you've automated the rest of the pipeline per "Writing an End-to-End
Bundle-to-Splat Orchestration Script," this export function is the last
stage that script should call: capture bundle in, `.orbit-splat.zip` out,
ready to hand to whatever walkable viewer your operator opens on a laptop or
phone. Everything upstream of it, from registration health to loss curves to
what the optimizer was actually doing to those Gaussians, only matters
insofar as it produces a scene worth exporting. This is the step where the
Gaussians stop being a training artifact and become a place someone can walk
through.
