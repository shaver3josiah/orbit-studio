# Extracting Camera Intrinsics and Rig Metadata from the Bundle

COLMAP can estimate camera intrinsics from scratch. Feed it a folder of JPGs and `feature_extractor` will default every image to the `SIMPLE_RADIAL` camera model and let bundle adjustment refine focal length and distortion as it goes. That works, but it throws away information you already have. The Orbit Capture bundle carries a manifest with per-shot metadata: the phone's reported focal length and sensor size, or, for 360 captures, the Insta360 X4 Air's known dual-fisheye geometry and the fixed relative pose between the two lenses. Reconstructing that from scratch by triangulation is strictly harder than reading it out of a JSON file that was sitting there the whole time.

This book covers the middle step: turning bundle metadata into COLMAP's own intrinsics and rig formats, so `feature_extractor` and `rig_configurator` start from known values instead of blind priors. It assumes you already have the bundle open in memory, as covered in "Reading the Bundle: Opening manifest.json and crops/*.jpg in Python", and that the params this book produces feed directly into "Parameterizing COLMAP Runs Per Rig Type from manifest.json", which decides which mapper and matcher strategy to run once the cameras are seeded.

## Why seed instead of estimate

COLMAP's own FAQ is direct about this trade-off: "if camera intrinsics are known ahead of time, individual parameter groups can be fixed during bundle adjustment; with enough shared-intrinsic images, SfM-estimated intrinsics are often better than manual calibration-pattern parameters" (COLMAP FAQ). Read carefully, that's not an argument for always seeding. It says a large, well-connected set of same-camera images can out-perform a checkerboard calibration once bundle adjustment gets enough views to converge. But an Orbit Capture room walkthrough is not that case: it's one operator, one lens, tens to low hundreds of images per room, often with fisheye or wide-FOV optics where the standard `SIMPLE_RADIAL` model's single distortion term is a rough fit at best. In that regime, seeding known intrinsics reduces what bundle adjustment has to discover from scratch, and seeding known rig geometry (for the X4 Air's two-lens rig) prevents COLMAP from re-deriving a relationship that's fixed by the camera's housing and never changes shot to shot.

The two things worth extracting are distinct and get consumed by different COLMAP commands:

- **Per-camera intrinsics**: model name, image width/height, and the parameter vector (focal length, principal point, distortion coefficients) that COLMAP's `cameras.txt` format expects: one line of `CAMERA_ID, MODEL, WIDTH, HEIGHT, PARAMS[]` per camera (COLMAP Output Format docs).
- **Rig geometry**: for multi-sensor captures, the fixed rotation and translation of each non-reference sensor relative to one reference sensor. COLMAP models this explicitly: "a COLMAP rig is a multi-sensor system whose sensors keep fixed relative poses to one reference sensor defining the rig's origin; synchronized captures across sensors are called frames" (COLMAP Rig Support docs).

## Reading intrinsics out of the manifest

The manifest schema is bundle-specific, but the fields worth pulling map cleanly onto COLMAP's camera parameter vector. For a single-lens phone capture with locked exposure, you typically have focal length in 35mm-equivalent or pixel units, plus image dimensions; for the X4 Air's dual-fisheye source, you have two lens entries sharing one rig ID.

```python
import json
from dataclasses import dataclass


@dataclass
class CameraIntrinsics:
    camera_id: int
    model: str
    width: int
    height: int
    params: list[float]


def camera_from_manifest_entry(entry: dict, camera_id: int) -> CameraIntrinsics:
    width = entry["width"]
    height = entry["height"]
    focal_px = entry.get("focal_length_px")

    if focal_px is None:
        # Fall back to 35mm-equivalent focal length if the bundle only
        # recorded that; convert using the sensor crop factor Orbit Capture
        # stamps alongside it during phone capture.
        focal_35mm = entry["focal_length_35mm_equiv"]
        crop_factor = entry["sensor_crop_factor"]
        focal_px = (focal_35mm / crop_factor) * (width / 36.0)

    cx, cy = width / 2.0, height / 2.0

    if entry.get("lens_type") == "fisheye":
        # OPENCV_FISHEYE: fx, fy, cx, cy, k1, k2, k3, k4
        model = "OPENCV_FISHEYE"
        params = [focal_px, focal_px, cx, cy, 0.0, 0.0, 0.0, 0.0]
    else:
        # SIMPLE_RADIAL: f, cx, cy, k -- COLMAP's feature_extractor default
        model = "SIMPLE_RADIAL"
        params = [focal_px, cx, cy, 0.0]

    return CameraIntrinsics(camera_id, model, width, height, params)


def write_cameras_txt(cameras: list[CameraIntrinsics], out_path: str) -> None:
    with open(out_path, "w") as f:
        f.write("# CAMERA_ID, MODEL, WIDTH, HEIGHT, PARAMS[]\n")
        for cam in cameras:
            params_str = " ".join(f"{p:.6f}" for p in cam.params)
            f.write(f"{cam.camera_id} {cam.model} {cam.width} {cam.height} {params_str}\n")
```

Two things to notice. First, distortion terms are seeded at zero rather than guessed, because the manifest usually doesn't carry a calibrated distortion estimate, and it's safer to let bundle adjustment refine distortion from real correspondences than to fabricate a plausible-looking coefficient. Second, the model choice matters upstream too: `feature_extractor`'s `--ImageReader.camera_model` flag defaults to `SIMPLE_RADIAL`, and `--ImageReader.single_camera` / `--ImageReader.single_camera_per_folder` (both default 0) control whether a batch of images is treated as sharing one camera or gets a fresh camera per image (COLMAP CLI docs). If every image in a room came from the same locked-exposure phone session, you want `single_camera_per_folder=1` so COLMAP doesn't allocate a redundant camera entry per shot.

## Extracting rig metadata for the X4 Air

The X4 Air's two fisheye lenses are physically fixed relative to each other inside the housing, so their relative pose doesn't need to be discovered by SfM at all, it's a manufacturing constant your capture tool already knows or can measure once and store in the manifest. COLMAP's rig workflow consumes that as a JSON config: "known rig geometry (`cam_from_rig_rotation` quaternion, `cam_from_rig_translation` xyz, optional `camera_model_name`/`camera_params` per camera) is supplied via a JSON config consumed by `colmap rig_configurator --database_path ... --rig_config_path rig_config.json`" (COLMAP Rig Support docs).

```python
def build_rig_config(manifest: dict) -> dict:
    lenses = manifest["insta360_lenses"]
    reference = lenses[0]
    others = lenses[1:]

    cameras = [{
        "camera_id": reference["camera_id"],
        "image_prefix": reference["image_prefix"],
    }]

    for lens in others:
        cameras.append({
            "camera_id": lens["camera_id"],
            "image_prefix": lens["image_prefix"],
            "cam_from_rig_rotation": lens["cam_from_rig_rotation_wxyz"],
            "cam_from_rig_translation": lens["cam_from_rig_translation_xyz"],
        })

    return {"rigs": [{"cameras": cameras}]}


def save_rig_config(manifest: dict, out_path: str) -> None:
    with open(out_path, "w") as f:
        json.dump(build_rig_config(manifest), f, indent=2)
```

This only applies when you're feeding COLMAP the raw dual-fisheye pair per capture point rather than a pre-stitched equirectangular JPG; if the bundle already stitched to 2:1 equirectangular before handoff, there's no two-lens rig left to describe, just one unusual camera model, and this rig step doesn't apply. When it does apply, lock the relationship during optimization: "setting `--Mapper.ba_refine_sensor_from_rig 0` locks relative rig-sensor poses during bundle adjustment, preventing them from drifting apart" (COLMAP Rig Support docs). If your manifest doesn't have a trustworthy relative pose yet, COLMAP also documents the inverse workflow: "when rig poses aren't known upfront, the documented workflow is: reconstruct without rig constraints first, then run `rig_configurator` against the existing reconstruction to average the relative sensor poses from all registered images" (COLMAP Rig Support docs). That's a reasonable fallback for a first capture of a new rig configuration, before you've measured and cached the offset.

## Wiring it into the run

Once `cameras.txt` and (optionally) `rig_config.json` exist, they get consumed before matching starts:

```python
import subprocess


def seed_colmap_database(database_path: str, image_path: str, rig_config_path: str | None) -> None:
    subprocess.run([
        "colmap", "feature_extractor",
        "--database_path", database_path,
        "--image_path", image_path,
        "--ImageReader.single_camera_per_folder", "1",
    ], check=True)

    if rig_config_path:
        subprocess.run([
            "colmap", "rig_configurator",
            "--database_path", database_path,
            "--rig_config_path", rig_config_path,
        ], check=True)
```

Note that `feature_extractor` here is still letting COLMAP pick its own default parameters per camera rather than importing your `cameras.txt` values directly; the practical path most bundles take is to run extraction once, then overwrite the resulting camera rows in the database with your known intrinsics before matching, since COLMAP's CLI doesn't expose an argument to import a full `cameras.txt` at extraction time. The rig-relative constraints from `rig_config.json`, by contrast, do apply directly through `rig_configurator` and then take effect during the mapper's bundle adjustment pass, which is where "Parameterizing COLMAP Runs Per Rig Type from manifest.json" picks up: choosing `--Mapper.ba_refine_sensor_from_rig` and the rest of the run's parameters based on which rig type produced the bundle.

Whatever intrinsics and rig constraints you seed, they only matter if they show up correctly in the reconstruction COLMAP hands back. "Exporting COLMAP Poses and Point Clouds for gsplat Training" covers reading `cameras.bin`, `images.bin`, and (for rigged captures) `rigs.bin` and `frames.bin` back out once reconstruction finishes, so you can confirm the seeded values held rather than drifted away under bundle adjustment.

The notes available for this book cover COLMAP's own rig JSON schema, its cameras.txt format, and its CLI flags for camera model selection well; they do not cover the Insta360 Media SDK's own stitching or calibration API in detail; that gap is called out explicitly in the shelf's research notes rather than filled with invented method signatures, so the fisheye-lens rig fields above assume you're sourcing `cam_from_rig_rotation`/`cam_from_rig_translation` from your own measured or vendor-supplied calibration, not from a documented SDK call.
