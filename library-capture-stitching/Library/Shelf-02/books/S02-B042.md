# Merging Overlapping Room Scans into One Coordinate Frame

You walked the building room by room. Each room got its own bundle of stills, its own COLMAP database, its own sparse reconstruction with its own arbitrary coordinate origin. That is normal, not a mistake: COLMAP will happily produce several disconnected models from one folder of images if the images never accumulated enough shared feature tracks to register into a single model ("Tutorial - COLMAP"). The hallway overlap shots you took on purpose are what stitch these separate rooms back into one building. This book codes that stitch: turning two independently-reconstructed room models into one shared coordinate frame, ready to hand to gsplat as a single training set.

This is the alignment cousin of "Handling Multi-Session Buildings: Merging Separate Scans," which deals with the higher-level problem of entire capture sessions taken on different days. Here the scope is narrower and more mechanical: two sub-models from the same session, same day, same lighting, that share a doorway's worth of overlapping images.

## Why two rooms end up as two models in the first place

COLMAP's incremental mapper seeds a reconstruction from one image pair, then grows it by registering new images one at a time, triangulating new points as it goes ("Tutorial - COLMAP"). If the hallway-transition images between Room A and Room B do not carry enough shared, well-matched features, the mapper simply gives up on connecting them and starts a second model instead of a second branch of the first. You end up with `sparse/0` and `sparse/1`, each internally consistent, each in its own arbitrary rotation/translation/scale.

The fix is not to re-run everything from scratch. COLMAP ships a purpose-built tool for exactly this: `model_merger`. It merges two disconnected reconstructions that already share some registered images, by computing a similarity transform from the poses of those shared images ("COLMAP model_merger usage and limitations"). No re-matching, no re-triangulation, just algebra on the poses you already have.

## The merge command, then the safety net

The command itself is one line:

```bash
colmap model_merger \
  --input_path1 room_a/sparse/0 \
  --input_path2 room_b/sparse/0 \
  --output_path merged/sparse/0
```

That is the entire documented usage ("COLMAP model_merger usage and limitations"). It is also where the honest caveats live: `model_merger` assumes the two sub-models share consistent image identifiers for the overlapping images, and because it estimates the transform purely from the two models' existing poses rather than re-matching or re-triangulating, it can produce large alignment errors if those shared poses are individually imprecise. The documented best practice is to always follow the merge with a full global bundle adjustment pass to refine the combined model:

```bash
colmap bundle_adjuster \
  --input_path merged/sparse/0 \
  --output_path merged/sparse/0_refined
```

Bundle adjustment jointly refines the 3D points, camera poses, and (optionally) intrinsics against the reprojection error of every image observation ("Bundle adjustment - Wikipedia"), so this pass is what actually irons out the seam rather than just trusting the raw similarity transform.

## Wrapping the merge in Python for the pipeline

You do not want a shell script buried in your build; you want a function the orchestrator (see "Writing an End-to-End Bundle-to-Splat Orchestration Script") can call and check. `pycolmap` exposes the same scene classes the CLI works with, so a Python wrapper can validate the merge instead of trusting a silent success exit code.

```python
import subprocess
from pathlib import Path
import pycolmap


def merge_room_models(
    room_a_sparse: Path,
    room_b_sparse: Path,
    output_sparse: Path,
    min_shared_images: int = 3,
) -> pycolmap.Reconstruction:
    rec_a = pycolmap.Reconstruction(str(room_a_sparse))
    rec_b = pycolmap.Reconstruction(str(room_b_sparse))

    names_a = {img.name for img in rec_a.images.values()}
    names_b = {img.name for img in rec_b.images.values()}
    shared = names_a & names_b
    if len(shared) < min_shared_images:
        raise ValueError(
            f"Only {len(shared)} shared registered images between "
            f"{room_a_sparse} and {room_b_sparse}; need at least "
            f"{min_shared_images} to trust model_merger's similarity "
            "transform. Reshoot the doorway transition or add sequential "
            "matches between the two rooms and re-run the mapper first."
        )

    output_sparse.mkdir(parents=True, exist_ok=True)
    subprocess.run(
        [
            "colmap", "model_merger",
            "--input_path1", str(room_a_sparse),
            "--input_path2", str(room_b_sparse),
            "--output_path", str(output_sparse),
        ],
        check=True,
    )

    refined = output_sparse.parent / f"{output_sparse.name}_refined"
    refined.mkdir(parents=True, exist_ok=True)
    subprocess.run(
        [
            "colmap", "bundle_adjuster",
            "--input_path", str(output_sparse),
            "--output_path", str(refined),
        ],
        check=True,
    )

    return pycolmap.Reconstruction(str(refined))
```

The `min_shared_images` guard is not decoration. Loading each sub-model with `pycolmap.Reconstruction(...)` and comparing `.images` name sets ("pycolmap Python bindings") is cheap, and it catches the single most common failure mode before you burn a `model_merger` call on it: not enough shared images to constrain a similarity transform at all. `model_merger` will still run on two shared images, but a transform anchored by two points has no redundancy to average out pose error, which is exactly the fragility the tool's own limitations note warns about.

## Why this only works because the doorway shots are not a pure pan

It is worth being explicit about why walking through a doorway with overlapping stills works here but a panorama-style pivot-in-place would not. Two camera positions that differ only by rotation, with no real translation between them, put every corresponding ray through the same 3D line: there is no parallax to recover depth or scale from ("Pure rotation as a degenerate two-view geometry configuration"). That is precisely the assumption classic panorama stitching leans on: pure rotation about the optical center, resolved with a single homography ("Panorama stitching's single-viewpoint (no-parallax) assumption"). It is also exactly the case that defeats SfM triangulation. The reason your hallway-transition shots register into both room models at all is that you were walking, not spinning: each step gave the mapper real translation and real parallax to triangulate against, which is what let those images pick up 3D points from both rooms and made them the anchors `model_merger`'s similarity transform depends on.

## Guarding against a false doorway match

The overlap region between two rooms is also the likeliest place for a bad match to sneak in unnoticed, for a reason that generalizes past this specific alignment step: perceptually similar but spatially distinct places produce near-identical descriptors, and that aliasing is the core cause of false loop-closures in SLAM-style pipelines ("Perceptual aliasing and false loop closures in repetitive environments"). A false-positive closure corrupts a pose graph by asserting two distinct places are the same one ("Perceptual aliasing and false loop closures in repetitive environments"); the direct analogue here is a false match between, say, two similar-looking hallway sections that quietly pulls `model_merger`'s transform toward the wrong answer. Two mitigations from that literature translate directly: prefer matching short sequences of consecutive frames over single isolated frames, and treat any candidate shared-image set with suspicion if it is small. The `min_shared_images` check above is a blunt version of exactly that second mitigation, and it costs three lines.

The gaps file for this shelf's research is candid that no source pins down an exact numeric threshold for "healthy" versus "risky" overlap-region registration; the 3-image floor here is a conservative, defensible convention grounded in the same aliasing literature, not a number handed down by COLMAP itself. Say so plainly rather than presenting it as an official spec.

## Inspecting what actually merged

Before trusting `merged/sparse/0_refined`, look at the joined model's bundle-adjustment error and registered-image count, both of which are visible straight off the `pycolmap.Reconstruction` object:

```python
def summarize_merge(rec: pycolmap.Reconstruction) -> dict:
    errors = [p.error for p in rec.points3D.values()]
    mean_error = sum(errors) / len(errors) if errors else float("nan")
    return {
        "num_images": len(rec.images),
        "num_points3D": len(rec.points3D),
        "mean_reprojection_error_px": mean_error,
    }
```

`points3D.txt`'s `ERROR` field is the mean reprojection error in pixels for that point's track, and it is only meaningful after a global bundle adjustment has actually run over the model ("Output Format - COLMAP"), which is exactly why `summarize_merge` should be called on the refined reconstruction, not the raw merger output. A merged model whose mean error jumped well past what either room's original model reported on its own is telling you the doorway match was weaker than it looked, and it is worth re-checking before this bundle ever reaches "Exporting COLMAP Poses and Point Clouds for gsplat Training," where a bad merge shows up much later and much harder to diagnose, as a warped seam in the trained splat.

## Self-check

```python
def demo():
    assert callable(merge_room_models)
    try:
        merge_room_models(Path("nope_a"), Path("nope_b"), Path("nope_out"))
    except Exception:
        pass
    else:
        raise AssertionError("expected missing reconstructions to raise")
    print("merge_room_models guard behaves as expected")


if __name__ == "__main__":
    demo()
```

This does not stand up a real COLMAP install; it confirms the guard rails fail loud on bad input rather than silently emitting a garbage merge, which is the failure mode that actually costs you time on a real capture.
