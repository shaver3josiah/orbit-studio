# The Rotation-Only Trap: Diagnosing a Degenerate Baseline

How do you tell, from a COLMAP run that finished without a single error, that the reconstruction it handed you is unusable?

This is not a hypothetical. It is the single most common way a solo Orbit Capture session goes wrong. The operator stands in the middle of a room and pivots on their feet, sweeping the phone or the Insta360 X4 Air around in a circle to cover every wall. COLMAP ingests the images, extracts features, matches them, registers every single frame, and writes out a sparse model with no warnings. Everything about the run looks healthy. And the Gaussian splat trained from it comes out flat, smeared, or refuses to converge at all. The sibling volume *Baseline Requirements for gsplat: Why Pure Rotation Fails Training* explains why this happens mechanically. This book is about catching it earlier, directly from COLMAP's own pose output, before you waste a training run finding out the hard way.

**Why full registration doesn't mean full success**

The instinct is to treat "100% of images registered" as the success signal. It is not. Registration only means COLMAP found enough 2D feature matches between images to solve for each camera's rotation and position relative to the others. A pure pivot on one spot gives COLMAP exactly the kind of images it's good at handling: same features, same scene, high overlap, easy correspondences. It will register cleanly. The problem is what those correspondences can and can't tell the solver.

The underlying geometry is well understood: when two camera positions differ only by rotation, with no translation between them, every corresponding ray from the two images intersects along the same 3D line rather than at a distinct point in space. There is no parallax to triangulate against, so absolute depth and scale cannot be recovered from that image pair (source: "Pure rotation as a degenerate two-view geometry configuration"). The same literature makes an important secondary point: the rotational component itself can often still be recovered even when translation and structure cannot. That is exactly the trap. COLMAP can solve the rotations, register every image, and print a clean log, all while never having had the parallax it needed to build real 3D structure. It is worth noting this is the same assumption panorama-stitching software depends on deliberately: classic automatic panorama stitching aligns images with a single homography specifically because it assumes the camera only rotates about its optical center with no translation (source: image-stitching survey/tutorial literature, arXiv 1701.08006). A rotation-only capture is, geometrically, a panorama. It just isn't the input gsplat needs.

**Reading the pose file instead of the summary**

COLMAP's text output format gives you exactly what you need to check this yourself. In `images.txt`, each registered image gets two lines: the first carries the image ID, a rotation quaternion (QW, QX, QY, QZ), and a translation vector (TX, TY, TZ), followed by the camera ID and filename (source: "Output Format — COLMAP official docs"). That translation vector is the diagnostic. In a healthy walkthrough capture, the TX/TY/TZ values spread out across the images, tracing the physical path the operator walked through the room. In a rotation-only capture, those translation values cluster tightly around a single point, image after image, because the operator never actually moved the optical center. The quaternions will vary widely, showing all the pivoting that happened. The translations will not.

This is a check you can run without loading a viewer. Pull `images.txt` (or the equivalent from pycolmap, which loads a reconstruction with `pycolmap.Reconstruction("path/to/sparse/model")` and exposes `.images` as Python objects) and look at the spread of translation vectors across the sequence. If the operator walked ten feet across a room, the translations should reflect a path of comparable scale relative to the scene. If they collapse to a small cluster no matter how many images you have, you are looking at a pivot, not a walkthrough, regardless of what the registration percentage says.

**What the console log tells you as it happens**

You don't have to wait for the run to finish to notice this. COLMAP's incremental mapper prints per-image registration lines during the reconstruction itself, such as "Registering image #241 (230)" followed by a line reporting how many of the model's existing points that image sees (source: "COLMAP incremental mapper console log format," PR #2420). By default only high-level milestones print; the detailed per-image statistics require verbose logging via `GLOG_v=1`, `--v=1`, or setting `pycolmap.logging.verbose_level = 1`. Turn that verbosity on for a rotation-only sequence and a specific pattern shows up: images keep registering, and the points-seen count keeps climbing, but they're all seeing the same tight cluster of triangulated points near the capture origin, not new points further into the scene. Feature counts and match counts can look completely normal here. What's missing is depth variation in what gets triangulated, which is a direct consequence of the missing parallax the rotation degeneracy causes.

**Why this justifies a dedicated check, not just a good eye**

It would be easy to say "just look at the sparse point cloud in a viewer," and that is a reasonable secondary check, but it doesn't scale to an automated capture tool, and a small, subtly curved walking path can look deceptively similar to a pivot in a casual viewer glance. Reading the translation vectors directly out of `images.txt` gives you a number, not an impression: compute the spread (for example, the bounding box or standard deviation of TX/TY/TZ across the sequence) and compare it to the physical scale of the room the operator says they captured. That comparison is exactly the kind of check an engineer building the capture tool can run automatically right after the COLMAP job finishes, flagging the session before it ever reaches gsplat training.

It's also worth being honest about a limit here: this check tells you a sequence has no meaningful translation, but it doesn't by itself tell you whether the translation that does exist is sufficient, only that it exists. A capture with a few feet of real movement in an otherwise cramped pattern will pass this check while still under-supporting large sections of a room. That finer-grained question, how much parallax is enough per frame rather than in aggregate, is the concern of *Filtering Frames with Insufficient Parallax Before Training*. And the reason any of this matters for training quality in the first place goes back to *What a Gaussian Splat Is and Why It Needs a Baseline*.

**What this means for the operator**

If you build one habit into your capture routine, make it this: before you commit to a training run, pull the translation vectors out of the sparse model and confirm they trace a path with a scale that matches how far you actually walked. If they collapse to a point regardless of how much you turned in place, the sequence needs to be recaptured with real translation between frames, not just more pivoting. A clean COLMAP log is not proof of a usable baseline. The pose file is where the truth actually lives, and it takes one look to see it.
