# Handling Repeating Geometry: Avoiding False Loop Closures in COLMAP

A hotel corridor with identical doors every ten feet. A hospital wing where every patient room is the same room. An office floor with the same cubicle layout repeated four times. These are the buildings that break COLMAP in a specific, quiet way: not by failing to register images, but by registering them *too confidently* into the wrong place.

As covered in "Loop Closure and Why COLMAP Needs to Recognize Return Visits," COLMAP does not run a dedicated loop-closure module the way visual SLAM systems do. It relies on feature matching and geometric verification to decide whether two images observe the same 3D structure, then folds that belief into the same incremental bundle adjustment used for everything else. That is fine for scenes where "looks the same" reliably means "is the same place." Repeating geometry breaks the premise. This book is about closing that gap with logic that sits between capture and reconstruction, not inside COLMAP itself.

## Why repeating rooms fool the matcher

The failure mode here is perceptual aliasing: visually or structurally similar but spatially distinct places produce near-identical feature descriptors, which is the core cause of false-positive loop closures and is especially severe in repetitive environments (Perceptual aliasing and false loop closures in repetitive environments, ROVER). A false loop closure that gets accepted corrupts the pose graph, because it wrongly asserts two distinct locations are the same place (same source). Room 204 and Room 304 in an Orbit Capture hotel scan can share the same carpet, the same bed frame, the same window trim, at the same relative distance from camera to wall. SIFT or ALIKED descriptors extracted from those two rooms will match at rates indistinguishable from true same-room matches.

COLMAP's exhaustive matcher makes this worse by construction: it matches all possible image pairs and is intended for small datasets, up to a few hundred images (Feature Extraction and Matching, COLMAP docs). It has no concept of "these two images were captured forty minutes and three floors apart." The sequential matcher matches images in capture/sequential order and is suited to video-like or ordered walkthrough sequences (same source), which already helps by not comparing arbitrary pairs, but a solo operator's room-by-room capture is not a single continuous sequence with clean topology; sequence order alone cannot tell COLMAP that image 800 (Room 304, session start) is not the same place as image 40 (Room 204, session start), because both are "the first shot after entering a room."

The mitigations documented for this class of problem are probabilistic modeling of ambiguous candidates and matching short sequences of consecutive observations, temporal context, rather than single-frame descriptors, to reduce aliasing-driven false matches (same source). We can implement a version of that idea entirely outside COLMAP: gate candidate matches by metadata before they ever reach the matcher, and re-verify anything COLMAP itself decides looks like a loop closure.

## Layer 1: constrain the candidate set before matching

The cheapest fix is never letting the aliased pair become a candidate. COLMAP's `spatial_matcher` restricts pairing to images with nearby geolocation priors, and `sequential_matcher` restricts pairing to capture-order neighbors (Command-line Interface, COLMAP docs). Neither of those alone captures "same building, different floor, same-looking room," but a manifest-driven room ID solves it directly: tag every image with the room/session it came from during capture, then only allow matching within a room or between rooms declared adjacent.

```python
# match_plan.py
# Builds a custom match-pair list instead of trusting exhaustive_matcher's
# blind all-pairs default. Consumes a per-image manifest the capture tool
# writes alongside the JPGs.

import json
import sqlite3
import itertools
from pathlib import Path

def load_manifest(bundle_dir: Path) -> dict:
    # Notes cite zipfile.ZipFile + json.loads(zf.read("manifest.json"))
    # as the documented way to pull a manifest out of a capture bundle
    # (zipfile docs). Here the bundle is already unpacked to disk.
    manifest = json.loads((bundle_dir / "manifest.json").read_text())
    return {entry["image"]: entry for entry in manifest["images"]}

def build_pairs(images: dict, adjacency: dict[str, set[str]]) -> list[tuple[str, str]]:
    by_room: dict[str, list[str]] = {}
    for name, meta in images.items():
        by_room.setdefault(meta["room_id"], []).append(name)

    pairs = []
    for room, names in by_room.items():
        pairs.extend(itertools.combinations(sorted(names), 2))
        for neighbor in adjacency.get(room, ()):
            for a in names:
                for b in by_room.get(neighbor, ()):
                    pairs.append((a, b))
    return pairs

def write_match_list(pairs: list[tuple[str, str]], out_path: Path) -> None:
    with out_path.open("w") as f:
        for a, b in pairs:
            f.write(f"{a} {b}\n")
```

That match list feeds `colmap matches_importer`, one of the matching commands documented alongside `exhaustive_matcher`, `vocab_tree_matcher`, `sequential_matcher`, `spatial_matcher`, and `transitive_matcher` (Command-line Interface, COLMAP docs), instead of letting an unconstrained matcher decide which rooms are allowed to talk to each other:

```bash
colmap matches_importer \
    --database_path workspace/database.db \
    --match_list_path match_pairs.txt \
    --match_type pairs
```

This is a room-ID adjacency graph the capture tool already knows (which room follows which in the walk), turned into a hard constraint on the matcher's input. It is deliberately conservative: two rooms not marked adjacent simply never get compared, so an identical-looking Room 204 and Room 304 pair is never proposed in the first place, provided the manifest's room IDs are trustworthy. If the operator mislabels a room, the constraint fails silently, so validating the manifest against session timestamps is worth doing before this step runs, not after.

## Layer 2: re-verify anything COLMAP still wants to register as a loop closure

Constraining match pairs handles the common case, but hallway shots and doorway transition frames can genuinely look identical across rooms even within an adjacency-correct pipeline, and COLMAP's incremental mapper will still try to register an image against whatever model points look closest. As covered in "Writing a Loop-Closure-Aware Matching Pass for Room Sequences," the fix at that stage is a post-hoc consistency check using pycolmap rather than trusting the mapper's acceptance outright.

pycolmap exposes COLMAP's scene classes, Reconstruction, Image, Camera, Frame, Rig, Point3D, and lets you override default incremental-mapping behavior to build custom SfM pipelines instead of only using the CLI (pycolmap Python bindings docs). A reconstruction loads with `pycolmap.Reconstruction("path/to/sparse/model")`, after which `.images`, `.points3D`, and `.cameras` are accessible as Python objects (same source). That is enough to write a disambiguation pass that runs after each incremental registration step and rejects registrations that are geometrically implausible even though they matched.

```python
# loop_guard.py
# Runs after colmap mapper (or between incremental steps if driving
# pycolmap.IncrementalPipeline directly) to flag suspicious registrations.

import pycolmap
import numpy as np

MAX_PLAUSIBLE_JUMP_M = 3.0  # ponytail: tuned per building scale, not derived

def suspicious_registrations(model_path: str, manifest: dict) -> list[str]:
    reconstruction = pycolmap.Reconstruction(model_path)
    flagged = []

    images_by_name = {img.name: img for img in reconstruction.images.values()}
    ordered_names = sorted(images_by_name, key=lambda n: manifest[n]["capture_index"])

    for prev_name, curr_name in zip(ordered_names, ordered_names[1:]):
        prev_room = manifest[prev_name]["room_id"]
        curr_room = manifest[curr_name]["room_id"]
        if prev_room == curr_room:
            continue

        prev_center = images_by_name[prev_name].projection_center()
        curr_center = images_by_name[curr_name].projection_center()
        jump = np.linalg.norm(np.array(curr_center) - np.array(prev_center))

        if jump < MAX_PLAUSIBLE_JUMP_M and manifest[prev_name].get("far_apart_rooms"):
            flagged.append(curr_name)

    return flagged
```

The idea mirrors what pure-rotation degeneracy already tells us about two-view geometry: when two camera positions differ only by rotation, all corresponding rays intersect along the same 3D line, so there is no parallax to disambiguate scale or position (rotation-only pose literature). A false loop closure between two identical rooms produces exactly this signature at the reconstruction level: COLMAP is confident about the match, but the resulting camera position for the "returning" image sits implausibly close to a room it should be physically distant from, because the two rooms were never actually the same rig position, only the same-looking one. Checking projected camera centers against a manifest's declared room-to-room distances (even coarse ones, "these rooms are on opposite ends of the floor") catches what descriptor matching alone cannot.

This is deliberately a coarse heuristic, not a formal aliasing detector: it only flags implausible jumps between manifest-declared distant rooms, and a mislabeled or missing manifest entry defeats it entirely. It buys real protection cheaply, though, precisely because it runs after COLMAP's own bundle adjustment has already committed to a reprojection-error-minimizing pose (Bundle adjustment, Wikipedia summary of Hartley & Zisserman), so a flagged image is one COLMAP is confident about for the wrong reason, not one it was already uncertain of.

## Layer 3: when the two rooms really should merge, do it explicitly

Sometimes rooms genuinely are connected, an open floor plan, a doorway between two aliased-looking spaces, and the fix is not rejection but an explicit, auditable merge rather than letting the mapper guess. That is the domain of "Handling Multi-Session Buildings: Merging Separate Scans," which covers `model_merger`: it merges two disconnected reconstructions that share common registered images by computing a similarity transform from those images' poses, and the documented best practice afterward is a full global `bundle_adjuster` pass to refine the alignment (COLMAP model_merger usage and limitations). Reconstructing suspicious room pairs as separate sub-models first, then merging only the ones a human or the manifest confirms are adjacent, converts an implicit, opaque loop-closure decision into an explicit, reviewable one.

One gap worth naming plainly: there is no single published source specifically addressing white-balance drift causing false color-dependent matches at room-to-room boundaries, so any claim along those lines here would be inference from general descriptor-illumination-sensitivity literature rather than a documented finding, and this book does not assert it as fact.
