# Running COLMAP Feature Extraction and Matching from a Script

`automatic_reconstructor` is the easy button. Point it at a workspace and an image folder, pick a `--quality` tier and a `--data_type`, and it runs feature extraction, matching, and mapping (plus dense reconstruction if you let it) as one opaque command, per the *Command-line Interface — COLMAP* docs. That is fine for a first pass, and the sibling volume "A First Pass: Feeding a Bundle Straight Through COLMAP" covers exactly that path. This book is about the next step: calling `feature_extractor` and the matcher binaries yourself, from a Python script, so you can inspect and tune each stage instead of hoping the automatic pipeline guessed right for a room walkthrough.

The motivation is control. Orbit Capture bundles are not internet photo collections. They are one operator's sequential walk through a room, sometimes hundreds of overlapping stills, sometimes an X4 Air's stitched equirectangular frames. The automatic reconstructor's presets are tuned for a generic case. Scripting the stages directly lets your capture tool decide the camera model, the feature budget, and the matcher strategy per job, and lets you log and recover from each stage independently rather than treating the whole reconstruction as one black box.

## The two stages COLMAP actually needs

Per the *Tutorial — COLMAP* docs, structure-from-motion in COLMAP is three stages: feature detection/extraction, feature matching plus geometric verification, then incremental reconstruction (registration and triangulation). This book scripts the first two. Mapping is its own concern, covered in "Running Incremental Mapping and Reading the Reconstruction Stats."

Both stages are plain CLI subprocess calls against a COLMAP database file. There is no COLMAP Python API required for this part (pycolmap exists and is documented in the *pycolmap Python bindings* reference, but the CLI binaries are sufficient and simpler for a scripted pipeline that just needs to run stages and check exit codes).

## A driver script

```python
from __future__ import annotations

import json
import subprocess
import sys
from dataclasses import dataclass, field
from pathlib import Path


@dataclass
class ExtractionConfig:
    camera_model: str = "SIMPLE_RADIAL"
    single_camera: bool = True
    single_camera_per_folder: bool = False
    max_num_features: int = 8192
    use_root_sift: bool = True


@dataclass
class MatchConfig:
    strategy: str = "sequential"
    use_gpu: bool = True
    overlap: int = 10


def run_colmap(args: list[str], log_path: Path) -> None:
    with log_path.open("a", encoding="utf-8") as log:
        log.write(f"$ colmap {' '.join(args)}\n")
        result = subprocess.run(
            ["colmap", *args],
            capture_output=True,
            text=True,
        )
        log.write(result.stdout)
        log.write(result.stderr)
    if result.returncode != 0:
        raise RuntimeError(
            f"colmap {args[0]} failed (exit {result.returncode}); see {log_path}"
        )


def extract_features(
    database_path: Path,
    image_path: Path,
    log_path: Path,
    cfg: ExtractionConfig = ExtractionConfig(),
) -> None:
    args = [
        "feature_extractor",
        "--database_path", str(database_path),
        "--image_path", str(image_path),
        "--ImageReader.camera_model", cfg.camera_model,
        "--ImageReader.single_camera", "1" if cfg.single_camera else "0",
        "--ImageReader.single_camera_per_folder",
        "1" if cfg.single_camera_per_folder else "0",
        "--SiftExtraction.max_num_features", str(cfg.max_num_features),
        "--SiftExtraction.normalization", "l1_root" if cfg.use_root_sift else "l2",
    ]
    run_colmap(args, log_path)


def match_features(
    database_path: Path,
    log_path: Path,
    cfg: MatchConfig = MatchConfig(),
) -> None:
    if cfg.strategy == "sequential":
        args = [
            "sequential_matcher",
            "--database_path", str(database_path),
            "--SequentialMatching.overlap", str(cfg.overlap),
            "--SiftMatching.use_gpu", "1" if cfg.use_gpu else "0",
        ]
    elif cfg.strategy == "exhaustive":
        args = [
            "exhaustive_matcher",
            "--database_path", str(database_path),
            "--SiftMatching.use_gpu", "1" if cfg.use_gpu else "0",
        ]
    else:
        raise ValueError(f"unhandled matcher strategy: {cfg.strategy}")
    run_colmap(args, log_path)


def run_stage_pipeline(workspace: Path, image_path: Path) -> Path:
    workspace.mkdir(parents=True, exist_ok=True)
    database_path = workspace / "database.db"
    log_path = workspace / "colmap_stages.log"

    extract_features(database_path, image_path, log_path)
    match_features(database_path, log_path, MatchConfig(strategy="sequential"))

    return database_path


if __name__ == "__main__":
    workspace_dir = Path(sys.argv[1])
    images_dir = Path(sys.argv[2])
    db = run_stage_pipeline(workspace_dir, images_dir)
    print(json.dumps({"database_path": str(db)}))
```

Everything here is a thin wrapper: build an argument list, shell out, capture stdout/stderr to a per-job log, raise on nonzero exit. That is deliberate. The value of scripting the stages isn't clever Python, it's that every flag becomes a config field your capture tool can set per job, and every stage becomes a checkpoint you can retry or skip without re-running the whole thing.

## Why each flag is set the way it is

`--ImageReader.camera_model` defaults to `SIMPLE_RADIAL` in COLMAP itself (per the *Command-line Interface* docs), and that default is reasonable for phone captures with a single lens and a fixed focal length. `--ImageReader.single_camera` and `--ImageReader.single_camera_per_folder` both default to `0` (off), meaning COLMAP will otherwise estimate a separate camera model per image unless told to share one. For a single-operator room walkthrough where every frame comes off the same physical lens at the same locked exposure and focal length, sharing one camera model (`single_camera=1`) gives the bundle adjuster fewer intrinsic parameters to solve simultaneously, which is exactly the kind of prior COLMAP's own FAQ page endorses: "with enough shared-intrinsic images, SfM-estimated intrinsics are often better than manual calibration-pattern parameters" (*Frequently Asked Questions — COLMAP*). If a job mixes an X4 Air's stitched equirectangular frames with phone stills in the same folder tree, `single_camera_per_folder` is the knob that keeps those two capture types from being forced into one shared model; put each capture type in its own subfolder and let this flag key off that.

`descriptor_normalization` (the `--SiftExtraction.normalization` flag in the script above) defaults to `l1_root`, i.e. RootSIFT, versus the `l2` standard SIFT normalization (per the *Command-line Interface* docs). Leave it at the default unless a specific dataset's matching quality tells you otherwise; RootSIFT is generally the safer default and there is nothing in the notes for this shelf that argues against it for room-scale captures.

`max_num_features` defaults to 8192 per image (again, *Command-line Interface*). That is a per-image budget, not a global one, and it is the first knob to reduce if extraction is too slow across a few hundred images, or raise if a texture-poor room is under-registering.

On the matching side, the choice between `sequential_matcher` and `exhaustive_matcher` is a direct fit-to-capture-pattern decision documented in *Feature Extraction and Matching — COLMAP*: `exhaustive_matcher` compares every possible image pair and is suitable for small datasets up to a few hundred images, while `sequential_matcher` matches images in capture order and is built for video-like or ordered walkthrough sequences. An Orbit Capture room walk is inherently sequential, shot in order as the operator moves, so `sequential_matcher` is the natural default here; the deeper tradeoffs between it and the other matcher families (`vocab_tree_matcher`, `spatial_matcher`, `transitive_matcher`) are worked through in "Choosing COLMAP Matcher Settings for Indoor Room Sequences." `SiftMatching.use_gpu` defaults to enabled (per *Feature Extraction and Matching*), which matters because matching is the stage most likely to become a bottleneck as pair count grows; leaving GPU matching on is the default posture unless the target machine genuinely lacks one.

One pairing constraint worth keeping in the script even though this book doesn't use ALIKED: extractor and matcher families must agree. SIFT extraction pairs with `SIFT_BRUTEFORCE` or `SIFT_LIGHTGLUE` matching, and `ALIKED_*` extraction pairs with `ALIKED_BRUTEFORCE` or `ALIKED_LIGHTGLUE` matching (*Feature Extraction and Matching — COLMAP*). If a future config field lets the capture tool switch to ALIKED for a texture-poor building, the matcher selection has to switch with it, not stay hardcoded to a SIFT-only variant.

## What the script buys you over automatic_reconstructor

Three things. First, per-stage logs: `run_colmap` writes each command and its full output to a job-specific log file, so a failed match on image 340 of 400 doesn't get buried inside a single monolithic reconstruction log. Second, per-job configuration: `ExtractionConfig` and `MatchConfig` are dataclasses your capture tool's job dispatcher can populate from a job manifest (JPG bundle vs. stitched equirectangular bundle, single lens vs. mixed), instead of picking one `--quality` tier for every job type. Third, a real checkpoint: the database file produced by these two stages is a complete, inspectable artifact. You can hand it to `colmap gui` for a visual sanity check, or straight to `mapper` for incremental reconstruction, without re-running extraction or matching if only the mapping parameters need iterating.

## What this book does not cover

It does not cover choosing between `sequential_matcher`'s neighbor-overlap window and the other matcher families for tricky repeated-room layouts (see "Choosing COLMAP Matcher Settings for Indoor Room Sequences"), and it does not cover what happens after matching, i.e. running `mapper` and reading its per-image registration log lines (see "Running Incremental Mapping and Reading the Reconstruction Stats"). The research notes for this shelf also flag that they could not independently verify precise ALIKED-vs-SIFT tradeoffs beyond the FAQ's general note that ALIKED can produce more repeatable matches in low-texture, low-overlap, or high-illumination-change scenes, so treat ALIKED as a documented option rather than a fully worked-out alternative pipeline in this book.
