# Building a Continuous Registration Health Dashboard Across Scans

A single scan's registration health tells you whether one building came out clean. It does not tell you whether you, the operator, are getting better at this. That second question only answers itself over time: fifty scans in, is your median registration rate climbing, is your reprojection error tightening, are the same failure modes still showing up in every stairwell? This book builds the dashboard that answers it, a small SQLite-backed aggregator that ingests every scan's health report and tracks trend lines across your whole capture history.

This volume assumes you already have a per-scan health score. If you don't, start with "Scripting a Registration Health Report from COLMAP Output," which is the sibling book that parses one scan's COLMAP output into the numbers this dashboard aggregates. This book is strictly about the layer above that: turning N single-scan reports into a longitudinal view.

## What a per-scan report actually gives you

COLMAP's incremental mapper logs each image as it registers, in a directly parseable format: lines like `Registering image #241 (230)` followed by `=> Image sees 3755 / 8696 points` ("COLMAP incremental mapper console log format," PR #2420 discussion). That per-image registered-points ratio is one building block. The other lives in the sparse output itself: `points3D.txt` records, for every triangulated point, a mean reprojection `ERROR` in pixels, which is only meaningful after a global bundle adjustment has run ("Output Format — COLMAP official docs"). A third signal is coarser but decisive: the fraction of your input images that ended up registered at all, since COLMAP will happily produce multiple disconnected sub-models instead of one when matching wasn't good enough ("Tutorial — COLMAP official docs").

A single-scan health score, as built in the sibling report book, typically folds these into one number: percent of images registered, mean reprojection error, and number of connected components (ideally one). This book does not re-derive that scoring logic. It treats the per-scan report as a fact table row and asks what you do with a few hundred of those rows.

One honest caveat up front: the notes backing this shelf do not define a canonical "registration health score" threshold scheme (a specific cutoff for "warning" vs. "healthy"). That's a product convention this pipeline chooses, not something COLMAP itself defines. What the research does support is that registered-image percentage varies widely in practice and that COLMAP's own console output and file formats give you the raw ingredients to compute your own thresholds and watch them move over time, which is exactly what this dashboard is for.

## Schema: one row per scan, not per image

Resist the urge to store every per-image ratio forever. The dashboard's job is trend detection across scans, so the unit of storage is one row per scan, with enough detail to drill back into a specific bad scan if a trend line dips.

```python
import sqlite3
from dataclasses import dataclass
from datetime import datetime, timezone


SCHEMA = """
CREATE TABLE IF NOT EXISTS scans (
    scan_id TEXT PRIMARY KEY,
    building_id TEXT NOT NULL,
    captured_at TEXT NOT NULL,
    ingested_at TEXT NOT NULL,
    total_images INTEGER NOT NULL,
    registered_images INTEGER NOT NULL,
    num_components INTEGER NOT NULL,
    mean_reproj_error REAL NOT NULL,
    mean_track_length REAL,
    health_score REAL NOT NULL,
    notes TEXT
);

CREATE INDEX IF NOT EXISTS idx_scans_captured_at ON scans (captured_at);
CREATE INDEX IF NOT EXISTS idx_scans_building ON scans (building_id);
"""


@dataclass(frozen=True)
class ScanHealth:
    scan_id: str
    building_id: str
    captured_at: str
    total_images: int
    registered_images: int
    num_components: int
    mean_reproj_error: float
    mean_track_length: float | None
    health_score: float
    notes: str = ""


def open_dashboard_db(path: str) -> sqlite3.Connection:
    conn = sqlite3.connect(path)
    conn.execute("PRAGMA journal_mode=WAL")
    conn.executescript(SCHEMA)
    return conn


def record_scan(conn: sqlite3.Connection, scan: ScanHealth) -> None:
    conn.execute(
        """
        INSERT INTO scans (
            scan_id, building_id, captured_at, ingested_at,
            total_images, registered_images, num_components,
            mean_reproj_error, mean_track_length, health_score, notes
        ) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
        ON CONFLICT(scan_id) DO UPDATE SET
            registered_images=excluded.registered_images,
            num_components=excluded.num_components,
            mean_reproj_error=excluded.mean_reproj_error,
            mean_track_length=excluded.mean_track_length,
            health_score=excluded.health_score,
            notes=excluded.notes
        """,
        (
            scan.scan_id,
            scan.building_id,
            scan.captured_at,
            datetime.now(timezone.utc).isoformat(),
            scan.total_images,
            scan.registered_images,
            scan.num_components,
            scan.mean_reproj_error,
            scan.mean_track_length,
            scan.health_score,
            scan.notes,
        ),
    )
    conn.commit()
```

SQLite is the whole database layer here, and that's deliberate. A solo operator producing a few scans a week will not outgrow a single file for years; reaching for Postgres before you have a reason is exactly the kind of complexity this pipeline should avoid. `ON CONFLICT ... DO UPDATE` gives you idempotent re-ingestion, which matters because you will re-run a health report after a reprocess and want the dashboard to reflect the latest numbers, not accumulate duplicate history for the same scan.

## Computing the health score once, at ingestion time

The dashboard should not recompute scoring logic that belongs to the report generator. It accepts a health score as an input and stores it, but it's worth being explicit about what a defensible formula looks like, since you will be asked to justify it later. A reasonable, source-grounded composite:

```python
def compute_health_score(
    total_images: int,
    registered_images: int,
    num_components: int,
    mean_reproj_error: float,
) -> float:
    if total_images == 0:
        return 0.0

    registration_rate = registered_images / total_images
    fragmentation_penalty = 1.0 / num_components if num_components > 0 else 0.0

    error_score = max(0.0, 1.0 - mean_reproj_error / 2.0)

    return round(
        0.5 * registration_rate + 0.2 * fragmentation_penalty + 0.3 * error_score,
        4,
    )
```

Registration rate is grounded directly in COLMAP's behavior of leaving images unregistered or splitting the reconstruction into multiple models when matching fails ("Tutorial — COLMAP official docs"). The fragmentation penalty encodes the same fact: one connected component is the goal, and `num_components > 1` is a real, observable failure mode, not a hypothetical. The error term uses the `points3D.txt` mean reprojection error, scaled against a rough 2-pixel budget as a starting point; that scale factor is a tuning knob you should treat as provisional, not as something the notes hand you a citation for. Mark it as such in your own code:

```python
# ponytail: 2.0px error-scale divisor is a starting heuristic, not a
# sourced constant. Tune against your own scan history once you have
# 20+ scans and can see where mean_reproj_error actually clusters.
```

## Aggregating trends across the whole history

The dashboard's actual value is in rolling aggregates: is your last 10 scans' median health score higher than your first 10? This is a query problem, not a machine-learning problem, and SQLite's window functions handle it directly.

```python
def rolling_health_trend(conn: sqlite3.Connection, window: int = 10) -> list[dict]:
    rows = conn.execute(
        """
        SELECT
            scan_id,
            building_id,
            captured_at,
            health_score,
            AVG(health_score) OVER (
                ORDER BY captured_at
                ROWS BETWEEN ? PRECEDING AND CURRENT ROW
            ) AS rolling_avg,
            AVG(mean_reproj_error) OVER (
                ORDER BY captured_at
                ROWS BETWEEN ? PRECEDING AND CURRENT ROW
            ) AS rolling_reproj_error
        FROM scans
        ORDER BY captured_at
        """,
        (window - 1, window - 1),
    ).fetchall()

    columns = [
        "scan_id", "building_id", "captured_at",
        "health_score", "rolling_avg", "rolling_reproj_error",
    ]
    return [dict(zip(columns, row)) for row in rows]


def worst_recent_scans(conn: sqlite3.Connection, limit: int = 5) -> list[dict]:
    rows = conn.execute(
        """
        SELECT scan_id, building_id, captured_at, health_score, notes
        FROM scans
        ORDER BY captured_at DESC
        LIMIT 50
        """
    ).fetchall()
    columns = ["scan_id", "building_id", "captured_at", "health_score", "notes"]
    ranked = sorted((dict(zip(columns, row)) for row in rows), key=lambda r: r["health_score"])
    return ranked[:limit]
```

`rolling_health_trend` is the whole point of this book: one query, no external analytics library, giving you a moving average you can plot or just print as a table. `worst_recent_scans` answers a different, equally important question: not "is the trend up" but "which recent buildings dragged it down," which is where you go looking for a specific bad stairwell or a specific day you rushed the capture.

## Rendering a plain dashboard

You do not need a web framework for this. A solo operator checking their own trend line is well served by a terminal report generated on demand.

```python
def print_dashboard(conn: sqlite3.Connection) -> None:
    total = conn.execute("SELECT COUNT(*) FROM scans").fetchone()[0]
    if total == 0:
        print("No scans recorded yet.")
        return

    trend = rolling_health_trend(conn, window=10)
    latest = trend[-1]
    earliest_avg = trend[min(9, len(trend) - 1)]["rolling_avg"]

    print(f"Scans recorded: {total}")
    print(f"Latest rolling health (last 10): {latest['rolling_avg']:.3f}")
    print(f"Earliest rolling health (first 10): {earliest_avg:.3f}")
    print(f"Latest rolling mean reprojection error: {latest['rolling_reproj_error']:.3f}px")

    print("\nWorst scans in the last 50:")
    for row in worst_recent_scans(conn):
        print(f"  {row['captured_at']}  {row['building_id']:<20}  score={row['health_score']:.3f}")
```

This is deliberately not a web dashboard. A Flask app or a static-site generator is a real option once you're sharing this across a team, but for one operator watching their own numbers, a script you run after each scan is the whole product. Add the web layer when a second person needs to see it without running Python locally, not before.

## Feeding the dashboard from the field

The dashboard is only as good as its ingestion discipline. The natural place to call `record_scan` is at the end of whatever process already reads the per-scan health report, likely a JSON file the sibling report book writes next to each scan's COLMAP output.

```python
import json
from pathlib import Path


def ingest_health_report(conn: sqlite3.Connection, report_path: Path) -> None:
    payload = json.loads(report_path.read_text())

    scan = ScanHealth(
        scan_id=payload["scan_id"],
        building_id=payload["building_id"],
        captured_at=payload["captured_at"],
        total_images=payload["total_images"],
        registered_images=payload["registered_images"],
        num_components=payload["num_components"],
        mean_reproj_error=payload["mean_reproj_error"],
        mean_track_length=payload.get("mean_track_length"),
        health_score=payload["health_score"],
        notes=payload.get("notes", ""),
    )
    record_scan(conn, scan)
```

This is the seam where "Registration Diagnostics as a Feedback Loop to the Field Operator" plugs in on the other side: that book is about surfacing a single scan's diagnostics back to you immediately after capture, while this dashboard is about what happens once dozens of those diagnostics accumulate. They read the same JSON report file for different audiences and different timescales, one instant, one longitudinal.

## What this dashboard will not save you from

A rising trend line can hide a lot. If you started shooting exclusively bright, high-texture office buildings and moved on to dim, feature-poor warehouses, your registration rate will drop for reasons that have nothing to do with your technique getting worse. The notes are explicit that scenes with little texture and drastic illumination changes degrade matching regardless of operator skill (COLMAP FAQ). Segment your trend by rough scene category if you capture a mix of building types, or you'll chase a phantom regression.

Similarly, a health score of zero components-fragmentation but a climbing reprojection error is not the same failure as a healthy error but a dropping registration rate; the dashboard should let you inspect each metric's own trend line, not just the composite, because the composite score can stay flat while its ingredients move in opposite directions and cancel out. The rolling-average query above already returns both `rolling_avg` and `rolling_reproj_error` separately for exactly this reason: read them side by side, not just the composite.

Finally, none of this replaces catching a bad run before it's baked into history. Ingestion failures, a report file that never got written because the pipeline crashed mid-run, should fail loud rather than silently leave a gap in your trend line. That's the concern of "Hardening the Pipeline: Retrying, Logging, and Failing Loud," which covers making sure every scan either produces a health report or produces a clearly logged failure, so the dashboard's history is complete rather than quietly missing your worst days.

## A minimal self-check

```python
def _demo() -> None:
    import tempfile
    import os

    with tempfile.TemporaryDirectory() as tmp:
        db_path = os.path.join(tmp, "dashboard.db")
        conn = open_dashboard_db(db_path)

        for i in range(12):
            score = compute_health_score(
                total_images=100,
                registered_images=70 + i * 2,
                num_components=1 if i > 2 else 2,
                mean_reproj_error=1.2 - i * 0.05,
            )
            record_scan(
                conn,
                ScanHealth(
                    scan_id=f"scan-{i:03d}",
                    building_id="warehouse-a" if i % 2 == 0 else "office-b",
                    captured_at=f"2026-0{(i % 6) + 1}-{10 + i:02d}T00:00:00",
                    total_images=100,
                    registered_images=70 + i * 2,
                    num_components=1 if i > 2 else 2,
                    mean_reproj_error=1.2 - i * 0.05,
                    mean_track_length=None,
                    health_score=score,
                ),
            )

        trend = rolling_health_trend(conn, window=5)
        assert len(trend) == 12
        assert trend[-1]["rolling_avg"] >= trend[0]["rolling_avg"], (
            "expected improving trend in synthetic data"
        )

        worst = worst_recent_scans(conn, limit=3)
        assert len(worst) == 3
        assert worst[0]["health_score"] <= worst[-1]["health_score"]

        conn.close()
        print("self-check passed")


if __name__ == "__main__":
    _demo()
```

The synthetic data in `_demo` walks registration rate up and reprojection error down scan by scan, so an assertion that the rolling average improves is a real check on the window-function query, not a tautology. Run it whenever you touch the schema or the aggregation query; a broken `ORDER BY captured_at` or an off-by-one in the window frame is exactly the kind of bug that looks fine on one scan and silently corrupts every trend line after it.
