# Parameterizing COLMAP Runs Per Rig Type from manifest.json

Every Orbit Capture bundle carries a `manifest.json` with a `rig` field: something like `"phone"` or `"insta360_x4_air"`. That one string should decide a handful of COLMAP invocation details before a single `colmap` command runs: which `--ImageReader.camera_model` to force, whether images share intrinsics, and which matcher fits the way the operator actually walked the room. Baking that decision into a `RigProfile` lookup means the pipeline never has to guess, and the operator never has to remember which flags go with which rig.

This book assumes the manifest has already been ingested into a COLMAP project directory, as covered in "Building the Bundle Ingestion Module: manifest.json to a COLMAP Project", and that per-image intrinsics have already been pulled out, as covered in "Extracting Camera Intrinsics and Rig Metadata from the Bundle". What's left here is turning `rig` into concrete `feature_extractor` and matcher arguments.

## What the rig field actually needs to control

Per the COLMAP CLI docs, `feature_extractor` takes `--ImageReader.camera_model` (default `SIMPLE_RADIAL`), plus `--ImageReader.single_camera` and `--ImageReader.single_camera_per_folder`, both defaulting to `0`. Those three flags are the entire surface a rig type needs to touch on the extraction side. The matching side is a choice among documented matcher commands: `exhaustive_matcher`, `vocab_tree_matcher`, `sequential_matcher`, `spatial_matcher`, and `transitive_matcher`.

Two capture rigs, two different answers:

- **Phone rig** (locked-exposure overlapping stills, walked room by room): each photo comes from the same physical lens with fixed intrinsics for the whole session, so `single_camera=1` is correct, and the walk order is genuinely sequential, so `sequential_matcher` fits the documented use case of "video-like or ordered walkthrough sequences" per "Feature Extraction and Matching."
- **Insta360 X4 Air rig** (dual-fisheye stitched to 2:1 equirectangular JPGs, per the X4 Air announcement covering its two 1/1.8-inch fisheye lenses): the stitched output is a single flat frame per capture position, still one consistent camera across the session, so `single_camera=1` still holds. The matcher choice is the same `sequential_matcher` if the operator walked a route, since the stitch happens before COLMAP ever sees the frame.

There's a real gap here worth stating plainly: none of the research notes for this shelf identify a COLMAP camera model name for equirectangular projections, and the Splatfacto documentation explicitly says "Gaussian rasterization assumes a perspective camera" and that fisheye/equirectangular models are not currently supported in the rasterization pipeline. So this book cannot tell you to pick some `EQUIRECTANGULAR` COLMAP camera model, because the notes don't establish COLMAP has one that gsplat can consume downstream. The practical implication, which the code below encodes as a loud warning rather than a silent default, is that an equirectangular rig needs a perspective-camera workaround (cropping/re-projecting faces of the sphere) upstream of COLMAP before `feature_extractor` runs at all, and that workaround is out of scope for this book.

## The RigProfile lookup

```python
from __future__ import annotations

import json
import subprocess
from dataclasses import dataclass, field
from pathlib import Path


@dataclass(frozen=True)
class RigProfile:
    rig_key: str
    camera_model: str
    single_camera: bool
    single_camera_per_folder: bool
    matcher: str
    matcher_extra_args: list[str] = field(default_factory=list)
    warning: str | None = None


RIG_PROFILES: dict[str, RigProfile] = {
    "phone": RigProfile(
        rig_key="phone",
        camera_model="SIMPLE_RADIAL",
        single_camera=True,
        single_camera_per_folder=False,
        matcher="sequential_matcher",
        matcher_extra_args=["--SequentialMatching.overlap", "10"],
    ),
    "insta360_x4_air": RigProfile(
        rig_key="insta360_x4_air",
        camera_model="SIMPLE_RADIAL",
        single_camera=True,
        single_camera_per_folder=False,
        matcher="sequential_matcher",
        matcher_extra_args=["--SequentialMatching.overlap", "10"],
        warning=(
            "insta360_x4_air frames are stitched dual-fisheye equirectangular JPGs. "
            "None of this library's sources document a COLMAP camera model for "
            "equirectangular projections, and Splatfacto's docs say Gaussian "
            "rasterization assumes a perspective camera. SIMPLE_RADIAL is applied "
            "here as a placeholder so the pipeline runs, not as a validated fit -- "
            "re-projection to perspective faces before feature_extractor is the "
            "documented-elsewhere fix this book does not implement."
        ),
    ),
}


def load_rig(manifest_path: Path) -> str:
    manifest = json.loads(manifest_path.read_text())
    rig = manifest.get("rig")
    if not rig:
        raise ValueError(f"manifest.json at {manifest_path} has no 'rig' field")
    return rig


def resolve_profile(rig: str) -> RigProfile:
    try:
        return RIG_PROFILES[rig]
    except KeyError:
        known = ", ".join(sorted(RIG_PROFILES))
        raise ValueError(f"unknown rig '{rig}', expected one of: {known}") from None
```

The dataclass is deliberately flat. Every field maps to one CLI flag or one matcher choice, nothing more, because adding indirection here (a class hierarchy per rig, a plugin registry) would just be ceremony around a dictionary lookup. When a third rig type shows up, it's a new entry in `RIG_PROFILES`, not a new code path.

`resolve_profile` raises rather than silently falling back to a default rig. A manifest with a typo'd or unrecognized `rig` value is a data problem worth surfacing immediately, before an hour of feature extraction runs against the wrong camera model.

## Turning a profile into the actual commands

```python
def build_feature_extractor_args(
    profile: RigProfile, database_path: Path, image_path: Path
) -> list[str]:
    args = [
        "colmap",
        "feature_extractor",
        "--database_path",
        str(database_path),
        "--image_path",
        str(image_path),
        "--ImageReader.camera_model",
        profile.camera_model,
        "--ImageReader.single_camera",
        "1" if profile.single_camera else "0",
        "--ImageReader.single_camera_per_folder",
        "1" if profile.single_camera_per_folder else "0",
    ]
    return args


def build_matcher_args(profile: RigProfile, database_path: Path) -> list[str]:
    args = ["colmap", profile.matcher, "--database_path", str(database_path)]
    args.extend(profile.matcher_extra_args)
    return args


def run_for_rig(manifest_path: Path, database_path: Path, image_path: Path) -> None:
    rig = load_rig(manifest_path)
    profile = resolve_profile(rig)
    if profile.warning:
        print(f"[rig-profile warning] {profile.warning}")

    extractor_cmd = build_feature_extractor_args(profile, database_path, image_path)
    matcher_cmd = build_matcher_args(profile, database_path)

    subprocess.run(extractor_cmd, check=True)
    subprocess.run(matcher_cmd, check=True)
```

`run_for_rig` is the entire integration point: read the manifest, look up the profile, print the warning if there is one, run the two commands. Nothing here retries, nothing here parses COLMAP's stdout for success -- that belongs in whatever orchestration layer calls this function, and duplicating it here would just be a second place for that logic to drift out of sync.

## Why `single_camera` matters more than it looks

The `single_camera_per_folder` flag exists in the COLMAP docs for a case this pipeline doesn't hit: multiple physical cameras sharing one image tree, split by subfolder. Both Orbit Capture rig types produce one logical camera stream per session (a phone's rear lens with locked exposure, or a stitched equirectangular frame from the X4 Air), so `single_camera=1` and `single_camera_per_folder=0` is correct for both today. If a future rig captures from two lenses into two folders without pre-stitching (raw dual-fisheye passed straight to COLMAP, skipping the stitch step entirely), that's the flag that would flip, and it would need its own `RigProfile` entry rather than a conditional bolted onto these two.

## Choosing sequential over exhaustive

Both current rig types default to `sequential_matcher` because both describe a single operator walking a room-by-room route -- exactly the "video-like or ordered walkthrough" case the COLMAP feature-matching docs call out for that matcher, as opposed to `exhaustive_matcher`, which the same docs scope to small datasets of up to a few hundred images. A hundred-plus-image room walkthrough sits right at that boundary, which is why "Choosing COLMAP Matcher Settings for Indoor Room Sequences" is worth reading alongside this book: it goes deeper into overlap windows and when a sequence stops behaving sequentially (dense-featured rooms revisited out of order, for instance) in a way that would just be a distraction bolted onto a rig-selection lookup.

## Self-check

```python
def _demo() -> None:
    import tempfile

    with tempfile.TemporaryDirectory() as tmp:
        manifest_path = Path(tmp) / "manifest.json"

        manifest_path.write_text(json.dumps({"rig": "phone"}))
        profile = resolve_profile(load_rig(manifest_path))
        assert profile.camera_model == "SIMPLE_RADIAL"
        assert profile.single_camera is True
        assert profile.matcher == "sequential_matcher"
        assert profile.warning is None

        manifest_path.write_text(json.dumps({"rig": "insta360_x4_air"}))
        profile = resolve_profile(load_rig(manifest_path))
        assert profile.warning is not None

        manifest_path.write_text(json.dumps({"rig": "drone_swarm_v9"}))
        try:
            resolve_profile(load_rig(manifest_path))
            raise AssertionError("expected unknown rig to raise")
        except ValueError:
            pass

        args = build_feature_extractor_args(
            RIG_PROFILES["phone"], Path("db.db"), Path("images/")
        )
        assert "--ImageReader.single_camera" in args
        assert args[args.index("--ImageReader.single_camera") + 1] == "1"

    print("all rig-profile checks passed")


if __name__ == "__main__":
    _demo()
```

That's the whole surface: a dictionary keyed by `rig`, a loader that fails loudly on an unrecognized value, and two functions that turn a profile into the argument lists `subprocess.run` needs. Skipped a plugin/registry abstraction for rig types since two entries don't need one -- add it when a fourth or fifth rig makes the dictionary awkward to read.
