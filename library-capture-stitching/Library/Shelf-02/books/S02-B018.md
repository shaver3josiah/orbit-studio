# Stitching Dual-Fisheye to Equirectangular with Insta360 Tools

An Insta360 X4 Air never gives you a panorama. It gives you two fisheye circles, one per lens, each covering roughly 170 degrees per the X4 Air's single-lens spec (Insta360 X4 Air product announcement). Turning that pair into the flat 2:1 equirectangular JPG your pipeline expects is a distinct processing step, and it has to happen before the file ever reaches COLMAP. This book scripts that step end to end: locating the raw dual-fisheye asset, invoking Insta360's stitching tooling against it, and landing a validated equirectangular JPG in the folder your ingest script watches. The companion volume "Dual-Fisheye Capture and Why the Insta360 X4 Air Needs a Stitch Step" covers why the camera hands you two circles in the first place; this one is about scripting the fix.

## What the SDK actually gives you

Insta360 publishes developer resources split into two SDKs (Insta360 Developer Resources SDK Guide). The Camera SDK handles connection, live status, preview streams, parameter configuration, shooting control, and file listing/deletion on the device itself. The Media SDK is the one that matters here: it covers preview/display, stitching, and image/video export, and it is the documented path for turning dual-fisheye output into a usable image or video. The guide is explicit that in-camera video stitching is not available for the raw dual-fisheye stream, so stitching for video has to route through the Media SDK rather than happening on-device.

Worth being honest about upfront: the public developer pages describe these as capability categories, not documented method signatures. Exact function names, parameter lists, and batch-export flags for the Media SDK are not published on the open developer resource pages found for this book; deeper access likely requires SDK registration. What follows treats Insta360's desktop stitching application (Insta360 Studio) and its command-line/batch export mode as the concrete tool you script against, since that is the interface an Orbit Capture operator without SDK registration will actually have on hand. If you do have Media SDK access, the same orchestration shape applies, you are just swapping a subprocess call for a native binding.

## The stitch step as a subprocess

Treat the stitcher as an external tool with a contract: raw `.insv` in, equirectangular `.jpg` out. Python's job is to find inputs, invoke the tool correctly, and verify what came back before letting it into the pipeline.

```python
import json
import shutil
import subprocess
from dataclasses import dataclass
from pathlib import Path


@dataclass
class StitchJob:
    source: Path
    dest: Path
    width: int = 5760
    height: int = 2880

    def output_ratio_ok(self) -> bool:
        return self.width == self.height * 2


class StitchError(RuntimeError):
    pass


def find_raw_captures(scan_dir: Path) -> list[Path]:
    return sorted(scan_dir.glob("*.insv"))


def build_stitch_command(exe: Path, job: StitchJob) -> list[str]:
    if not job.output_ratio_ok():
        raise StitchError(
            f"requested {job.width}x{job.height} is not 2:1, refusing to build a bad job"
        )
    return [
        str(exe),
        "--input", str(job.source),
        "--output", str(job.dest),
        "--type", "equirect",
        "--width", str(job.width),
        "--height", str(job.height),
        "--stitch-mode", "optical_flow",
    ]


def run_stitch(exe: Path, job: StitchJob, timeout_s: int = 600) -> None:
    cmd = build_stitch_command(exe, job)
    result = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout_s)
    if result.returncode != 0:
        raise StitchError(
            f"stitch failed for {job.source.name}: rc={result.returncode} "
            f"stderr={result.stderr.strip()[:500]}"
        )
    if not job.dest.exists() or job.dest.stat().st_size == 0:
        raise StitchError(f"stitch reported success but {job.dest} is missing or empty")
```

The CLI flags above (`--type equirect`, `--stitch-mode optical_flow`) are illustrative of the shape Insta360 Studio's batch export exposes, not a verified flag-for-flag transcription of a published spec; the gap noted above applies here directly. Confirm the exact flags against your installed Insta360 Studio version's `--help` output before relying on them, the same discipline the notes describe for COLMAP's own community parameter cheatsheet, which flags itself as useful-but-unverified against the installed binary (colmap-parameters community reference). Script the discovery, don't hardcode a flag list you never checked.

`--stitch-mode optical_flow` deliberately names the underlying approach: Insta360's stitcher compares the overlapping regions of each lens's image, and for video, adjacent frames from the same lens, to route the seam around actual scene content instead of along a fixed geometric boundary (Insta360 optical-flow stitching explainer). That explainer describes tiered options, a basic Optical Flow mode, a faster "New Optical Flow" mode, and a higher-quality "AI Flow" mode built on Insta360's Disflow technology, trading stitch time against seam quality. For static room-by-room capture where a few extra seconds per shot is free, the highest-quality tier is the right default; for a time-boxed walkthrough, the faster mode may be the pragmatic choice. That source's exact wording is worth re-verifying since it came through a cached summary after a direct fetch returned HTTP 403, but the tiered-tradeoff shape is the operative fact for scripting purposes: expose the tier as a parameter, don't bury it.

## Why the seam even needs intelligence

A naive stitch would just blend fisheye edges along a fixed geometric line. Insta360's optical-flow approach exists because two lenses looking in different directions rarely see overlapping content as flat, aligned pixels: parallax and slight lens misalignment mean a straight seam cuts through real scene geometry, doorframes, furniture edges, whatever happens to sit at the boundary. This is the same underlying tension the sibling volume on validation calls out from the other side: stitching only works cleanly when the two lens views are treated as one head. If you have already spent time internalizing why panorama stitching relies on a pure-rotation, single-viewpoint assumption to make one homography work at all, the same logic explains why the seam has to bend around content rather than sit on a straight line: real scenes are not flat, so a smart seam earns its cost.

## Wiring it into the batch loop

A single-file wrapper is a demo. The real script walks a folder of raw captures from one building pass, stitches each, and writes a manifest so downstream steps know what succeeded.

```python
def stitch_batch(exe: Path, raw_dir: Path, out_dir: Path) -> dict:
    out_dir.mkdir(parents=True, exist_ok=True)
    manifest = {"succeeded": [], "failed": []}

    for raw in find_raw_captures(raw_dir):
        dest = out_dir / f"{raw.stem}.jpg"
        job = StitchJob(source=raw, dest=dest)
        try:
            run_stitch(exe, job)
            manifest["succeeded"].append(str(dest))
        except StitchError as exc:
            manifest["failed"].append({"source": str(raw), "error": str(exc)})

    manifest_path = out_dir / "stitch_manifest.json"
    manifest_path.write_text(json.dumps(manifest, indent=2))
    return manifest


def stitcher_available(exe_name: str = "insta360studio") -> Path | None:
    found = shutil.which(exe_name)
    return Path(found) if found else None
```

`stitch_batch` deliberately does not raise on a single failed file. One bad `.insv` (a dropped frame, a corrupted transfer) should not kill the run for every other room captured that day; it goes into `manifest["failed"]` and the operator or the next pipeline stage decides what to do with it. `stitcher_available` is a cheap guard clause: fail fast with a clear message if Insta360 Studio isn't installed or isn't on PATH, rather than letting every job in the batch fail with the same confusing subprocess error.

## What "done" means before upload

A stitched JPG existing on disk is not the same as a stitched JPG that is safe to feed into the SfM pipeline. Two properties matter immediately: the file must actually be 2:1 (equirectangular projection only means anything at that ratio, per the PanoTools wiki definition, and a panorama even one pixel off true 2:1 has been observed to confuse downstream viewers), and it needs to be wide enough that COLMAP's feature extractor has real pixels to work with rather than a soft, upscaled image. This book only scripts the stitch call itself; the actual pixel-dimension and ratio checks, plus what to do when a file fails them, belong to "Validating an Equirectangular Export: 2:1 Ratio and Width > 3840px." Treat that check as a mandatory gate immediately after `stitch_batch`, not an optional nicety, since a bad ratio here silently degrades every downstream reconstruction that touches the file.

This script is also not meant to run by hand for every room in a building. Once it is reliable, it belongs behind a watcher that fires the moment a new `.insv` lands from the camera, which is exactly the scope of "Automating the Dual-Fisheye-to-Equirect Stitch Step in the Pipeline." The manifest-writing pattern above, a JSON record of what succeeded and what didn't, is what that automation layer will poll instead of re-deriving success/failure from raw stitcher output each time.

## A minimal self-check

```python
def demo() -> None:
    job = StitchJob(source=Path("room.insv"), dest=Path("room.jpg"), width=5760, height=2880)
    assert job.output_ratio_ok()

    bad_job = StitchJob(source=Path("room.insv"), dest=Path("room.jpg"), width=4000, height=3000)
    assert not bad_job.output_ratio_ok()
    try:
        build_stitch_command(Path("insta360studio"), bad_job)
        raise AssertionError("expected StitchError for non-2:1 output")
    except StitchError:
        pass

    cmd = build_stitch_command(Path("insta360studio"), job)
    assert "--width" in cmd and "5760" in cmd
    print("stitch scripting self-check passed")


if __name__ == "__main__":
    demo()
```

Run `demo()` after any change to `build_stitch_command` or `StitchJob`. It won't catch a wrong CLI flag against the real binary, only a live run against Insta360 Studio does that, but it catches the cheaper mistake: a ratio guard that silently stops guarding, or a command builder that drops a required argument.
