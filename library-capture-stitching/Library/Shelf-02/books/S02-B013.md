# Diagnosing a Failed COLMAP Run from Its Sparse Output

A COLMAP run finishes. No crash, no red error text, just a prompt returning control to you. You point your gsplat pipeline at the sparse model and the result is garbage: half the room is missing, or the walls warp like a funhouse mirror, or the whole scene collapses into a smear. What happened? COLMAP will not tell you in plain language. But it already wrote down everything you need to know, and reading it is a skill, not a mystery.

The sparse output is COLMAP's ledger of what it believed. Three files carry the story: `cameras`, `images`, and `points3D` (binary by default, but exportable as `.txt` via `model_converter`, as the official Output Format documentation describes). `images` records, for every photo, its estimated position and orientation plus a list of 2D keypoints and which 3D point each one triangulated to, with -1 meaning that keypoint never got a home. `points3D` records every triangulated 3D point, its color, its track (which images observed it), and its reprojection error. Between those two files sits the entire diagnosis of your run: how many images made it in, how well-supported each 3D point is, and how far off the model's own predictions were from what the cameras actually saw.

Start with the crudest signal: how many images registered. COLMAP's incremental mapper does not require every photo to earn a place in the model. It seeds a reconstruction from an initial image pair, then progressively registers more images and triangulates new points as it goes, per the COLMAP tutorial. Any image whose features could not be matched confidently enough into the growing model is simply left out. So the first question of a failed run is arithmetic: how many of the images you fed in show up in `images.bin` versus how many you shot. If you walked eight rooms and shot four hundred images but only two hundred and ten registered, something broke, and it likely broke in a specific room, not everywhere at once. That is the subject of a sibling volume, Why Some Rooms Register and Others Don't, which goes deeper into the causes; this book is about reading the symptom in the output file, not the room-level story.

A subtler failure hides even when registration counts look fine: a shattered scene. COLMAP does not promise one connected model. The tutorial is explicit that if not all images end up registered together, COLMAP reconstructs multiple separate models rather than forcing a single, possibly wrong, connection. If your capture tool only looks at total registered-image count, it can report "180 of 200 images registered" as a success while the truth is two disconnected fragments of ninety images each, unaligned and unusable together. The fix here is not exotic: `model_merger` can stitch two sub-models that share common registered images, computing a similarity transform from their shared poses, though the GitHub discussion on `model_merger` usage warns it relies only on those two models' poses rather than full re-triangulation, so a global bundle-adjuster pass afterward is recommended to clean up the alignment. But merging is a repair; detecting the fracture in the first place means checking whether COLMAP wrote out more than one model directory, not just trusting a single registered-count number.

Once you know images registered into one connected model, the next question is how well each 3D point is actually supported. This is track length: the number of images whose keypoints triangulated to the same 3D point, listed explicitly in `points3D`'s `TRACK[]` field as `(IMAGE_ID, POINT2D_IDX)` pairs. A point with a track length of two was seen by only two cameras. Geometrically that is the bare minimum for triangulation, and it is fragile: two nearly-parallel viewing rays intersecting at a shallow angle produce a 3D estimate that is extremely sensitive to small pixel-level noise in either observation. A point with a track length of eight or ten, by contrast, has been independently corroborated by that many viewpoints, and its position is pinned down much more tightly. COLMAP's own console output reports summary statistics on this directly: number of points and mean track length, according to the Output Format documentation. A model whose mean track length has collapsed toward two or three, even with a healthy registered-image count, is a model built on thin, unreliable triangulation, and it will show up downstream as noisy or floating geometry once you seed a Gaussian-splat training run from it, since Splatfacto and similar 3DGS implementations initialize their Gaussians directly from these SfM points.

The last and most quantitative signal is reprojection error, stored per-point in the `ERROR` field of `points3D`. This number is the mean distance, in pixels, between where the 3D point's estimated position projects into each observing camera and where the corresponding keypoint actually was detected. Crucially, the documentation notes this value is only updated after a global bundle adjustment runs, so a mid-pipeline model or one that skipped final refinement will show stale or absent error values, not a signal you can trust yet. Bundle adjustment itself, as described in the literature summarized on Wikipedia's treatment of the topic (citing Hartley and Zisserman's Multiple View Geometry), is the joint refinement step that adjusts every camera pose and every 3D point together to minimize total reprojection error across the whole scene, the final polish pass every serious SfM pipeline runs before calling a reconstruction done. A model where most points carry sub-pixel to low single-digit error is healthy. A model peppered with points carrying error in the tens of pixels has structure that does not agree with what the cameras actually recorded, geometry built on a compromise the optimizer was forced into rather than a real consensus. Reading that distribution of errors as a health signal in its own right, not just a pass/fail cutoff, is exactly the ground covered by another sibling volume, Interpreting Bundle Adjustment Residuals as a Health Signal, worth reading alongside this one.

Put together, these three numbers, registered image count, track length distribution, and reprojection error, form a triage order. Registered count tells you if the room made it in at all. Fragmentation, checked via multiple model directories, tells you whether "made it in" secretly means "made it in twice, disconnected." Track length tells you whether the points that did make it in are well-triangulated or barely holding on. Reprojection error tells you whether the final geometry actually agrees with the photographs. A failed splat almost always traces back to a weak link in that chain, and the sparse output already has the receipts. Manually opening `points3D.txt` and eyeballing three columns works for a one-off diagnosis, but for a production capture tool you want this triage automated and reported per capture, not read by hand after the fact, which is precisely what Scripting a Registration Health Report from COLMAP Output walks through.

For the solo operator standing in a building with a phone or an X4 Air, none of this requires becoming a computer-vision researcher. It requires knowing that COLMAP already tells you exactly where a capture went wrong, in three plain numbers sitting in a file you can open. Learn to read them once, and every future failed run stops being a mystery and starts being a location on a map, one you can walk back into and reshoot.
