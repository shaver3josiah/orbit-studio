# Monitoring gsplat Training Loss and Point Cloud Growth

A gsplat training run gives almost no feedback by default. You launch it, a progress bar ticks forward for twenty or forty minutes, and you find out whether the room looks right only when it is done. For a solo operator who just spent an hour walking a building with a phone or an Insta360 X4 Air, that is an expensive way to discover a run has diverged or stalled. The fix is not complicated: log loss and splat count to a CSV every N steps, and plot both curves so a bad run is visible in minutes instead of at the end.

This book assumes you already have a training run wired up along the lines described in "Setting Up a gsplat Training Run from a COLMAP Sparse Model" and understand what the optimizer is actually doing, covered in "From Point Cloud to Splat: What Training Actually Optimizes." Here we only add instrumentation around that loop, not change what it optimizes.

## What gsplat already tracks internally

gsplat's densification is handled by a `Strategy` object, not by your training loop. The two shipped strategies are `DefaultStrategy` (the original Kerbl et al. adaptive density control that splits or clones Gaussians whose accumulated positional gradient exceeds a threshold) and `MCMCStrategy` (which reframes densification as stochastic-gradient Langevin dynamics with injected noise) (gsplat: An Open-Source Library for Gaussian Splatting). Both strategies expose the parameters that govern when and how aggressively the splat count changes, and reading them off the strategy object is the cheapest way to know what your run is configured to do before you even start plotting.

For `DefaultStrategy`, the documented defaults are `prune_opa=0.005` (opacity floor below which Gaussians are pruned), `grow_grad2d=0.0002` (image-plane gradient threshold above which Gaussians split or duplicate), `grow_scale3d=0.01` and `grow_scale2d=0.05` (size thresholds that decide duplicate vs. split), `prune_scale3d=0.1` and `prune_scale2d=0.15` (oversized-Gaussian pruning), `refine_start_iter=500`, `refine_stop_iter=15000`, `refine_every=100`, and `reset_every=3000` for periodic opacity reset (gsplat documentation, Strategy API). `MCMCStrategy` instead defaults to `min_opacity=0.005`, `refine_start_iter=500`, `refine_stop_iter=25000`, `refine_every=100`, and a hard `cap_max=1,000,000` on total Gaussian count. Those last two numbers matter for monitoring: under MCMC the splat count should approach `cap_max` and plateau, while under the default strategy it grows and shrinks in response to gradients with no fixed ceiling. Knowing which regime you are in changes what a "healthy" count curve looks like.

## Instrumenting the training loop

The training loop itself (from the companion volume on setting up a run) already computes a loss per step and calls `strategy.step_post_backward(...)` after the backward pass to let densification happen. The only change needed here is to read two numbers out of that loop on a fixed cadence and append them to a CSV: the scalar loss, and `len(splats["means"])` (or the equivalent count of active Gaussians in your parameter dict) as it stands after that step's densification.

```python
import csv
import time
from pathlib import Path

class TrainingLogger:
    def __init__(self, log_path: Path, flush_every: int = 50):
        self.log_path = log_path
        self.flush_every = flush_every
        self._rows_since_flush = 0
        is_new = not log_path.exists()
        self._fh = open(log_path, "a", newline="")
        self._writer = csv.writer(self._fh)
        if is_new:
            self._writer.writerow(["step", "wall_time", "loss", "num_splats"])

    def log(self, step: int, loss: float, num_splats: int):
        self._writer.writerow([step, time.time(), loss, num_splats])
        self._rows_since_flush += 1
        if self._rows_since_flush >= self.flush_every:
            self._fh.flush()
            self._rows_since_flush = 0

    def close(self):
        self._fh.flush()
        self._fh.close()
```

Flushing every 50 rows rather than every row keeps disk I/O off the hot path without leaving you with an empty file if the process gets killed mid-run. In the training loop itself, logging is a two-line addition:

```python
logger = TrainingLogger(Path("runs/room-042/metrics.csv"))

for step in range(max_steps):
    optimizer.zero_grad()
    render, info = rasterize(splats, camera)
    loss = compute_loss(render, target_image)
    loss.backward()
    strategy.step_post_backward(
        params=splats, optimizers=optimizer, state=strategy_state,
        step=step, info=info,
    )
    optimizer.step()

    if step % log_every == 0:
        logger.log(step, float(loss.detach()), splats["means"].shape[0])

logger.close()
```

`log_every` of 10 to 20 is enough resolution to see a trend without bloating the CSV; a 30k-step run at every-10 logging produces 3,000 rows, which any plotting library handles instantly.

## Reading the loss curve

The loss itself is whatever combination of photometric terms (L1, D-SSIM) the training setup uses; the shape of the curve matters more than its exact units. A healthy run shows a fast initial drop over the first few hundred steps, then a long, noisy but steadily declining tail. Two failure shapes are worth watching for specifically:

A **stalled run** shows loss flatten out early and stay flat, often before `refine_start_iter` has even triggered densification. If loss has not visibly improved by the time densification would normally start (step 500 under the documented defaults), something upstream is wrong: intrinsics, image-camera pose alignment, or a camera model mismatch, not a hyperparameter that a longer run will fix.

A **diverging run** shows loss trending up, or spiking sharply and never recovering, often right around a `reset_every` opacity reset under `DefaultStrategy`. A single spike that recovers within the next refine window is normal; a spike that the curve never comes back down from means the optimizer overshot after that reset. Since `reset_every` defaults to 3000, quick sanity plots at steps 3000, 6000, 9000, and so on will catch this pattern early rather than waiting for the full run.

## Reading the splat count curve

Splat count tells a different story from loss, and the two need to be read together, not separately. Under `DefaultStrategy`, count should climb during the `refine_start_iter` to `refine_stop_iter` window (500 to 15000 by default) as gradient-driven splitting and cloning add Gaussians, then flatten once refinement stops at 15000, with only pruning still trimming the tail. If count is still climbing steeply at step 15000, either the run has more geometric detail than the strategy's default window accounts for, or gradients are staying artificially high because the geometry underneath is wrong, in which case loss will usually be flat or noisy at the same time, not improving.

Under `MCMCStrategy`, the useful comparison is against `cap_max` (1,000,000 by default). A healthy MCMC run's count curve rises and asymptotically approaches the cap; if it plateaus far below the cap while loss is still improving, that is fine, it just means the scene did not need the full budget. If count hits the cap almost immediately and loss is bad, that usually means the gradient signal is saturating the strategy rather than reflecting real added detail, worth checking against the sparse point cloud's own density from the COLMAP run.

The other pattern worth flagging is count that *drops* sharply mid-run outside of an expected pruning phase. Since pruning removes Gaussians whose opacity falls below `prune_opa` (0.005) or whose scale exceeds `prune_scale3d`/`prune_scale2d` (0.1 / 0.15), a sudden large drop usually means a batch of Gaussians collectively collapsed to near-zero opacity, often correlated with the same loss spikes described above. Reading loss and count side by side turns two noisy signals into one diagnosis: loss flat and count flat together means stalled; loss spiking and count crashing together means a bad optimizer step, not normal pruning.

## Plotting

A single matplotlib figure with two stacked axes, loss on top and count on bottom sharing the x-axis, is enough. This does not need to run live inside the training process; run it against the CSV after the fact, or on a timer against the growing file while training continues in another process.

```python
import pandas as pd
import matplotlib.pyplot as plt

def plot_run(csv_path: str, out_path: str = "runs/room-042/progress.png"):
    df = pd.read_csv(csv_path)

    fig, (ax_loss, ax_count) = plt.subplots(2, 1, sharex=True, figsize=(9, 6))

    ax_loss.plot(df["step"], df["loss"], linewidth=1)
    ax_loss.set_ylabel("loss")
    ax_loss.set_yscale("log")
    ax_loss.grid(alpha=0.3)

    ax_count.plot(df["step"], df["num_splats"], color="tab:orange", linewidth=1)
    ax_count.set_ylabel("num splats")
    ax_count.set_xlabel("step")
    ax_count.grid(alpha=0.3)

    fig.tight_layout()
    fig.savefig(out_path, dpi=120)
    plt.close(fig)
```

Log-scale loss is worth defaulting to: the first few hundred steps drop by an order of magnitude or more, and a linear axis compresses the entire interesting tail into a flat-looking line near zero. Re-running `plot_run` every few thousand steps against the still-growing CSV, or wiring it into a simple watch loop, gives a check-in point without needing a dashboard framework.

## Turning the two curves into a go/no-go check

For a solo operator without deep gsplat experience, the practical use of this instrumentation is a short manual checklist run at two or three points during a long training session, for example at steps 1000, 5000, and 15000 (the default `refine_stop_iter`):

```python
def quick_diagnosis(csv_path: str, strategy: str = "default", cap_max: int = 1_000_000):
    df = pd.read_csv(csv_path)
    recent = df.tail(max(1, len(df) // 20))
    loss_trend = recent["loss"].iloc[-1] - recent["loss"].iloc[0]
    count_now = int(df["num_splats"].iloc[-1])

    flags = []
    if loss_trend > 0:
        flags.append("loss rising over the last 5% of logged steps: possible divergence")
    if recent["loss"].std() / max(recent["loss"].mean(), 1e-8) < 0.01 and df["step"].iloc[-1] < 500:
        flags.append("loss essentially flat this early: possible stall before densification")
    if strategy == "mcmc" and count_now >= cap_max:
        flags.append(f"splat count at cap ({cap_max}): check if this saturated early")

    return flags or ["no obvious problems from loss/count alone"]
```

This is a heuristic, not a certainty. It exists to catch the two cheapest-to-fix failure modes, a stall and a divergence, before you burn the rest of a training budget on a run that was never going to finish well. Once a run passes this check and completes, the next step is exporting it into something you can actually walk through, which is the subject of "Exporting a Trained Splat for a Walkable Viewer."

A gap worth stating plainly: the notes behind this book do not include gsplat's exact `rasterization()` call signature or a documented built-in logging/callback API (that surface exists on the gsplat GitHub repo but was not independently verified here), so the logger above wraps the loop from the outside rather than hooking into any first-party instrumentation gsplat itself ships.
