# Reading the Bundle: Opening manifest.json and crops/*.jpg in Python

Every Orbit Capture run ends the same way on disk: a single `bundle.zip` that the operator hands off (or the capture app uploads) to whatever machine is going to run COLMAP and gsplat. Before any structure-from-motion happens, something has to open that zip, read its manifest, and confirm the images it promises are actually inside. That something is a small, boring script, and it is the first piece of code in this shelf's pipeline. Everything downstream (the environment setup covered in *Setting Up a COLMAP + gsplat Environment in Python 3.11*, the fuller ingestion module in *Building the Bundle Ingestion Module: manifest.json to a COLMAP Project*, and the end-to-end shape described in *From Photos to a Walkable Scene: The Reconstruction Pipeline at a Glance*) assumes this step already happened cleanly.

The bundle's layout is a product convention rather than a COLMAP or Python standard, so we state it plainly here: `bundle.zip` contains a `manifest.json` at its root and a `crops/` directory holding the room-by-room JPG stills (or stitched equirectangular frames, for X4 Air captures). The manifest carries four top-level keys worth caring about at this stage: `app` (which capture client and version produced the bundle), `project` (the human-facing name and any room/session identifiers), `crops` (a list describing each image file the zip should contain), and `rig` (camera/rig metadata, present when the capture used a fixed multi-sensor setup rather than a single handheld phone). This book's job is narrow: open the zip, parse those four keys, and list the crops so a human or the next script can sanity-check the bundle before it goes anywhere near a reconstruction pipeline.

## Why zipfile and not something heavier

Python's standard library already does everything this step needs. The `zipfile` module's `ZipFile` class opens an archive for reading, exposes `namelist()` to enumerate every member path, and `read(name)` to pull a member's raw bytes back without extracting it to disk first (per the official Python 3 `zipfile` documentation). That last part matters: a manifest is a few kilobytes of JSON, and there is no reason to unzip the whole bundle just to read it. `ZipFile` also works as a context manager, so `with zipfile.ZipFile(path) as zf:` closes the archive handle automatically even if something inside the block raises.

That is the entire dependency list for this book: `zipfile` and `json`, both stdlib. No third-party archive library, no manifest schema validator pulled in from PyPI. If the manifest format grows real structural guarantees later (required fields, versioned schemas), that is a reasonable place to reach for `pydantic` or similar, but a first reader that lists what is inside a bundle does not need it yet.

## The script

```python
"""bundle_reader.py

Opens an Orbit Capture bundle.zip, parses manifest.json, and lists
the crop images the manifest says should be present.
"""

from __future__ import annotations

import json
import zipfile
from dataclasses import dataclass
from pathlib import Path


@dataclass
class CropEntry:
    filename: str
    room: str | None
    index: int | None


@dataclass
class BundleManifest:
    app: dict
    project: dict
    crops: list[CropEntry]
    rig: dict | None

    @property
    def crop_filenames(self) -> list[str]:
        return [c.filename for c in self.crops]


def load_manifest(zf: zipfile.ZipFile, manifest_name: str = "manifest.json") -> BundleManifest:
    raw = zf.read(manifest_name)
    data = json.loads(raw)

    crops_raw = data.get("crops", [])
    crops = [
        CropEntry(
            filename=entry["filename"],
            room=entry.get("room"),
            index=entry.get("index"),
        )
        for entry in crops_raw
    ]

    return BundleManifest(
        app=data.get("app", {}),
        project=data.get("project", {}),
        crops=crops,
        rig=data.get("rig"),
    )


def open_bundle(bundle_path: str | Path) -> tuple[zipfile.ZipFile, BundleManifest]:
    zf = zipfile.ZipFile(bundle_path)
    manifest = load_manifest(zf)
    return zf, manifest


def list_crops(bundle_path: str | Path) -> None:
    with zipfile.ZipFile(bundle_path) as zf:
        manifest = load_manifest(zf)
        names_in_zip = set(zf.namelist())

        print(f"app: {manifest.app.get('name', '?')} {manifest.app.get('version', '')}")
        print(f"project: {manifest.project.get('name', '?')}")
        if manifest.rig:
            print(f"rig: {manifest.rig.get('name', manifest.rig.get('type', 'unnamed'))}")
        else:
            print("rig: none (handheld capture)")

        print(f"\n{len(manifest.crops)} crops listed in manifest:")
        missing = []
        for crop in manifest.crops:
            zip_path = f"crops/{crop.filename}"
            present = zip_path in names_in_zip
            marker = "ok" if present else "MISSING"
            room = crop.room or "-"
            print(f"  [{marker}] {zip_path}  room={room}  index={crop.index}")
            if not present:
                missing.append(zip_path)

        if missing:
            print(f"\n{len(missing)} crop(s) declared in manifest.json but not found in the zip.")


if __name__ == "__main__":
    import sys

    if len(sys.argv) != 2:
        print("usage: python bundle_reader.py path/to/bundle.zip")
        raise SystemExit(1)

    list_crops(sys.argv[1])
```

## Reading it

`load_manifest` takes an already-open `ZipFile` rather than a path, which keeps it testable and keeps the archive-lifetime decision (when to open, when to close) in the caller's hands, matching how `zipfile` is meant to be used as a context manager. It calls `zf.read("manifest.json")` to get the manifest's raw bytes straight out of the zip, then `json.loads` to turn them into a plain dict, exactly the read-then-parse pattern the `zipfile` docs describe for pulling a member and decoding it.

The four manifest keys map onto the `BundleManifest` dataclass without transformation for `app` and `project`, since at this stage we only need to display them, not validate their internals. `crops` gets a light shape check: each entry becomes a `CropEntry` with `filename`, and optional `room`/`index` fields (`.get` rather than `[]` for the optional ones, so a manifest that omits per-crop room tagging still parses). `rig` is left as `None` when absent, since a handheld phone capture legitimately has no rig block; a fixed multi-sensor rig only exists when the capture explicitly used one, and that "no rig" case is not an error, just a different capture mode.

`list_crops` is the operator-facing entry point. It cross-checks the manifest's claimed crop filenames against `zf.namelist()`, the actual member list inside the archive, and flags anything the manifest says should be there but the zip does not contain. This is the cheapest form of bundle validation available: no image decoding, no EXIF reading, just "does the file that manifest.json promised actually exist in this archive." A bundle that fails this check should never reach the reconstruction pipeline, because a missing crop later shows up as a mysterious COLMAP registration gap rather than a clear error at ingestion time.

One thing this script deliberately does not do: it does not open or decode the JPGs themselves with Pillow or OpenCV. That is a job for the next stage in the pipeline, once the bundle is confirmed complete. Keeping this script to "parse the manifest, confirm the crop list" makes it fast (no image I/O) and keeps its failure mode legible; if it reports every crop present, the bundle is structurally sound even if nothing about pixel content has been checked yet.
