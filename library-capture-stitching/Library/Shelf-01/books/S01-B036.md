# Flagging and Triggering a Reshoot Mid-Session

A blur score that only shows up in a post-capture report is a score you read tomorrow, in a hotel room, three buildings away from the wall that needs a redo. The whole value of scoring blur on-device is temporal: catch the bad frame while the operator is still standing in that spot, phone still raised, before the next step forward makes the frame unrecoverable. This book wires the sibling volume's scoring routine, described in "On-Device Laplacian-Variance Blur Scoring in Kotlin", into a live flag that fires inside the capture loop itself: score the frame, compare it to a threshold, and if it fails, interrupt the operator immediately instead of letting them walk on.

The underlying measurement is not new. The variance-of-Laplacian technique documented in PyImageSearch's "Blur detection with OpenCV" is a single call, `cv2.Laplacian(image, cv2.CV_64F).var()`, run on a grayscale frame: convolve with the Laplacian kernel, take the variance of the response. Sharp images carry abundant edges and produce high variance; blurry images have few distinct edges and score low. The 64-bit float output matters because Laplacian derivatives can be negative, and an 8-bit unsigned buffer would clip that signal before it reaches the variance calculation. That single fact is the entire physical basis for everything below; the rest of this book is the plumbing that turns one offline number into a same-second interrupt.

## What "flagging" actually means here

Flagging is not the same job as scoring, and it is not the same job as deciding. Scoring (covered in the sibling volume) produces a number. Deciding whether that number, combined with overlap coverage, means the room needs a redo is the job of "Deciding On-Site Whether a Room Needs a Reshoot" and, at the multi-signal level, "Automating Reshoot Triggers from Blur and Overlap Scores Together." This book sits between those two: it is the wiring that takes a fresh score and turns it into an immediate, actionable interrupt for one frame, before the operator's next footstep. Flagging has one job: notice fast, and never notice fast at the cost of false alarms so frequent the operator starts ignoring the flag.

That last constraint shapes the design more than the Laplacian math does. PyImageSearch's own worked example scored blurry images in the 64-83 range and sharp images from 200 to 1000+, using a threshold of 100.0, but the author is explicit that this number is "quite subjective to the contents of the image(s)" and must be tuned per dataset rather than treated as universal. A flagging system that hardcodes 100.0 and calls it done will either nag constantly on genuinely low-texture rooms (a blank hallway wall legitimately scores lower than a bookshelf) or miss real blur on high-texture scenes where even a blurry frame retains some edge energy. The notes give no indoor-specific number to substitute, so the honest move is a threshold that calibrates itself against the room rather than a fixed constant.

## The live flag as a small state machine

The flag needs to be a state machine, not a bare `if (score < threshold) interrupt()`. A single low score should not, by itself, launch a full-screen "RESHOOT" prompt mid-swing, because CameraX's `ImageAnalysis` use case delivers frames continuously and any one frame can be transiently soft from a hand tremor that resolves itself a frame later. The flag needs a short run of consecutive low scores before it escalates, and it needs to reset the instant a good frame comes through.

```kotlin
class BlurFlagController(
    private val consecutiveBadFramesToTrigger: Int = 3,
    private val calibrationWindow: Int = 40
) {
    private val recentScores = ArrayDeque<Double>(calibrationWindow)
    private var consecutiveBad = 0
    private var dynamicThreshold = DEFAULT_THRESHOLD

    fun onScore(score: Double): FlagDecision {
        recentScores.addLast(score)
        if (recentScores.size > calibrationWindow) recentScores.removeFirst()
        if (recentScores.size >= MIN_SAMPLES_FOR_CALIBRATION) {
            dynamicThreshold = computeThreshold(recentScores)
        }

        return if (score < dynamicThreshold) {
            consecutiveBad += 1
            if (consecutiveBad >= consecutiveBadFramesToTrigger) {
                consecutiveBad = 0
                FlagDecision.Reshoot(score, dynamicThreshold)
            } else {
                FlagDecision.Watching(score, dynamicThreshold)
            }
        } else {
            consecutiveBad = 0
            FlagDecision.Clear(score, dynamicThreshold)
        }
    }

    private fun computeThreshold(samples: ArrayDeque<Double>): Double {
        val sorted = samples.sorted()
        val median = sorted[sorted.size / 2]
        return median * THRESHOLD_FRACTION_OF_MEDIAN
    }

    companion object {
        private const val DEFAULT_THRESHOLD = 100.0
        private const val MIN_SAMPLES_FOR_CALIBRATION = 10
        private const val THRESHOLD_FRACTION_OF_MEDIAN = 0.5
    }
}

sealed class FlagDecision(val score: Double, val threshold: Double) {
    class Clear(score: Double, threshold: Double) : FlagDecision(score, threshold)
    class Watching(score: Double, threshold: Double) : FlagDecision(score, threshold)
    class Reshoot(score: Double, threshold: Double) : FlagDecision(score, threshold)
}
```

The `DEFAULT_THRESHOLD` of 100.0 is seeded directly from PyImageSearch's worked example, used only until enough in-session samples accumulate to calibrate against the room the operator is actually standing in. `computeThreshold` takes the running median of recent frame scores and sets the reshoot line at half that median. This is a deliberate ceiling, not a principled derivation: the notes support the general pattern that photogrammetry guidance raises thresholds for harder scene types (Pix4D and the CIPA 3x3 Rules both document scenario-specific overlap increases for texture-poor or repetitive surfaces) but no source gives a specific indoor blur-threshold multiplier, so treat 0.5 as a starting knob to retune against your own capture sessions, not a validated constant.

## Wiring it into CameraX's analysis pipeline

The flag controller is deliberately camera-API-agnostic; the CameraX side just needs to feed it a score per frame and act on the decision. `ImageAnalysis.Analyzer` is the natural seam, since it already runs off the UI thread and CameraX drops frames it can't keep up with rather than queuing them, which keeps the blur check from becoming the bottleneck in the capture loop.

```kotlin
class BlurCheckAnalyzer(
    private val flagController: BlurFlagController,
    private val onDecision: (FlagDecision) -> Unit
) : ImageAnalysis.Analyzer {

    override fun analyze(imageProxy: ImageProxy) {
        try {
            val grayMat = imageProxy.toGrayscaleMat()
            val score = laplacianVariance(grayMat)
            val decision = flagController.onScore(score)
            onDecision(decision)
        } finally {
            imageProxy.close()
        }
    }
}
```

`laplacianVariance` here is the routine built out fully in "On-Device Laplacian-Variance Blur Scoring in Kotlin"; this book treats it as a black box that returns the same number PyImageSearch's `cv2.Laplacian(...).var()` would, computed via OpenCV's Android bindings on the frame's luminance plane. The important detail for wiring purposes is that `imageProxy.close()` must run in a `finally` block regardless of what happens in scoring, because CameraX will stop delivering new frames to an analyzer that never releases the buffer it was given.

Reacting to a `FlagDecision.Reshoot` should be loud and immediate: a haptic buzz plus a screen overlay that the operator can dismiss only by acknowledging, not a toast that fades in two seconds while their attention is on the doorway ahead. The interrupt is the entire point; anything more diplomatic than that defeats the purpose of catching the frame before the operator's feet have already moved.

## One honest gap

The research notes underlying this shelf do not include Android's own OpenCV documentation for the Laplacian operator; PyImageSearch is a credible third-party source for the formula and the `CV_64F` rationale, but a writer or engineer needing the exact OpenCV Android API signature should verify it against OpenCV's own docs before shipping, since these notes cannot confirm the exact call surface there.
