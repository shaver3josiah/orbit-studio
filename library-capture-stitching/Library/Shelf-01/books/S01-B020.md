# AWB Lock vs. a True Fixed-Kelvin White Balance

Why do two rooms shot in the same "locked" white balance mode sometimes come out looking like they belong to different buildings?

The answer is that "locked" and "fixed" are not the same promise. Most operators reach for AWB lock because the name sounds like exactly what a splat capture needs: one color balance, held steady, no drift between the hundred-odd stills that make up a room. But AWB lock and a deliberately chosen Kelvin value freeze two different things, and the gap between them is where color-consistency bugs live.

## What AWB lock actually freezes

On Android, the Camera2 API exposes CONTROL_AWB_LOCK as a boolean. When it is on, "auto-white-balance is currently locked to its latest calculated values" and will not change color balance until unlocked (Android Developers, CaptureRequest reference). That phrasing matters: it locks to whatever the auto-algorithm last converged on, not to a value you chose. If you walked into the room, let the camera meter for half a second under mixed light, and locked at that instant, you have frozen the algorithm's best guess for that half second. It is stable from then on, but it was never aimed at anything in particular.

CONTROL_AWB_MODE, the sibling control that actually names a target, is limited to a fixed list of presets: INCANDESCENT, FLUORESCENT, WARM_FLUORESCENT, DAYLIGHT, CLOUDY_DAYLIGHT, TWILIGHT, SHADE (Android Developers, CameraMetadata). Each of these approximates a specific reference illuminant rather than an arbitrary number. INCANDESCENT approximates CIE standard illuminant A; FLUORESCENT approximates CIE standard illuminant F2. There is no CONTROL_AWB_MODE_5000K. Camera2 simply does not expose a "set white balance to N Kelvin" control. So a true fixed-Kelvin strategy on Android is necessarily an approximation through the nearest preset, and it is a categorically different move from locking: one is choosing a target, the other is freezing an in-flight guess wherever it happened to land.

## Why the difference matters for a splat capture

The practical case for holding one white balance across a shoot is well established outside of Android's API surface too. Auto white balance is fine for a single scene under stable daylight, but it is documented to visibly drift frame-to-frame under mixed or colored indoor lighting, because it re-estimates color temperature independently on every shot (Fstoppers, on shooting with Kelvin temperatures). Techniques that depend on color consistency across many frames — panoramas, focus stacks, blended-exposure sequences, and by direct extension, a room's worth of overlapping stills destined for COLMAP and gaussian splat training — are specifically called out as needing a fixed setting rather than an auto one, because AWB can shift slightly between otherwise-identical frames and create mismatches that have to be corrected in post.

Now put AWB lock into that picture. Locking freezes the drift, which is real progress: you will not get frame 40 shifted orange relative to frame 4. But if the guess you locked onto was itself a compromise, every frame in the room now shares that same compromise consistently. That is subtly worse than it sounds, because consistency is not the same goal as accuracy. A splat trained on a room where every image agrees on a slightly-wrong color cast will still produce visible seams the moment that room's data meets the next room's data, where AWB happened to lock onto a different compromise. The companion volume in this shelf, "Carrying One White Balance Across Differently-Lit Rooms," works through exactly that seam problem: two rooms, two lock events, two different frozen guesses, and a visible color jump between them in the finished scene. Locking within a room solves the within-room problem. It does nothing for the between-room problem, because "locked" only ever means "whatever it was when I pressed the button," and different rooms produce different whatevers.

A deliberately chosen Kelvin value, even approximated through the nearest Camera2 preset, sidesteps that failure mode differently. If a tungsten-lit hallway and a tungsten-lit bedroom both get set to the same INCANDESCENT-approximating preset on purpose, they share a target, not just an accident. Typical indoor tungsten lighting sits around 3000K, and because the human eye compensates for that orange cast automatically while a sensor records it faithfully, indoor scenes need that deliberate decision rather than a hopeful reliance on perception or on-the-fly estimation (Fstoppers). For genuinely mixed lighting within one room, such as a window and a lamp in the same frame, the same source recommends setting for the dominant or key light and accepting a single global compromise for the rest, rather than trying to correct multiple sources with one in-camera setting.

## The engineering distinction

For the engineer building the capture tool, this is a state-reading problem before it is a color-science problem. AE lock is a useful analogy and a trap at the same time: CONTROL_AE_LOCK determines whether exposure is locked to its latest calculated values, but because the camera pipelines in-flight requests, the settings that actually end up locked do not necessarily match the settings in the most recently delivered CaptureResult, since further captures or AE updates can occur before that result arrives (Android Developers, CaptureRequest reference). The sibling volume "AE Lock: What It Freezes and What It Doesn't" goes deeper into that pipelining hazard specifically for exposure. AWB behaves analogously: a UI that shows "locked" the instant the user taps the button may not reflect the value that actually got locked a frame or two later. If the tool needs to know exactly what white balance ended up frozen, and not just that locking was requested, it has to read that state back explicitly rather than trust the request it just sent, which is the subject of "Reading and Applying AWB Lock State via Camera2." Android's own guidance on this point is blunt: when AE is turned off, AWB and AF behavior becomes device-dependent, and the documented fix is to either set AWB and AF to OFF or lock them explicitly before disabling AE, specifically to get consistent behavior across different devices (Android Developers, CaptureRequest reference). That is a strong signal that "lock" in Camera2 is treated as a stabilization mechanism for cross-device consistency, not as a mechanism for hitting a chosen target.

## What this means for the operator

Treat AWB lock as a tool for holding still, not a tool for aiming. Before locking, walk to the room's dominant light source, let the camera meter on it deliberately, and only then lock, so the frozen value is a choice you made rather than an accident of timing. Better still, where the capture tool exposes it, set an explicit preset matched to the room's dominant illuminant and skip the auto-then-freeze step entirely. Either way, log what was used per room. A splat pipeline built from unlabeled, inconsistently-frozen guesses will always cost you a color-correction pass later that a five-second deliberate choice at capture time would have avoided.
