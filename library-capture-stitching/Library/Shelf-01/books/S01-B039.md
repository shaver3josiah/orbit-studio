# Assembling and Packing the Bundle: manifest.json and ZIP_STORED Crops

By the time a capture session ends, you have a folder of per-room JPEG crops on the phone and nothing that tells COLMAP, or the human running COLMAP, what any of it means. This book closes that gap. It builds `manifest.json`, the one file that names the app version, the project, every crop, and the rig that shot them, and it packs that manifest with the crops into a single `bundle.zip` that the pipeline can consume without surprises. The companion volume "The Bundle Contract: What Downstream Expects From You" defines what fields downstream code actually reads; this book is the concrete implementation that satisfies that contract.

## Why the manifest exists at all

A directory of JPEGs is not self-describing. It doesn't say which app produced it, which project or room each file belongs to, or what kind of rig captured it (locked-exposure phone stills versus a dual-fisheye 360 camera needing an equirectangular stitch). Without that, a downstream operator has to guess from filenames, and "Writing Per-Room Crops to Disk with Consistent Naming" already established that filenames only encode room and sequence, not capture metadata. The manifest is where that metadata lives, structured and machine-readable, so the COLMAP/gsplat side of the pipeline (or a human debugging a failed reconstruction) can inspect the bundle without opening a single image.

## The manifest schema

We keep four top-level keys: `app`, `project`, `crops`, and `rig`.

```python
from __future__ import annotations

import hashlib
import json
import platform
from dataclasses import dataclass, field
from datetime import datetime, timezone
from pathlib import Path


APP_NAME = "orbit-capture"
APP_VERSION = "1.4.0"
MANIFEST_VERSION = 1


@dataclass
class CropEntry:
    room: str
    filename: str
    sequence: int
    width: int
    height: int
    sha256: str
    captured_at: str

    def to_dict(self) -> dict:
        return {
            "room": self.room,
            "filename": self.filename,
            "sequence": self.sequence,
            "width": self.width,
            "height": self.height,
            "sha256": self.sha256,
            "captured_at": self.captured_at,
        }


@dataclass
class RigInfo:
    kind: str  # "phone_stills" or "insta360_x4_air"
    device_model: str
    ae_locked: bool
    awb_locked: bool
    notes: str = ""

    def to_dict(self) -> dict:
        return {
            "kind": self.kind,
            "device_model": self.device_model,
            "ae_locked": self.ae_locked,
            "awb_locked": self.awb_locked,
            "notes": self.notes,
        }


@dataclass
class ProjectInfo:
    project_id: str
    building_name: str
    rooms: list[str] = field(default_factory=list)

    def to_dict(self) -> dict:
        return {
            "project_id": self.project_id,
            "building_name": self.building_name,
            "rooms": self.rooms,
        }
```

Each field earns its place by answering a question the pipeline (or the person babysitting it) will otherwise have to ask by hand. `app` records which build of the capture tool produced the bundle, because a manifest schema written by version 1.4.0 is not guaranteed to match what version 2.0.0 emits, and a COLMAP run that behaves oddly is easier to triage once you know the producing version. `project` records the building and room list so a bundle can be identified without unzipping it. `crops` is the per-image inventory, one entry per JPEG, including a SHA-256 hash of the file bytes so a corrupted or truncated crop can be detected before it ever reaches COLMAP's feature extractor. `rig` records whether the source was locked-exposure phone stills or a stitched Insta360 X4 Air equirectangular sequence, because those two inputs have different implications for camera modeling downstream (a 360 rig produces equirectangular images that need different handling than standard pinhole phone photos).

## Building the manifest from a crop directory

```python
def sha256_of(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()


def image_dimensions(path: Path) -> tuple[int, int]:
    from PIL import Image

    with Image.open(path) as img:
        return img.width, img.height


def build_manifest(
    crop_dir: Path,
    project: ProjectInfo,
    rig: RigInfo,
) -> dict:
    crops: list[CropEntry] = []
    for jpg_path in sorted(crop_dir.glob("*.jpg")):
        stem_parts = jpg_path.stem.split("_")
        room, sequence = stem_parts[0], int(stem_parts[-1])
        width, height = image_dimensions(jpg_path)
        mtime = datetime.fromtimestamp(jpg_path.stat().st_mtime, tz=timezone.utc)
        crops.append(
            CropEntry(
                room=room,
                filename=jpg_path.name,
                sequence=sequence,
                width=width,
                height=height,
                sha256=sha256_of(jpg_path),
                captured_at=mtime.isoformat(),
            )
        )

    return {
        "manifest_version": MANIFEST_VERSION,
        "app": {"name": APP_NAME, "version": APP_VERSION, "host_os": platform.platform()},
        "project": project.to_dict(),
        "crops": [c.to_dict() for c in crops],
        "rig": rig.to_dict(),
    }
```

The filename parsing here assumes the `{room}_{sequence}.jpg` convention established in "Writing Per-Room Crops to Disk with Consistent Naming"; this book does not re-derive that scheme, it only consumes it. If that naming discipline was skipped upstream, `build_manifest` will fail loudly on the `int(stem_parts[-1])` conversion rather than silently misattribute a crop to the wrong room, which is the right failure mode for a manifest step: better to stop the bundle than ship a lying one.

## Why ZIP_STORED, not ZIP_DEFLATED

Python's `zipfile` module defaults to `ZIP_STORED`, the uncompressed storage method, and it only needs `ZIP_DEFLATED` (which requires the `zlib` module) when compression is explicitly requested (Python official docs, zipfile module). The `compresslevel` parameter has no effect at all under `ZIP_STORED`; it only does anything under `ZIP_DEFLATED` (same source). For this bundle that distinction matters because the crops are already JPEGs, and JPEG is already entropy-coded pixel data. Running `ZIP_DEFLATED` over already-compressed image bytes burns CPU time for a negligible size reduction, which is the documented justification in the zipfile docs themselves for choosing `ZIP_STORED` when the payload is photos rather than text or other easily-compressible data. On a solo operator's laptop, re-zipping a room's worth of full-resolution crops with deflate can visibly stall the tool for no benefit; storing them uncompressed keeps packing close to disk-I/O speed.

```python
import zipfile


def pack_bundle(
    crop_dir: Path,
    manifest: dict,
    output_zip: Path,
) -> Path:
    with zipfile.ZipFile(output_zip, mode="w", compression=zipfile.ZIP_STORED) as zf:
        zf.writestr("manifest.json", json.dumps(manifest, indent=2))
        for crop in manifest["crops"]:
            src = crop_dir / crop["filename"]
            zf.write(src, arcname=f"crops/{crop['filename']}")
    return output_zip
```

Two details are worth calling out. First, `manifest.json` is written at the archive root, not inside `crops/`, so a downstream reader can open the zip, read the first entry's name, and know exactly where the manifest lives without scanning the whole listing. Second, every crop is written under a fixed `crops/` prefix inside the archive regardless of where it lived on disk, so the bundle's internal layout is stable and independent of the operator's local folder structure. Both choices exist purely to make the archive predictable for whatever unpacks it next, which is the entire subject of "The Bundle Contract: What Downstream Expects From You."

## End-to-end assembly

```python
def assemble_bundle(
    crop_dir: Path,
    output_zip: Path,
    project_id: str,
    building_name: str,
    rig_kind: str,
    device_model: str,
) -> Path:
    rooms = sorted({p.stem.split("_")[0] for p in crop_dir.glob("*.jpg")})
    project = ProjectInfo(project_id=project_id, building_name=building_name, rooms=rooms)
    rig = RigInfo(
        kind=rig_kind,
        device_model=device_model,
        ae_locked=(rig_kind == "phone_stills"),
        awb_locked=(rig_kind == "phone_stills"),
    )
    manifest = build_manifest(crop_dir, project, rig)
    return pack_bundle(crop_dir, manifest, output_zip)


def demo() -> None:
    import tempfile

    with tempfile.TemporaryDirectory() as td:
        crop_dir = Path(td) / "crops"
        crop_dir.mkdir()
        from PIL import Image

        for room, seq in [("kitchen", 1), ("kitchen", 2), ("hallway", 1)]:
            Image.new("RGB", (64, 48), color=(seq * 30, 10, 10)).save(
                crop_dir / f"{room}_{seq:03d}.jpg"
            )

        out_zip = Path(td) / "bundle.zip"
        assemble_bundle(
            crop_dir, out_zip, "proj-001", "123 Main St", "phone_stills", "Pixel 8"
        )

        with zipfile.ZipFile(out_zip) as zf:
            names = zf.namelist()
            assert "manifest.json" in names
            assert "crops/kitchen_001.jpg" in names
            assert "crops/hallway_001.jpg" in names
            info = zf.getinfo("crops/kitchen_001.jpg")
            assert info.compress_type == zipfile.ZIP_STORED

            manifest = json.loads(zf.read("manifest.json"))
            assert len(manifest["crops"]) == 3
            assert manifest["project"]["rooms"] == ["hallway", "kitchen"]
            assert manifest["rig"]["kind"] == "phone_stills"

    print("bundle assembly self-check passed")


if __name__ == "__main__":
    demo()
```

`demo()` is the whole verification story this module needs: build a tiny synthetic crop set, pack it, then reopen the zip and assert that the manifest is present, every crop landed under `crops/`, the compression type on a stored member is actually `ZIP_STORED`, and the room list and rig fields round-tripped correctly. If a future change accidentally switches the writer to `ZIP_DEFLATED`, or breaks the room-from-filename parsing, this assertion catches it immediately rather than surfacing three steps later as a confusing COLMAP failure.

## What this doesn't cover

The notes available for this shelf document `ZIP_STORED` versus `ZIP_DEFLATED` behavior precisely, but they say nothing about incremental or streaming zip writes for very large bundles, nor about compressing the manifest itself independently of the crops; this book does not invent numbers or APIs beyond what `zipfile`'s own documentation supports, so those two questions are left open rather than guessed at.

Once the bundle is built this way, the operator's job is just to hand the zip off intact. What that handoff actually requires of the operator, versus what's automatic, is the subject of "Handoff Discipline: What the Operator Owes the Pipeline."
