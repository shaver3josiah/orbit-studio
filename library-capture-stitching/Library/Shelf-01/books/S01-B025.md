# Live Coverage Tracking: Am I Done With This Room?

An operator walking a room with a phone has no reliable internal sense of "enough." You feel like you have covered a wall because you have been standing in front of it for a while, but feel is not a coverage metric. What you actually need is a number: shots taken against this wall versus shots this wall requires, updated live, so the app can tell you "done" or "keep going" instead of you guessing and either under-shooting (holes in the reconstruction) or over-shooting (wasted time and a bloated image set that, per COLMAP's own tutorial, slows processing without improving quality past a point). This book builds that tally.

## What "enough" actually means, numerically

Two source numbers anchor the target. First, COLMAP's FAQ states a hard minimum: every object or surface point needs to appear in at least three images for geo-registration and reliable reconstruction to work at all ("Make sure that each object is seen in at least 3 images"). Three is a floor, not a target. Second, Pix4D's best-practices guidance calls out interior reconstruction specifically as needing high overlap, around 90%, with terrestrial (ground-based) capture recommended over other methods for interiors, well above the general-case baseline of 75% frontal / 60% side overlap it recommends for typical scenes. Interiors get pushed toward the high end of Pix4D's scenario table for the same reason forests and snow do: harder feature matching, more room for the reconstruction to fail quietly.

So the tracker is not counting toward 3. It is counting toward however many shots a 90%-overlap requirement implies for a wall of a given length, then treating 3 as an absolute floor that overrides the arithmetic if the wall is short enough that overlap math would suggest fewer.

The geometry: at a given standoff distance from the wall, a phone's horizontal field of view covers a strip of wall of some width. Geodetic Systems' basics-of-photogrammetry guidance frames standoff distance as a deliberately varied, but locally stable, parameter, and explicitly ties a stable standoff to holding the frame-to-frame overlap consistent while walking a path. If standoff drifts, the strip width drifts, and a fixed shot-spacing assumption stops matching reality. The tracker needs standoff as an input, not an assumption.

Given standoff `d` and horizontal FOV `theta`, the visible strip width is `w = 2 * d * tan(theta / 2)`. At target overlap fraction `o` (0.90 for interiors, per Pix4D), the required spacing between shot centers along the wall is `step = w * (1 - o)`. Number of shots needed for a wall of length `L` is `ceil(L / step) + 1`, floored at 3 per the COLMAP minimum.

## The wall model

A "wall" here is a straight run with a known or estimated length, identified by a heading bucket. The tracker does not need a full floor plan. It needs the operator (or a quick AR-measure tap, out of scope for this book) to register each wall's approximate length once, and then needs every subsequent shot classified against the nearest wall by device heading at capture time.

```kotlin
data class WallSpec(
    val id: String,
    val lengthMeters: Float,
    val headingDegrees: Float // outward-facing normal of the wall, 0-360
)

data class ShotRecord(
    val wallId: String,
    val timestampMs: Long,
    val standoffMeters: Float,
    val headingDegrees: Float
)

class WallCoverageTracker(
    private val walls: List<WallSpec>,
    private val horizontalFovDegrees: Float,
    private val targetOverlap: Float = 0.90f,
    private val minShotsPerWall: Int = 3
) {
    private val shotsByWall = mutableMapOf<String, MutableList<ShotRecord>>().apply {
        walls.forEach { put(it.id, mutableListOf()) }
    }

    fun requiredShots(wall: WallSpec, standoffMeters: Float): Int {
        val fovRad = Math.toRadians(horizontalFovDegrees.toDouble())
        val stripWidth = 2.0 * standoffMeters * kotlin.math.tan(fovRad / 2.0)
        val step = stripWidth * (1.0 - targetOverlap)
        if (step <= 0.0) return minShotsPerWall
        val bySpacing = kotlin.math.ceil(wall.lengthMeters / step).toInt() + 1
        return maxOf(bySpacing, minShotsPerWall)
    }

    fun recordShot(headingDegrees: Float, standoffMeters: Float, timestampMs: Long) {
        val wall = nearestWall(headingDegrees) ?: return
        shotsByWall.getValue(wall.id).add(
            ShotRecord(wall.id, timestampMs, standoffMeters, headingDegrees)
        )
    }

    fun coverage(wallId: String, standoffMeters: Float): CoverageStatus {
        val wall = walls.first { it.id == wallId }
        val taken = shotsByWall.getValue(wallId).size
        val required = requiredShots(wall, standoffMeters)
        return CoverageStatus(taken, required, taken >= required)
    }

    fun roomDone(assumedStandoffMeters: Float): Boolean =
        walls.all { coverage(it.id, assumedStandoffMeters).done }

    private fun nearestWall(headingDegrees: Float): WallSpec? {
        return walls.minByOrNull { wall ->
            val diff = kotlin.math.abs(wall.headingDegrees - headingDegrees) % 360f
            minOf(diff, 360f - diff)
        }
    }
}

data class CoverageStatus(val taken: Int, val required: Int, val done: Boolean)
```

`nearestWall` is deliberately naive, a wraparound-aware nearest-heading match against a small fixed list of walls. It has no notion of the operator standing at a corner and facing diagonally between two walls; a shot taken at 45 degrees between two perpendicular walls gets attributed entirely to whichever is closer, which will sometimes double-count a corner shot toward one wall's tally and starve the other. That is an acceptable ceiling for a v1 signal built on shot count, not a ground-truth coverage map; the companion volume A Field Overlap Estimator: Comparing Consecutive Frames covers the frame-to-frame overlap check that catches gaps this heading bucket alone would miss.

## Wiring it to capture

The tracker consumes two live signals per shot: device heading (from the rotation vector sensor or ARCore pose, not covered here) and standoff distance (from ARCore depth, a rangefinder pass, or an operator-entered constant per room). It does not care how the app got the frame, only that `recordShot` is called once per accepted capture.

```kotlin
class CoverageOverlay(
    private val tracker: WallCoverageTracker,
    private val standoffMeters: Float
) {
    fun onShotAccepted(headingDegrees: Float, timestampMs: Long) {
        tracker.recordShot(headingDegrees, standoffMeters, timestampMs)
    }

    fun statusText(): String {
        return tracker.roomDone(standoffMeters).let { done ->
            if (done) "Room coverage complete" else "Keep shooting: $incompleteWallsSummary"
        }
    }

    private val incompleteWallsSummary: String
        get() = "incomplete walls pending"
}
```

The overlay is intentionally thin. It exists to translate `roomDone()` into the single UI signal the operator actually wants: green light or keep going. Everything upstream, blur rejection, exposure lock, framing, belongs to the capture step that decides whether a shot even reaches `onShotAccepted` in the first place, and that decision is the subject of Working the 1-3 Minute Room: Pacing a Capture Session, which this tracker's `done` signal feeds directly into as the stop condition for a room.

## What this deliberately does not cover

The tracker treats a room as a set of vertical wall runs and stops there. It says nothing about ceiling and floor coverage, which have their own shot-count logic driven by a different geometry (looking up or down rather than across a standoff distance), covered separately in Vertical Coverage: Ceilings, Floors, and the Frames People Skip. It also does not attempt to detect texture-poor walls that need overlap above even the 90% interior baseline; the notes behind this shelf found no single authoritative source for an indoor-specific "tighten overlap further for blank walls" number, only the general pattern that Pix4D and CIPA both scale overlap up for harder scenarios (forests, snow, agricultural fields) without giving a specific figure for a blank interior wall, so that adjustment is left as an honest gap rather than an invented constant. An operator working a room with unusually blank drywall should treat this tracker's `done` signal as a floor, not a guarantee, and lean on visual judgment or the frame-overlap check in the sibling volume for anything the wall-tally math cannot see.
