# Capturing Frame Metadata: ISO, Shutter, EV, Timestamp

A splat-training run that comes out patchy in one hallway and clean everywhere else is a diagnosis problem, not just a modeling problem. By the time you are staring at gsplat's loss curves or COLMAP's sparse point cloud, the frame that caused the trouble is long gone, indistinguishable from its neighbors unless you kept a record. The fix is unglamorous: every crop this pipeline writes to disk gets a sidecar of the exposure state that produced it. ISO, shutter (exposure time), EV bias, and a capture timestamp, all captured at the moment `CaptureResult` becomes available and written next to the JPG before the operator ever moves to the next room.

This book is the metadata half of the room-by-room capture loop described in "Writing Per-Room Crops to Disk with Consistent Naming." That book owns the filename and the directory layout. This one owns what goes inside the sidecar. Together they mean a diagnostic script can later walk a run's crops, join each one to its exposure record, and answer "did ISO creep upward across this room" without re-opening the images.

## Why capture-time metadata, not derived-later metadata

It is tempting to reconstruct exposure info after the fact by reading JPEG EXIF. Don't. EXIF written by the OS encoder is not guaranteed to reflect the exact `CaptureRequest`/`CaptureResult` pair that produced the frame, and camera pipelines process requests in flight: per the Android Developers CaptureRequest reference, the settings that end up locked or applied "don't necessarily match the settings in the most recent CaptureResult received, since further captures/AE updates can occur before that result is delivered." That pipelining is exactly why this pipeline reads the `CaptureResult` for the specific capture, at the callback for that specific capture, rather than trusting a later snapshot of camera state to still describe an earlier frame.

This matters most in this project because of the sequence this shelf already teaches in "Coding the Unlock-Set-EV-Relock Sequence in Kotlin": AE gets unlocked, a bias is set, the camera relocks. If the frame that triggers a relock and the frame right after it get logged with the same timestamp-adjacent snapshot instead of their own actual results, drift diagnosis becomes guesswork. Same story for white balance: "Reading and Applying AWB Lock State via Camera2" locks AWB alongside AE for exactly the reason the Android Developers CaptureRequest reference gives for CONTROL_AWB_LOCK, that once locked, AWB "will not change color balance settings until" unlocked. Frame metadata should record that the exposure inputs were locked, not just what they were locked to.

## What gets recorded

Four fields per frame, matched one-to-one with the crop written to disk:

- **ISO** — the sensor sensitivity in effect for that capture.
- **Shutter** — the exposure time in effect for that capture.
- **EV bias** — the exposure compensation index applied on top of AE, which the Android Developers CaptureRequest reference documents as a fine adjustment "on top of the AE algorithm's own metering," reported in a device-specific step range around plus or minus 3 EV.
- **Timestamp** — the capture's sensor timestamp, so metadata can be sorted and joined against the room-walk order independent of file mtimes, which get scrambled by any copy or sync step downstream.

One honest gap: the research notes behind this shelf document AE lock, AWB lock, and exposure-compensation semantics from the Android Developers CaptureRequest reference in detail, but they do not enumerate the exact `CaptureResult` key names for ISO and shutter beyond that reference's general framing of exposure compensation as a separately configured control from the lock itself. The key names below (`SENSOR_SENSITIVITY`, `SENSOR_EXPOSURE_TIME`, `SENSOR_TIMESTAMP`, `CONTROL_AE_EXPOSURE_COMPENSATION`) are the standard Camera2 metadata keys used to read exactly this information, but treat them as implementation detail to verify against the SDK reference for the target API level, not as a claim sourced from these notes.

## Capturing the metadata in Kotlin

The capture session already has a `CameraCaptureSession.CaptureCallback` from the unlock-set-EV-relock sequence. Extending it to pull metadata costs nothing extra, it happens on the same callback that already exists to confirm the relock landed.

```kotlin
data class FrameExposure(
    val iso: Int,
    val shutterNanos: Long,
    val evBiasIndex: Int,
    val sensorTimestampNanos: Long
)

class FrameMetadataCapture {
    fun fromResult(result: TotalCaptureResult): FrameExposure {
        val iso = result.get(CaptureResult.SENSOR_SENSITIVITY)
            ?: error("SENSOR_SENSITIVITY missing from capture result")
        val shutter = result.get(CaptureResult.SENSOR_EXPOSURE_TIME)
            ?: error("SENSOR_EXPOSURE_TIME missing from capture result")
        val evIndex = result.get(CaptureResult.CONTROL_AE_EXPOSURE_COMPENSATION) ?: 0
        val timestamp = result.get(CaptureResult.SENSOR_TIMESTAMP)
            ?: error("SENSOR_TIMESTAMP missing from capture result")

        return FrameExposure(
            iso = iso,
            shutterNanos = shutter,
            evBiasIndex = evIndex,
            sensorTimestampNanos = timestamp
        )
    }
}
```

Failing loudly on a missing key, rather than defaulting it silently, is deliberate. A silently-defaulted ISO of zero in a diagnostic CSV looks like data, not like a missing read, and someone debugging exposure drift a week later has no way to tell the difference.

The callback that already exists for the relock confirmation is the natural place to call this:

```kotlin
class ExposureLoggingCaptureCallback(
    private val onFrame: (requestTag: Any?, exposure: FrameExposure) -> Unit
) : CameraCaptureSession.CaptureCallback() {

    override fun onCaptureCompleted(
        session: CameraCaptureSession,
        request: CaptureRequest,
        result: TotalCaptureResult
    ) {
        val exposure = FrameMetadataCapture().fromResult(result)
        onFrame(request.tag, exposure)
    }
}
```

`request.tag` is how this hooks into "Writing Per-Room Crops to Disk with Consistent Naming": tag each capture request with the room/frame identifier that book already generates for the filename, and the callback can pass both straight to a writer that persists them as a matched pair.

## Writing the sidecar

One JSON file per crop, same stem, `.exposure.json` suffix, written next to the JPG:

```kotlin
import org.json.JSONObject
import java.io.File

class ExposureSidecarWriter(private val outputDir: File) {

    fun write(cropFileName: String, exposure: FrameExposure) {
        val stem = cropFileName.substringBeforeLast(".")
        val sidecar = File(outputDir, "$stem.exposure.json")

        val json = JSONObject().apply {
            put("iso", exposure.iso)
            put("shutter_ns", exposure.shutterNanos)
            put("ev_bias_index", exposure.evBiasIndex)
            put("sensor_timestamp_ns", exposure.sensorTimestampNanos)
        }

        sidecar.writeText(json.toString())
    }
}
```

Flat JSON, one object, no nesting. This is deliberately not a database. A solo-operator capture session is a few hundred frames at most, and a diagnostic script downstream (Python, reading the crop directory) just globs `*.exposure.json` and joins on the shared filename stem. That script's job, not this book's, but the shape is worth stating: read every sidecar, sort by `sensor_timestamp_ns`, and plot ISO or EV bias against capture order to see where drift started.

```python
import json
from pathlib import Path

def load_exposure_series(crop_dir: Path) -> list[dict]:
    records = []
    for sidecar in sorted(crop_dir.glob("*.exposure.json")):
        data = json.loads(sidecar.read_text())
        data["stem"] = sidecar.name.removesuffix(".exposure.json")
        records.append(data)
    return sorted(records, key=lambda r: r["sensor_timestamp_ns"])
```

## A minimal self-check

Non-trivial logic here is the missing-key failure path and the filename-stem matching, so both get one runnable assertion:

```kotlin
fun demo() {
    val fakeResult = object {
        fun get(key: String): Any? = when (key) {
            "SENSOR_SENSITIVITY" -> 400
            "SENSOR_EXPOSURE_TIME" -> 8_000_000L
            "CONTROL_AE_EXPOSURE_COMPENSATION" -> -2
            "SENSOR_TIMESTAMP" -> 123_456_789L
            else -> null
        }
    }
    val exposure = FrameExposure(
        iso = fakeResult.get("SENSOR_SENSITIVITY") as Int,
        shutterNanos = fakeResult.get("SENSOR_EXPOSURE_TIME") as Long,
        evBiasIndex = fakeResult.get("CONTROL_AE_EXPOSURE_COMPENSATION") as Int,
        sensorTimestampNanos = fakeResult.get("SENSOR_TIMESTAMP") as Long
    )
    check(exposure.iso == 400)
    check(exposure.evBiasIndex == -2)
    println("frame metadata demo ok: $exposure")
}
```

Small, but it is the difference between an assumption and a checked one. When the diagnostic script three weeks from now says "ISO jumped from 400 to 1600 between frame 0043 and frame 0044 in the west hallway," that claim should trace back to a number that was actually read off the sensor at capture time, not inferred, not defaulted, and not re-derived from a JPEG's EXIF block after the fact.
