# Writing Per-Room Crops to Disk with Consistent Naming

An Orbit Capture session produces one flat pile of JPGs per room, and by the time that pile reaches COLMAP it has to already look like an ordered sequence, not a bag of files a shell happened to list in some order. This book implements the one piece of plumbing that makes that true: a `crops/` writer that gives every frame a filename encoding its room, its sequence position, and a stable sort order, before anything ever touches structure-from-motion.

The research notes for this shelf are thin on file-naming conventions specifically; no source in this shelf's bibliography addresses folder layout or filename schemes for photogrammetry capture tools. What the notes do support is *why* ordering matters once files reach COLMAP, and that's the design constraint this book builds against.

## Why the filename is not cosmetic

COLMAP's sequential matcher assumes frame order carries information. Per the COLMAP documentation on feature matching strategies, the sequential matcher's `overlap` parameter defaults to 10 consecutive images, matching image `i` against images in `[i-overlap, i+overlap]`, with an optional `quadratic_overlap` mode that spaces matches at `2^i` instead of linearly ("COLMAP sequential matcher overlap parameter and vocabulary-tree loop detection"). That only produces a sane reconstruction if "consecutive" in the filesystem means "consecutive" in the walk. If a room's frames get written out of order, or if two rooms' frames interleave because they landed in one directory sorted alphabetically by a timestamp that doesn't monotonically increase, sequential matching quietly matches the wrong neighbors.

The same notes describe loop detection firing on `(i mod loop_detection_period) == 0`, pulling the most visually similar prior frames from a vocabulary tree. That mechanism depends on a stable index `i`, which depends on a stable file order. If the capture tool renumbers files between sessions, or two devices contribute frames whose names collide or sort unpredictably, loop detection compares the wrong things, and the shelf's notes elsewhere flag that indoor scenes with repeating layouts already make loop closure fragile (visual aliasing between two similar-looking rooms is a documented risk in the loop-closure literature this shelf draws on). Consistent naming is the cheapest defense available before that problem ever reaches SLAM-adjacent code: if the room id is baked into the filename and the frame index is monotonic and zero-padded, no sort operation anywhere in the pipeline can scramble the walk.

This is also why the naming scheme has to be decided at write time, in the same module that receives frames from the state machine described in "Building the Room-by-Room Session State Machine". That state machine already knows which room is active and what index the operator is on; the crop writer's job is to turn that knowledge into a filename and a location on disk, not to re-derive it later from metadata.

## The naming scheme

Each crop gets a name of the form:

```
{room_slug}__{frame_index:06d}__{capture_ts}.jpg
```

- `room_slug` is a filesystem-safe, lowercase identifier for the room (`kitchen`, `bedroom-02`), assigned once by the state machine when the room opens and never renamed mid-session.
- `frame_index` is a zero-padded, monotonically increasing counter scoped to that room, reset to zero each time a new room starts. Six digits comfortably covers any session (a room with 999,999 frames is not a real scenario).
- `capture_ts` is the frame's capture timestamp in a sortable form (`YYYYMMDDTHHMMSSmmm`), carried over from the metadata described in "Capturing Frame Metadata: ISO, Shutter, EV, Timestamp". It is not the primary sort key, but it gives a human or a script a second, independent way to verify ordering without trusting the index alone.

The double underscore is deliberate: it is unlikely to appear inside a room slug and makes the three fields trivially splittable with `str.split("__")` without a regex.

Rooms live in their own subdirectory under `crops/`, named identically to the slug embedded in each frame's filename:

```
crops/
  kitchen/
    kitchen__000000__20260716T140212104.jpg
    kitchen__000001__20260716T140212430.jpg
    ...
  bedroom-02/
    bedroom-02__000000__20260716T140355012.jpg
    ...
```

The redundancy (room name in both the directory and the filename) is intentional, not sloppy. Directory-only grouping breaks the moment a bundle-packing step (see "Assembling and Packing the Bundle: manifest.json and ZIP_STORED Crops") flattens files into a single archive member list; the filename has to carry the grouping on its own once the directory structure is gone.

## Implementation

```python
from __future__ import annotations

import re
import shutil
from dataclasses import dataclass
from datetime import datetime
from pathlib import Path

ROOM_SLUG_RE = re.compile(r"^[a-z0-9]+(-[a-z0-9]+)*$")


def slugify_room_name(raw_name: str) -> str:
    slug = raw_name.strip().lower()
    slug = re.sub(r"[^a-z0-9]+", "-", slug)
    slug = slug.strip("-")
    if not slug:
        raise ValueError(f"room name '{raw_name}' has no usable characters")
    return slug


@dataclass(frozen=True)
class CropWriter:
    session_root: Path

    @property
    def crops_root(self) -> Path:
        return self.session_root / "crops"

    def room_dir(self, room_slug: str) -> Path:
        if not ROOM_SLUG_RE.match(room_slug):
            raise ValueError(f"'{room_slug}' is not a valid room slug")
        return self.crops_root / room_slug

    def open_room(self, room_slug: str) -> "RoomCropSequence":
        room_dir = self.room_dir(room_slug)
        room_dir.mkdir(parents=True, exist_ok=True)
        existing = sorted(room_dir.glob(f"{room_slug}__*.jpg"))
        if existing:
            raise FileExistsError(
                f"room '{room_slug}' already has {len(existing)} crops; "
                "each room must be opened exactly once per session"
            )
        return RoomCropSequence(room_dir=room_dir, room_slug=room_slug, next_index=0)


@dataclass
class RoomCropSequence:
    room_dir: Path
    room_slug: str
    next_index: int

    def write_frame(self, src_path: Path, captured_at: datetime) -> Path:
        if not src_path.is_file():
            raise FileNotFoundError(src_path)

        ts = captured_at.strftime("%Y%m%dT%H%M%S") + f"{captured_at.microsecond // 1000:03d}"
        filename = f"{self.room_slug}__{self.next_index:06d}__{ts}.jpg"
        dest_path = self.room_dir / filename

        if dest_path.exists():
            raise FileExistsError(f"refusing to overwrite existing crop {dest_path}")

        tmp_path = dest_path.with_suffix(".jpg.tmp")
        shutil.copyfile(src_path, tmp_path)
        tmp_path.replace(dest_path)

        self.next_index += 1
        return dest_path


def parse_crop_filename(path: Path) -> tuple[str, int, str]:
    stem = path.stem
    parts = stem.split("__")
    if len(parts) != 3:
        raise ValueError(f"'{path.name}' does not match room__index__timestamp.jpg")
    room_slug, index_str, ts = parts
    return room_slug, int(index_str), ts


def list_room_frames_in_order(room_dir: Path) -> list[Path]:
    frames = sorted(room_dir.glob("*.jpg"), key=lambda p: parse_crop_filename(p)[1])
    for i, frame in enumerate(frames):
        _, index, _ = parse_crop_filename(frame)
        if index != i:
            raise ValueError(
                f"gap or duplicate at position {i}: found index {index} in {frame.name}"
            )
    return frames
```

`open_room` refuses to reopen a room that already has crops on disk. This mirrors the discipline the session state machine already enforces (a room transitions once, from active to closed) and gives the crop writer an independent check rather than trusting the caller not to call it twice. `write_frame` writes to a `.tmp` sibling and renames into place; on POSIX and NTFS, `Path.replace` is atomic within the same filesystem, so a crash mid-copy never leaves a half-written file sitting under the final name where a downstream reader could pick it up.

`list_room_frames_in_order` is the read-side counterpart, and it does real work: it does not just sort by filename string (which happens to work here because of the zero-padding) but re-derives the index from the parsed filename and asserts there are no gaps or duplicates. A gap means a frame failed to copy and nobody noticed; a duplicate means the writer was called twice for the same index, which should be structurally impossible given `next_index` is monotonic in memory, but the check exists because "should be impossible" is not the same guarantee as "verified impossible" once a bundle gets packed, transferred, and unpacked days later.

## Feeding COLMAP without renaming anything

Because COLMAP's sequential matcher works off whatever order it reads image filenames in, and this scheme's zero-padded index sorts identically whether read by Python's `sorted()`, a shell `ls`, or COLMAP's own file-listing code, no reordering step is needed between `crops/<room>/` and the `images/` directory COLMAP expects. A room's crops can be copied or symlinked into a per-room COLMAP workspace directly:

```python
def stage_room_for_colmap(room_dir: Path, colmap_images_dir: Path) -> None:
    colmap_images_dir.mkdir(parents=True, exist_ok=True)
    for frame in list_room_frames_in_order(room_dir):
        target = colmap_images_dir / frame.name
        if not target.exists():
            target.hardlink_to(frame)
```

`list_room_frames_in_order` is called here rather than a bare glob so a corrupted room (a gap from a dropped frame) fails loudly before COLMAP ever sees it, rather than silently feeding a matcher that expects continuity it doesn't have.

## What this scheme deliberately does not do

It does not attempt cross-room ordering. Two different rooms' `frame_index` counters both start at zero, and nothing in this scheme claims kitchen frame 12 was captured before or after bedroom frame 5. That is fine, because COLMAP is run per-room in this pipeline (a consequence of the room-by-room capture model), and the manifest that ties rooms together into a single session, along with the ordering of rooms themselves, is the job of "Assembling and Packing the Bundle: manifest.json and ZIP_STORED Crops", not this module. This writer's only promise is that within one room's directory, filename order equals capture order equals COLMAP-matching order, exactly once, with no renaming step anywhere between the phone and the SfM solver.
