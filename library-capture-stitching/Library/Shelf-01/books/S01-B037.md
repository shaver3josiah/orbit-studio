# Building the Room-by-Room Session State Machine

A solo Orbit Capture operator does not think in frames. They think in rooms: walk in, shoot the room, decide if it is done, move to the next one. Every other piece of the app - exposure locking, coverage overlays, file naming - is a detail inside one of those four moments. If the app's code does not also think in rooms, you end up with a tangle of booleans (`isShooting`, `roomDone`, `pendingRoom`) that drift out of sync the first time the operator walks back into a room they thought they finished. A state machine makes the moments explicit and gives every other module in the app one thing to hang off: "what state is the session in right now."

This book builds that machine: a `Room` sealed hierarchy with four states (`Entering`, `Shooting`, `CoverageCheck`, `Complete`), a `SessionStateMachine` that owns transitions between rooms, and the coverage-check thresholds it enforces before letting a room close out. It does not re-derive the coverage math itself - that is the job of "Live Coverage Tracking: Am I Done With This Room?" - or the capture session setup - covered in "Camera2 Capture Session Basics for a Locked-Exposure App" - or the file layout captured shots land in, which is "Writing Per-Room Crops to Disk with Consistent Naming." This book is the traffic controller that calls into all three.

## Why a state machine and not a flag bag

The temptation is to track progress with a handful of mutable fields on a `RoomSession` object: a shot counter, a `blurryShotCount`, a `coverageOk` flag the UI polls. That works until two things happen at once - the operator backs out of a room mid-shoot, or a background blur-check completes after the operator has already moved to `CoverageCheck` - and now two code paths are racing to mutate the same fields. A state machine does not eliminate races, but it makes every transition a single, named, auditable event: you can log `Entering -> Shooting` and `Shooting -> CoverageCheck` and reconstruct exactly what happened in a session from the log alone. That auditability matters more here than in most mobile UI code, because a failed room only surfaces as a problem hours later, when COLMAP fails to register enough images for it - by then the operator is long gone from the building.

## The four states

```kotlin
sealed class RoomState {
    data class Entering(val roomId: String) : RoomState()

    data class Shooting(
        val roomId: String,
        val shotsCaptured: Int = 0,
        val sharpShots: Int = 0
    ) : RoomState()

    data class CoverageCheck(
        val roomId: String,
        val shotsCaptured: Int,
        val sharpShots: Int
    ) : RoomState()

    data class Complete(val roomId: String, val shotsCaptured: Int) : RoomState()
}
```

`Entering` exists as its own state rather than folding into `Shooting` because it is where the app does setup work that must finish before a single frame is captured: locking AE/AWB per "Camera2 Capture Session Basics," creating the per-room output directory per "Writing Per-Room Crops to Disk with Consistent Naming." If that setup is still a side effect buried inside a `startShooting()` call, a slow lock acquisition or a directory-creation failure has nowhere clean to surface. As a named state, it can time out, retry, or report an error without inventing a fifth "setting up" flag bag.

`shotsCaptured` and `sharpShots` are tracked separately because a raw shot count is a poor proxy for readiness. The blur-detection technique from "PyImageSearch - Blur detection with OpenCV" (`cv2.Laplacian(image, cv2.CV_64F).var()`, thresholded around 100 in their worked example, with the explicit caveat that the threshold is subjective per dataset) tells you which of those shots are actually usable. A room with forty shots and six of them hopelessly blurred from a hand jolt is not forty shots deep into coverage, it is thirty-four. `sharpShots` is the number the coverage check should reason about, not `shotsCaptured`.

## Transitions

```kotlin
sealed class RoomEvent {
    data class EnterFinished(val roomId: String) : RoomEvent()
    data class ShotCaptured(val isSharp: Boolean) : RoomEvent()
    object RequestCoverageCheck : RoomEvent()
    data class CoverageResult(val passed: Boolean) : RoomEvent()
    object ForceComplete : RoomEvent()
    object Reopen : RoomEvent()
}

class SessionStateMachine(initialRoomId: String) {
    var state: RoomState = RoomState.Entering(initialRoomId)
        private set

    private val history = mutableListOf<Pair<RoomState, RoomState>>()

    fun handle(event: RoomEvent): RoomState {
        val next = transition(state, event)
        history.add(state to next)
        state = next
        return next
    }

    private fun transition(current: RoomState, event: RoomEvent): RoomState = when (current) {
        is RoomState.Entering -> when (event) {
            is RoomEvent.EnterFinished -> RoomState.Shooting(current.roomId)
            else -> current
        }
        is RoomState.Shooting -> when (event) {
            is RoomEvent.ShotCaptured -> current.copy(
                shotsCaptured = current.shotsCaptured + 1,
                sharpShots = current.sharpShots + if (event.isSharp) 1 else 0
            )
            is RoomEvent.RequestCoverageCheck -> RoomState.CoverageCheck(
                current.roomId, current.shotsCaptured, current.sharpShots
            )
            is RoomEvent.ForceComplete -> RoomState.Complete(current.roomId, current.shotsCaptured)
            else -> current
        }
        is RoomState.CoverageCheck -> when (event) {
            is RoomEvent.CoverageResult -> if (event.passed) {
                RoomState.Complete(current.roomId, current.shotsCaptured)
            } else {
                RoomState.Shooting(current.roomId, current.shotsCaptured, current.sharpShots)
            }
            else -> current
        }
        is RoomState.Complete -> when (event) {
            is RoomEvent.Reopen -> RoomState.Shooting(current.roomId, current.shotsCaptured)
            else -> current
        }
    }
}
```

The `transition` function is a pure function of `(current state, event) -> next state`. Every branch that does not recognize its event returns `current` unchanged rather than throwing - an operator double-tapping "next room" or a stray duplicate event from a flaky Bluetooth remote should be a no-op, not a crash mid-shoot. The `history` list exists for exactly the debugging scenario above: when a room comes back from COLMAP under-registered, you can dump the transition log for that `roomId` and see whether the coverage check actually ran, or whether `ForceComplete` fired early because the operator hit a "skip room" button.

Notice `CoverageCheck` never talks to the coverage math directly - it just holds the shot counts and waits for a `CoverageResult` event. The actual decision of `passed: Boolean` is computed by the tracker described in "Live Coverage Tracking: Am I Done With This Room?" This book's job stops at defining the state that decision plugs into, deliberately, so that swapping the coverage heuristic later never touches this file.

## What backs the coverage-check gate

The notes available to this shelf do not give a single authoritative "indoor room overlap" number - the coverage tracker book will need to derive its threshold by analogy rather than quote one. What they do give is a floor and a direction. COLMAP's own tutorial states the hard geometric minimum plainly: every object or surface needs to be seen in at least three images, and the FAQ repeats this as a requirement for geo-registration - "each object is seen in at least 3 images" is the quoted minimum. Pix4D's best-practices guidance goes further for the specific case this shelf cares about: general captures want at least 75% frontal and 60% side overlap, but interior reconstruction is called out by name as needing overlap around 90%, with terrestrial (ground-based, i.e., walking-through) imagery explicitly recommended over other capture methods for interiors. A `CoverageCheck` state that only asks "did we get three photos of every wall" is satisfying COLMAP's hard floor, not Pix4D's interior recommendation - the gap between those two numbers is exactly the room for false confidence, and it is why `sharpShots`, not a raw frame count, is what should feed the pass/fail decision.

There is a second, quieter reason `CoverageCheck` is its own state rather than an inline check at the end of `Shooting`: COLMAP's sequential matcher has a bounded lookback window (`overlap`, defaulting to ten consecutive images per the deepwiki notes on COLMAP's matching strategies) and periodic loop-detection against a vocabulary tree. A room that gets short shrift now costs real time later, in a pipeline stage the operator is not watching. Making the gate a distinct, named state - one the UI can visibly block on, with a spinner and a "keep shooting" prompt - turns a downstream pipeline failure into an on-site correction, while the operator is still standing in the room.

## Driving it from the room list

A capture session is a sequence of rooms, not one room in isolation. The outer driver just needs to know when to mint a fresh `SessionStateMachine` and when the whole session is done.

```kotlin
class CaptureSession(private val roomIds: List<String>) {
    private var index = 0
    var current: SessionStateMachine = SessionStateMachine(roomIds[0])
        private set

    val isSessionComplete: Boolean
        get() = index >= roomIds.size

    fun advance() {
        check(current.state is RoomState.Complete) {
            "cannot advance past ${current.state} before it reaches Complete"
        }
        index += 1
        if (!isSessionComplete) {
            current = SessionStateMachine(roomIds[index])
        }
    }
}
```

The `check` is deliberate, not decorative: it is the one place in the whole machine where an invariant violation should crash loudly in development rather than silently corrupt a session. Every other unrecognized event is a harmless no-op; skipping past an unfinished room is not - it is exactly the bug this book exists to prevent, so it gets a hard assertion instead of a quiet fallthrough.

## A minimal self-check

```kotlin
fun demo() {
    val sm = SessionStateMachine("kitchen")
    check(sm.state is RoomState.Entering)

    sm.handle(RoomEvent.EnterFinished("kitchen"))
    check(sm.state is RoomState.Shooting)

    repeat(12) { sm.handle(RoomEvent.ShotCaptured(isSharp = it % 4 != 0)) }
    val shooting = sm.state as RoomState.Shooting
    check(shooting.shotsCaptured == 12 && shooting.sharpShots == 9)

    sm.handle(RoomEvent.RequestCoverageCheck)
    check(sm.state is RoomState.CoverageCheck)

    sm.handle(RoomEvent.CoverageResult(passed = false))
    check(sm.state is RoomState.Shooting)

    sm.handle(RoomEvent.RequestCoverageCheck)
    sm.handle(RoomEvent.CoverageResult(passed = true))
    check(sm.state is RoomState.Complete)

    println("state machine self-check passed")
}
```

This is the whole contract: state transitions are pure, unrecognized events are no-ops, and only `CoverageResult(passed = true)` closes a room out. Everything upstream of that boolean - what counts as sharp, what counts as enough - belongs to the coverage tracker and the capture session setup, not to this file.
