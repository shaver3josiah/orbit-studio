# Building a Pre-Upload Capture Health Check on Device

By the time a solo operator finishes walking a room, three separate signals already exist somewhere in memory or on disk: a blur score per frame, a running coverage count per surface, and the exposure/white-balance metadata attached to each capture. Individually each one answers a narrow question. Blur asks "is this frame sharp enough to contribute keypoints." Coverage asks "has every wall been seen enough times." Exposure asks "did the lighting stay consistent enough that COLMAP and the Gaussian-splat trainer aren't fighting inconsistent brightness or color." None of them, alone, tells the operator whether the scan is actually done. This book builds the on-device pass that fuses all three into one gate the operator sees before the "End Scan" button becomes tappable.

This is deliberately the integration layer, not the source of any single metric. The Laplacian-variance blur scorer is covered in depth in "On-Device Laplacian-Variance Blur Scoring in Kotlin," and the coverage-counting logic lives in "Live Coverage Tracking: Am I Done With This Room?" This book assumes both already exist as callable components and focuses on how to combine their outputs into a single health check, plus how that check should read exposure metadata that the capture session already recorded.

## Why a single fused check, not three separate warnings

A capture app that pops up three unrelated toast messages ("2 blurry frames," "north wall under-covered," "exposure drifted on frame 41") trains the operator to dismiss all three, because on a real job at least one of them fires on almost every room. A single pass/fail gate that explains itself in one line is more likely to get acted on. It also mirrors how the downstream pipeline actually fails: COLMAP does not reject a scene because of blur alone, or coverage alone, it reconstructs badly because of some combination of weak features, missing viewpoints, and inconsistent photometric conditions across a bundle. COLMAP's own tutorial guidance is to capture with high visual overlap, ensure every surface is seen in at least three images, avoid texture-less surfaces, and keep illumination consistent across the shoot, explicitly naming HDR/inconsistent-lighting scenes as a problem case (COLMAP 3.6 Documentation - Tutorial). A health check that only watches one of those dimensions is checking a fraction of what actually determines reconstruction quality.

## What each input signal actually is

Before writing the fusion logic, it helps to be precise about what each upstream component hands over, because the fusion code trusts these shapes rather than re-deriving them.

The blur scorer (from its own volume) exposes a `BlurScore` per captured frame, computed as the variance of the Laplacian on a grayscale conversion of the frame, following the well-known technique of running `cv2.Laplacian(image, CV_64F).var()` and using CV_64F specifically because Laplacian responses can be negative and would clip under an 8-bit unsigned type (PyImageSearch - Blur detection with OpenCV). The number by itself carries no absolute meaning; PyImageSearch's own worked example used a threshold of 100.0 but explicitly warned that the cutoff is "quite subjective to the contents of the image(s)" and must be tuned per dataset, not treated as universal. That means the fused health check should not hardcode a single magic blur threshold either; it takes the threshold as a tunable parameter, calibrated the same way the sibling volume recommends.

The coverage tracker exposes a per-surface observation count, and the fusion check treats COLMAP's own hard floor as the non-negotiable minimum: every registered object or point needs to be seen in at least three images for geo-registration/alignment to succeed at all (COLMAP 3.6 Documentation - Frequently Asked Questions), a number COLMAP's tutorial repeats as advice for capture itself ("more is better"). Three is a floor, not a target, so the health check exposes both a hard-fail count and a soft-warn count above it.

Exposure metadata is the piece this book owns most directly. Camera2's `CaptureResult` for a locked-exposure frame carries `CONTROL_AE_LOCK` and `CONTROL_AWB_LOCK` state, plus whatever exposure compensation index was active. Android's own reference documents that AE lock freezes the auto-exposure algorithm to its latest calculated values, and separately warns that because the camera pipeline has requests in flight, the settings that end up locked do not necessarily match the settings in the most recently delivered `CaptureResult` (Android Developers - CaptureRequest reference). AWB lock behaves the same way for white balance: once locked, the algorithm will not change color balance until explicitly unlocked (Android Developers - CaptureRequest reference; confirmed against the canonical javadoc text via the Microsoft Learn mirror). Practically, this means the health check cannot just check "is AE_LOCK set to true" once at the start of the scan and assume it held; it needs to sample the actual lock state and exposure compensation value recorded per frame and flag any frame where they drifted from the session's chosen baseline.

## The data model

```kotlin
data class FrameHealth(
    val frameId: String,
    val blurScore: Double,
    val aeLocked: Boolean,
    val awbLocked: Boolean,
    val exposureCompensationIndex: Int,
    val surfaceId: String
)

data class HealthThresholds(
    val minBlurScore: Double = 120.0,
    val minObservationsPerSurface: Int = 3,
    val warnObservationsPerSurface: Int = 5,
    val expectedExposureCompensationIndex: Int = 0
)

sealed class CheckResult {
    data class Pass(val summary: String) : CheckResult()
    data class Warn(val reasons: List<String>) : CheckResult()
    data class Fail(val reasons: List<String>) : CheckResult()
}
```

`minBlurScore` defaults to a value in the same neighborhood as PyImageSearch's worked example, but it is a constructor parameter precisely because that source is explicit that the number needs per-dataset tuning rather than being treated as gospel. `minObservationsPerSurface` defaults to COLMAP's documented hard minimum of three; `warnObservationsPerSurface` is a softer target above that floor, since the tutorial's own guidance is "more is better" without giving an exact upper number.

## The fusion pass

```kotlin
class CaptureHealthCheck(private val thresholds: HealthThresholds) {

    fun evaluate(frames: List<FrameHealth>, coverageBySurface: Map<String, Int>): CheckResult {
        val failReasons = mutableListOf<String>()
        val warnReasons = mutableListOf<String>()

        val blurryFrames = frames.filter { it.blurScore < thresholds.minBlurScore }
        if (blurryFrames.isNotEmpty()) {
            val ratio = blurryFrames.size.toDouble() / frames.size
            if (ratio > 0.15) {
                failReasons.add("${blurryFrames.size} of ${frames.size} frames scored below blur threshold ${thresholds.minBlurScore}")
            } else {
                warnReasons.add("${blurryFrames.size} frames are borderline sharp, review before ending scan")
            }
        }

        val underCovered = coverageBySurface.filter { it.value < thresholds.minObservationsPerSurface }
        if (underCovered.isNotEmpty()) {
            failReasons.add("Surfaces below the ${thresholds.minObservationsPerSurface}-image minimum: ${underCovered.keys.joinToString()}")
        }
        val thinlyCovered = coverageBySurface.filter {
            it.value in thresholds.minObservationsPerSurface until thresholds.warnObservationsPerSurface
        }
        if (thinlyCovered.isNotEmpty()) {
            warnReasons.add("Surfaces at the coverage floor, more angles recommended: ${thinlyCovered.keys.joinToString()}")
        }

        val exposureDrift = frames.filter {
            !it.aeLocked || !it.awbLocked || it.exposureCompensationIndex != thresholds.expectedExposureCompensationIndex
        }
        if (exposureDrift.isNotEmpty()) {
            val ratio = exposureDrift.size.toDouble() / frames.size
            if (ratio > 0.10) {
                failReasons.add("${exposureDrift.size} frames show AE/AWB lock or exposure-compensation drift from the session baseline")
            } else {
                warnReasons.add("${exposureDrift.size} frames drifted from locked exposure, likely near room transitions")
            }
        }

        return when {
            failReasons.isNotEmpty() -> CheckResult.Fail(failReasons)
            warnReasons.isNotEmpty() -> CheckResult.Warn(warnReasons)
            else -> CheckResult.Pass("All ${frames.size} frames passed blur, coverage, and exposure checks")
        }
    }
}
```

The exposure drift check is the piece most specific to this pipeline's assumptions. The operator locks AE and AWB at the start of a room to keep every frame's brightness and color temperature consistent, because auto white balance is documented to visibly drift frame to frame under mixed or indoor lighting since it re-estimates color temperature independently on every shot (Fstoppers, on Kelvin presets vs. AWB consistency). If a later frame in the same room shows `aeLocked = false` or a different `exposureCompensationIndex` than the session's baseline, that is a strong signal the operator's thumb bumped a control, or the app silently re-armed auto-exposure, mid-room. Catching that before upload matters more than it looks: COLMAP's own tutorial names inconsistent illumination as something to avoid, alongside overlap and texture, as one of its core capture recommendations.

Note the asymmetry in how AE/AWB lock state is read. Android's documentation is explicit that a `CaptureResult`'s reported lock state can lag the actual in-flight request state, because the pipeline queues ahead (Android Developers - CaptureRequest reference). The health check reads whatever lock state was stamped onto each frame's metadata at capture time rather than querying live camera state after the fact, since only the per-frame stamp reflects what that specific exposure actually used.

## Wiring it into the end-of-room flow

```kotlin
class RoomScanController(
    private val blurScorer: BlurScorer,
    private val coverageTracker: CoverageTracker,
    private val healthCheck: CaptureHealthCheck
) {
    fun onEndScanTapped(sessionFrames: List<CapturedFrame>): CheckResult {
        val frameHealth = sessionFrames.map { frame ->
            FrameHealth(
                frameId = frame.id,
                blurScore = blurScorer.score(frame.grayscaleBitmap),
                aeLocked = frame.captureResult.get(CaptureResult.CONTROL_AE_LOCK) ?: false,
                awbLocked = frame.captureResult.get(CaptureResult.CONTROL_AWB_LOCK) ?: false,
                exposureCompensationIndex = frame.captureResult.get(CaptureResult.CONTROL_AE_EXPOSURE_COMPENSATION) ?: 0,
                surfaceId = frame.surfaceId
            )
        }
        val coverageBySurface = coverageTracker.currentCounts()
        return healthCheck.evaluate(frameHealth, coverageBySurface)
    }
}
```

This is where the three sibling systems actually meet: the blur scorer runs per-frame on capture (detailed in its own volume), the coverage tracker accumulates counts as the operator walks (detailed in its own volume), and this controller pulls both into one evaluation the moment the operator taps "End Scan." A `Fail` result should block the button and show the reasons list directly, not a generic error. A `Warn` result should let the operator proceed but surface the specific reasons, since some warnings (a couple of borderline-sharp frames, a thinly covered corner) are recoverable in post-processing and are not worth blocking a whole room over.

## What this check cannot catch

Being honest about scope matters here. This on-device check has no way to detect scene-level problems that COLMAP's own FAQ names as gaps in its guidance, such as reflective or transparent surfaces, nor can it detect the kind of feature-matching failure that occurs on texture-poor or repetitive walls even when blur, coverage, and exposure all look fine (documented as a known SIFT weak point in mural-digitization and texture-poor matching literature). It is a necessary gate, not a guarantee of a clean reconstruction. The notes available for this shelf do not cover a validated numeric threshold for "texture-poor room needs tighter coverage than the 3-image floor," so this book will not invent one; if that gap matters to a specific building, treat COLMAP's minimum as the floor and lean toward the warn-threshold end of the range rather than assuming three is always enough.

Before the bundle leaves the device at all, though, one more step matters: packing the frames that passed this check into a transferable bundle.
