# Coding the Unlock-Set-EV-Relock Sequence in Kotlin

The capture app needs one small, boring piece of logic to get exposure right on every frame: unlock auto-exposure, nudge the EV compensation, relock, then shoot. Get the sequencing wrong and you either shoot on stale settings or you shoot mid-transition, before the new exposure has actually taken hold. This book turns that sequence into a single Kotlin class with an explicit state machine, so it can be unit tested without a physical camera and reused unchanged from the operator's capture activity.

The companion volume "The Unlock-Set-EV-Relock Dance" covers why this three-step sequence exists and what goes wrong when a step is skipped. "Implementing AE Lock and a Fixed Metering Region in Camera2" covers the metering-region half of exposure control. This book is narrower: given that AE lock and EV compensation are both first-class Camera2 controls, how do you wire the transition between them into code you'd trust in a solo operator's build.

## What the Camera2 API actually gives you

Two `CaptureRequest` keys do the work. `CONTROL_AE_LOCK` is a boolean: "whether auto-exposure (AE) is currently locked to its latest calculated values" (Android CaptureRequest reference, mirrored at the Microsoft Learn javadoc copy). `CONTROL_AE_EXPOSURE_COMPENSATION` is an integer step index that nudges the AE algorithm's own metering, typically within a device-reported range around -3 to +3 EV steps queried from camera characteristics (Android CaptureRequest reference).

Two details from the notes matter for sequencing correctness. First, because the camera device pipelines in-flight requests, the settings that end up locked don't necessarily match the settings in the most recent `CaptureResult` you received, since further captures and AE updates can occur before that result is delivered (Android CaptureRequest reference). That's the reason a naive "set lock, immediately shoot" call is unsafe. Second, the Microsoft Learn javadoc mirror cross-links `CONTROL_AE_LOCK` to `CONTROL_AE_EXPOSURE_COMPENSATION` and `CONTROL_AE_MODE` as distinct, separately configured controls, not a single combined knob, confirming the unlock/set/relock choreography is intentional rather than a Camera2 quirk to work around.

## The state machine

Model the sequence as an explicit enum-backed state machine instead of a pile of booleans. Four states cover it: `Idle`, `Unlocked`, `EvApplied`, `Locked`. Only specific transitions are legal, and the class throws rather than silently no-ops if you call a step out of order. That's the property that makes it testable: a unit test can assert both the happy path and the illegal-transition path without touching real hardware.

```kotlin
package orbit.capture.exposure

import android.hardware.camera2.CaptureRequest
import android.hardware.camera2.CaptureResult
import android.hardware.camera2.CameraCaptureSession
import android.hardware.camera2.CameraCharacteristics
import android.util.Range

enum class ExposureState { IDLE, UNLOCKED, EV_APPLIED, LOCKED }

class IllegalExposureTransition(message: String) : IllegalStateException(message)

interface RepeatingRequestIssuer {
    fun issue(builder: CaptureRequest.Builder, onResult: (CaptureResult) -> Unit)
}

class UnlockSetEvRelockSequencer(
    private val requestBuilder: CaptureRequest.Builder,
    private val issuer: RepeatingRequestIssuer,
    private val evRange: Range<Int>,
) {
    var state: ExposureState = ExposureState.LOCKED
        private set

    fun unlock(onLockConfirmed: (CaptureResult) -> Unit) {
        check(state == ExposureState.LOCKED || state == ExposureState.IDLE) {
            "unlock() called from $state; expected LOCKED or IDLE"
        }
        requestBuilder.set(CaptureRequest.CONTROL_AE_LOCK, false)
        issuer.issue(requestBuilder) { result ->
            state = ExposureState.UNLOCKED
            onLockConfirmed(result)
        }
    }

    fun setEv(steps: Int, onApplied: (CaptureResult) -> Unit) {
        if (state != ExposureState.UNLOCKED) {
            throw IllegalExposureTransition("setEv() requires UNLOCKED, was $state")
        }
        val clamped = steps.coerceIn(evRange.lower, evRange.upper)
        requestBuilder.set(CaptureRequest.CONTROL_AE_EXPOSURE_COMPENSATION, clamped)
        issuer.issue(requestBuilder) { result ->
            state = ExposureState.EV_APPLIED
            onApplied(result)
        }
    }

    fun relock(onLocked: (CaptureResult) -> Unit) {
        if (state != ExposureState.EV_APPLIED) {
            throw IllegalExposureTransition("relock() requires EV_APPLIED, was $state")
        }
        requestBuilder.set(CaptureRequest.CONTROL_AE_LOCK, true)
        issuer.issue(requestBuilder) { result ->
            state = ExposureState.LOCKED
            onLocked(result)
        }
    }
}
```

The `evRange` comes from `CameraCharacteristics.CONTROL_AE_COMPENSATION_RANGE`, queried once per camera at session setup; clamping against it here means a caller can never push an out-of-range EV value into the builder by mistake.

## Why the issuer is an interface, not `CameraCaptureSession` directly

`CameraCaptureSession.setRepeatingRequest()` is fine for production, but it is also the thing that makes this class impossible to unit test without an instrumented device, because Android's real Camera2 classes are backed by native code and cannot be constructed or mocked in a plain JVM test. Wrapping the one method the sequencer actually needs, `issue(builder, onResult)`, behind `RepeatingRequestIssuer` gets you a seam. Production code implements it against a real `CameraCaptureSession`:

```kotlin
class SessionRepeatingRequestIssuer(
    private val session: CameraCaptureSession,
) : RepeatingRequestIssuer {
    override fun issue(builder: CaptureRequest.Builder, onResult: (CaptureResult) -> Unit) {
        session.setRepeatingRequest(
            builder.build(),
            object : CameraCaptureSession.CaptureCallback() {
                override fun onCaptureCompleted(
                    session: CameraCaptureSession,
                    request: CaptureRequest,
                    result: android.hardware.camera2.TotalCaptureResult,
                ) {
                    onResult(result)
                }
            },
            null,
        )
    }
}
```

A test fake implements the same interface with no camera at all:

```kotlin
class FakeIssuer : RepeatingRequestIssuer {
    var lastBuilder: CaptureRequest.Builder? = null
    override fun issue(builder: CaptureRequest.Builder, onResult: (CaptureResult) -> Unit) {
        lastBuilder = builder
        onResult(mockResult())
    }
    private fun mockResult(): CaptureResult =
        throw NotImplementedError("stub for the specific assertions a test needs")
}
```

The notes used to build this book don't cover Android instrumentation test frameworks (Robolectric, `CameraCharacteristics` fakes, or similar), so the concrete `mockResult()` body above is deliberately left as a stub rather than a fabricated recommendation: whatever your project already uses to fake a `CaptureResult` slots in there.

## Testing the transitions without a camera

The state machine's whole value is that illegal call orders fail loudly and immediately, in a plain JVM test, with no emulator:

```kotlin
class UnlockSetEvRelockSequencerTest {
    private fun sequencer(): UnlockSetEvRelockSequencer {
        val builder = mockCaptureRequestBuilder()
        val issuer = FakeIssuer()
        return UnlockSetEvRelockSequencer(builder, issuer, Range(-3, 3))
    }

    fun `setEv before unlock throws`() {
        val seq = sequencer()
        try {
            seq.setEv(2) {}
            error("expected IllegalExposureTransition")
        } catch (e: IllegalExposureTransition) {
            // expected: setEv() requires UNLOCKED, was LOCKED
        }
    }

    fun `full sequence reaches LOCKED`() {
        val seq = sequencer()
        seq.unlock {}
        seq.setEv(1) {}
        seq.relock {}
        assert(seq.state == ExposureState.LOCKED)
    }
}
```

`mockCaptureRequestBuilder()` is left unimplemented here for the same reason as `mockResult()` above: the notes support the Camera2 field semantics, not a specific Android test-mocking recipe, and this book won't invent one. Whatever mocking library the surrounding project already pulls in (Mockito, MockK, or a hand-rolled fake `CaptureRequest.Builder`) is the right place for that single function, not a new dependency introduced by this sequencer.

## Wiring it into a capture loop

In practice the sequencer sits between "operator walked to next position" and "shoot the frame." The capture loop calls `unlock`, waits for the confirming `CaptureResult`, calls `setEv` with whatever compensation the current room calls for, waits again, calls `relock`, and only then triggers the still capture. "Capturing Frame Metadata: ISO, Shutter, EV, Timestamp" covers what to read back out of that final locked `CaptureResult` and log alongside the JPG, which is the natural next step once this sequencer reports `LOCKED`.

Keeping the three transitions as named methods rather than one combined `applyExposure(ev)` call is the deliberate design choice here: each step corresponds to exactly one `CaptureRequest` mutation and one confirming callback, so a bug in sequencing shows up as a specific `IllegalExposureTransition` message rather than a silently wrong exposure on the next frame.
