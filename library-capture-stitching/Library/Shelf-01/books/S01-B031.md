# Implementing AE Lock and a Fixed Metering Region in Camera2

Orbit Capture asks one thing of the camera that stock camera apps actively fight: hold still. A solo operator picks a mid-tone reference at the start of a room, exposes for it, and then needs every frame shot in that room to keep the same brightness while walking past windows, dark corners, and light fixtures. Auto-exposure recalculating on every frame is the enemy here, because COLMAP and gsplat both assume the photometric conditions of a scene are stable enough that the same wall doesn't get brighter and darker across overlapping frames. This book codes the mechanism that pins exposure in place: `CaptureRequest.CONTROL_AE_LOCK`, combined with a metering region set once at the start of the room rather than left to roam across the frame.

This volume is deliberately narrow. It does not explain what AE lock does and doesn't freeze conceptually (that's "AE Lock: What It Freezes and What It Doesn't"), it does not build the capture session around it ("Camera2 Capture Session Basics for a Locked-Exposure App"), and it does not walk through the unlock-set-EV-relock sequence used when the operator wants to deliberately change exposure ("Coding the Unlock-Set-EV-Relock Sequence in Kotlin"). What it does is show the actual Kotlin needed to set a fixed metering region, lock AE against it, and keep that lock alive across repeated captures in a `CameraCaptureSession`.

## What CONTROL_AE_LOCK actually is

Per Android's own CaptureRequest reference, `CONTROL_AE_LOCK` "determines whether auto-exposure is currently locked to its latest calculated values." The reference adds an important caveat: because the camera device pipelines in-flight requests, the settings that end up locked don't necessarily match the settings in the most recent `CaptureResult` you've received, since further captures and AE updates can occur before that result is delivered to your app. In practice this means locking is not instantaneous relative to what you're looking at on screen; you should let AE converge and settle before you flip the lock, not lock the instant you see a result you like.

The Microsoft Learn mirror of the same Android javadoc (CC-BY 2.5 from AOSP) confirms the canonical wording, "Whether auto-exposure (AE) is currently locked to its latest calculated values," and cross-links `CONTROL_AE_LOCK` to `CONTROL_AE_EXPOSURE_COMPENSATION`, `CONTROL_AE_MODE`, and `CONTROL_AE_PRECAPTURE_TRIGGER` as distinct, separately configured controls. That distinction matters for this book: the lock is a boolean freeze, not a value-setting mechanism. It freezes whatever the AE algorithm last converged on. If you want to bias exposure before locking, that's a separate field (exposure compensation), which is out of scope here and belongs to the relock sequence volume.

## Why the metering region has to be fixed, not roaming

AE lock alone freezes exposure, but it doesn't control what the algorithm was measuring against right before you locked it. If the metering region defaults to the center of the frame, panning the phone before locking means you lock against whatever happened to be centered a moment ago, not against the mid-tone reference the operator deliberately chose. Orbit Capture's operator workflow is to point at a reference patch (a wall, a mid-gray card, a hand), let AE settle, and lock. For that gesture to be repeatable and predictable, the metering region needs to be set explicitly to a small area (ideally where the reference sits in frame) before the lock is engaged, not left as an unconstrained full-frame average.

One gap worth stating plainly: the research notes for this shelf confirm `CONTROL_AE_REGIONS` behavior mainly indirectly, through CameraX's documentation of how CameraX itself converts `MeteringPoint` objects into Camera2 `MeteringRectangle`s under the hood, rather than through the raw Camera2 reference page's own field-level wording. The code below follows the standard Camera2 `MeteringRectangle` pattern, but if you are implementing this in raw Camera2 (not CameraX) for production, verify `CaptureRequest.CONTROL_AE_REGIONS` region-count and weighting behavior against the SDK reference or source directly rather than relying solely on this description.

## Building a fixed metering region

`MeteringRectangle` takes pixel coordinates within the sensor's active array, plus a weight. Camera2 reports how many AE regions a device supports via `CONTROL_MAX_REGIONS_AE` in `CameraCharacteristics`; a value of 0 means the device doesn't support custom AE metering regions at all, and you fall back to whatever the device's default full-frame metering does.

```kotlin
import android.graphics.Rect
import android.hardware.camera2.CameraCharacteristics
import android.hardware.camera2.CameraDevice
import android.hardware.camera2.CaptureRequest
import android.hardware.camera2.params.MeteringRectangle
import kotlin.math.roundToInt

class FixedExposureRegion(
    private val characteristics: CameraCharacteristics
) {
    private val activeArray: Rect =
        characteristics.get(CameraCharacteristics.SENSOR_INFO_ACTIVE_ARRAY_SIZE)
            ?: error("Camera characteristics missing active array size")

    private val maxAeRegions: Int =
        characteristics.get(CameraCharacteristics.CONTROL_MAX_REGIONS_AE) ?: 0

    fun supportsCustomRegion(): Boolean = maxAeRegions > 0

    fun regionAt(normalizedCenterX: Float, normalizedCenterY: Float, normalizedSize: Float): MeteringRectangle {
        val halfW = (activeArray.width() * normalizedSize / 2f)
        val halfH = (activeArray.height() * normalizedSize / 2f)
        val centerX = activeArray.left + activeArray.width() * normalizedCenterX
        val centerY = activeArray.top + activeArray.height() * normalizedCenterY

        val left = (centerX - halfW).roundToInt().coerceIn(activeArray.left, activeArray.right)
        val top = (centerY - halfH).roundToInt().coerceIn(activeArray.top, activeArray.bottom)
        val right = (centerX + halfW).roundToInt().coerceIn(left + 1, activeArray.right)
        val bottom = (centerY + halfH).roundToInt().coerceIn(top + 1, activeArray.bottom)

        return MeteringRectangle(left, top, right - left, bottom - top, MeteringRectangle.METERING_WEIGHT_MAX)
    }
}
```

`normalizedSize` around `0.15f` to `0.2f` gives a metering patch roughly the size of a palm held up to the lens at typical operator arm's length, small enough to isolate the chosen reference tone from the rest of the frame. `METERING_WEIGHT_MAX` gives that single region full weight since only one region is being used; if a device reports `maxAeRegions` greater than one and you wanted multiple weighted regions, you'd size the array of `MeteringRectangle` accordingly, but Orbit Capture's single-reference-patch workflow only ever needs one.

## Wiring the region and the lock into a capture request

The sequence that matters is: set the region, submit a repeating request with AE unlocked so the algorithm actually converges against that region, then flip the lock on and resubmit. Locking before the region takes effect just freezes whatever the previous region (or the default) already converged on.

```kotlin
import android.hardware.camera2.CameraCaptureSession
import android.hardware.camera2.CaptureRequest
import android.hardware.camera2.params.MeteringRectangle
import android.os.Handler

class AeLockController(
    private val session: CameraCaptureSession,
    private val requestBuilder: CaptureRequest.Builder,
    private val callbackHandler: Handler
) {
    fun startMeteringOnRegion(region: MeteringRectangle) {
        requestBuilder.set(CaptureRequest.CONTROL_AE_REGIONS, arrayOf(region))
        requestBuilder.set(CaptureRequest.CONTROL_AE_LOCK, false)
        session.setRepeatingRequest(requestBuilder.build(), null, callbackHandler)
    }

    fun lockExposure() {
        requestBuilder.set(CaptureRequest.CONTROL_AE_LOCK, true)
        session.setRepeatingRequest(requestBuilder.build(), null, callbackHandler)
    }

    fun isLockedRequest(): CaptureRequest = requestBuilder.build()
}
```

Between `startMeteringOnRegion` and `lockExposure`, the operator needs a brief settle window, typically driven by watching `CaptureResult.CONTROL_AE_STATE` reach `CONTROL_AE_STATE_CONVERGED` via the session's capture callback, rather than a fixed timer, since convergence speed depends on scene brightness and how far off the previous exposure was. That callback wiring and the full capture-session lifecycle around it belong to "Camera2 Capture Session Basics for a Locked-Exposure App"; this volume assumes a session and repeating request already exist and focuses only on the region and lock fields themselves.

Once `lockExposure()` has been called, every subsequent `capture()` or `setRepeatingRequest()` call built from the same `requestBuilder` keeps `CONTROL_AE_LOCK` set to `true` and carries the same `CONTROL_AE_REGIONS` value forward, because `CaptureRequest.Builder` retains previously set fields until explicitly changed. This is what lets the operator walk the room shooting still after still without the exposure drifting: each still-capture request inherits the locked state from the builder rather than needing the lock re-applied per shot.

## The AWB question this book intentionally leaves open

Android's documentation on `CONTROL_AE_LOCK` and the related `CONTROL_AWB_LOCK` behavior notes that auto-white-balance and auto-focus behavior when AE is off is device-dependent, and Android's own guidance is to either set AWB and AF to OFF or lock them explicitly before turning AE off, specifically to get consistent behavior across different devices. Locking AE without also making a deliberate decision about white balance can leave color temperature free to drift frame to frame even while brightness stays pinned, which undermines the mid-tone consistency this book is coding for. This volume codes only the AE side; a fixed-Kelvin or locked-AWB companion is a natural pairing but is out of this book's scope and is not covered here.

## Practical notes for the fixed-region workflow

A metering region sized too small (a few percent of the frame) risks landing entirely on a shadow or a texture edge in the reference patch and gives the AE algorithm too little area to average, producing a less stable convergence than a modestly larger patch. A region sized too large starts pulling in whatever's around the reference tone, defeating the point of picking a deliberate mid-tone reference in the first place. There is no cited numeric ideal for this specific tradeoff in the research for this shelf; treat the 0.15-0.2 normalized size above as a starting point to tune against your own device and lighting rather than a fixed constant.
