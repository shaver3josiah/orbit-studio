# Reading and Applying AWB Lock State via Camera2

An Orbit Capture session lives or dies on color consistency. If the phone's auto white balance is free to drift from frame to frame while the operator walks a room, COLMAP gets a set of photos that disagree about what "white" means, and the eventual Gaussian splat inherits every one of those disagreements as color noise baked into the splats. The fix most capture tools reach for is `CONTROL_AWB_LOCK`, and it is the right first move, but it is worth being precise about what that lock actually freezes, because it is not the same thing as choosing a color temperature.

## What CONTROL_AWB_LOCK actually does

The Camera2 javadoc for `CaptureRequest.CONTROL_AWB_LOCK` is blunt about it: "Whether auto-white balance (AWB) is currently locked to its latest calculated values" (Android Developers, CaptureRequest reference; mirrored at Microsoft Learn / Android javadoc mirror, CaptureRequest.ControlAwbLock). The operative phrase is "latest calculated values." AWB lock does not pin the sensor to daylight, or tungsten, or any deliberately chosen target. It freezes whatever the auto-algorithm happened to converge on at the moment you locked it. Point the camera at a warm wooden floor for a second before locking and you lock in whatever compensation AWB applied for that floor, not a neutral reference.

This matters for the capture workflow because the value being frozen is a function of scene content up to the lock moment, not a stable physical quantity chosen in advance. Two operators locking AWB in the same room, at different angles, a few seconds apart, can lock in two different color balances if the algorithm hadn't fully converged or if the framing differed enough to shift its estimate. The notes on this exact distinction are explicit: CONTROL_AWB_MODE is cross-referenced with CONTROL_AWB_LOCK in the Android reference "implying the lock freezes whatever value AWB last computed rather than pinning to any deliberately chosen white-balance target" (Microsoft Learn / Android javadoc mirror, CaptureRequest.ControlAwbLock).

## Setting and confirming the lock in Camera2

The pattern is a `CaptureRequest.Builder` field toggle, applied to a repeating preview request and then carried forward into the capture request used for each still:

```kotlin
class AwbLockController(private val session: CameraCaptureSession) {

    fun engageLock(previewBuilder: CaptureRequest.Builder) {
        previewBuilder.set(CaptureRequest.CONTROL_AWB_LOCK, true)
        session.setRepeatingRequest(previewBuilder.build(), captureCallback, backgroundHandler)
    }

    fun releaseLock(previewBuilder: CaptureRequest.Builder) {
        previewBuilder.set(CaptureRequest.CONTROL_AWB_LOCK, false)
        session.setRepeatingRequest(previewBuilder.build(), captureCallback, backgroundHandler)
    }

    private val captureCallback = object : CameraCaptureSession.CaptureCallback() {
        override fun onCaptureCompleted(
            session: CameraCaptureSession,
            request: CaptureRequest,
            result: TotalCaptureResult
        ) {
            val lockState = result.get(CaptureResult.CONTROL_AWB_STATE)
            val isLocked = lockState == CaptureResult.CONTROL_AWB_STATE_LOCKED
            onAwbStateChanged(isLocked)
        }
    }

    private fun onAwbStateChanged(isLocked: Boolean) {
        // surfaced to the capture UI so the operator sees lock status before shooting
    }
}
```

Two things in that snippet deserve emphasis rather than inline comments. First, setting `CONTROL_AWB_LOCK` on the builder is a request, not a guarantee that arrives instantly; the camera device pipelines in-flight requests, so the values that actually end up locked don't necessarily match what was visible in the most recent preview frame you saw on screen. The Android CaptureRequest reference makes this same pipelining point about `CONTROL_AE_LOCK` explicitly, and it applies analogously to AWB: "because the camera device pipelines in-flight requests, the settings that end up locked don't necessarily match the settings in the most recent CaptureResult received, since further captures/AE updates can occur before that result is delivered" (Android Developers, CaptureRequest reference). Practically, this means an operator's capture tool should not assume the lock took effect on the exact frame where the toggle was flipped. It should read back `CONTROL_AWB_STATE` from the `CaptureResult` stream, as the callback above does, and only start treating subsequent frames as color-locked once `CONTROL_AWB_STATE_LOCKED` actually appears.

Second, the lock state is read from `CaptureResult`, not assumed from the request you sent. This is the same request/result asymmetry that governs frame metadata generally, and it is worth cross-referencing the companion volume on capturing frame metadata (ISO, shutter, EV, timestamp) for the broader pattern of reading confirmed state back off results rather than trusting requested values.

## Where a device-dependent gap shows up

The notes flag one more wrinkle worth building around defensively: Android's own guidance is that AWB and AF behavior when AE is off is device-dependent, and the documented mitigation is to explicitly set AWB (and AF) to OFF or lock them before turning AE off, specifically to get consistent behavior across different phones (Android Developers, CaptureRequest reference). An Orbit Capture tool that locks AE and AWB together as a single "freeze this frame's exposure and color" gesture should sequence the locks so AWB is settled before AE gets touched, rather than assuming the two locks are independent no-ops on every device. This is also where the sibling volume on implementing AE lock and a fixed metering region in Camera2 becomes directly relevant, since AE lock shares the exact same pipelining-lag caveat and the exact same "read the result, don't trust the request" discipline described above.

## Where a true fixed-Kelvin mode would diverge

This is the part of the scope that has to be stated as an honest boundary rather than papered over: Camera2 has no direct "set white balance to N kelvin" control. `CONTROL_AWB_MODE` is limited to a fixed preset list, specifically `INCANDESCENT`, `FLUORESCENT`, `WARM_FLUORESCENT`, `DAYLIGHT`, `CLOUDY_DAYLIGHT`, `TWILIGHT`, and `SHADE`, and each preset targets a specific reference illuminant rather than an arbitrary tunable color temperature (Android Developers, CameraMetadata / CONTROL_AWB_MODE preset values). `CONTROL_AWB_MODE_INCANDESCENT` approximates CIE standard illuminant A, and `CONTROL_AWB_MODE_FLUORESCENT` approximates CIE standard illuminant F2, both fixed physical references, not sliders.

The practical divergence from AWB lock is this: choosing `CONTROL_AWB_MODE_DAYLIGHT` for a session pins every frame to the same named illuminant regardless of what the algorithm would have auto-estimated, which is deterministic and repeatable across a whole building walk, but it is also only an approximation of the room's actual lighting unless the room genuinely matches that preset's reference illuminant. AWB lock, by contrast, matches whatever the room actually looks like at the moment of lock, but that match is not repeatable if you re-lock in a different corner of the same room. A true fixed-Kelvin strategy on Android is therefore necessarily an approximation via the nearest preset mode, and the notes are explicit that this is a documented gap: "this means a true 'fixed-Kelvin' white balance strategy on Android is necessarily an approximation via the nearest preset mode, distinct from AWB lock" (Android Developers, CameraMetadata / CONTROL_AWB_MODE preset values). For the full tradeoff between these two strategies, including which one an Orbit Capture operator should actually pick per session, see the sibling volume "AWB Lock vs. a True Fixed-Kelvin White Balance."

## A minimal state machine for the capture tool

Putting the pieces together, the capture tool's per-room sequence looks like this: enter the room, let AWB run unlocked in preview for a beat so it can converge on the room's actual lighting, engage the lock once `CONTROL_AWB_STATE_LOCKED` is confirmed in a result callback (not merely after sending the request), then shoot the overlapping still sequence with the same locked `CaptureRequest.Builder` reused for every capture. Only release the lock, and let AWB re-converge, when moving to a room with meaningfully different lighting. This is a straightforward toggle-and-verify loop, not a full preset system, and building a `CONTROL_AWB_MODE` preset selector on top of it is a separate, larger feature that belongs to the fixed-Kelvin volume rather than this one.
