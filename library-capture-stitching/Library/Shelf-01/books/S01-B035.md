# On-Device Laplacian-Variance Blur Scoring in Kotlin

The sibling volume "Estimating Capture Blur Risk with a Laplacian-Variance Score" works out the math on the desktop, in Python, against a folder of JPGs after the fact. This book ports the same idea into the capture app itself: a Kotlin routine that runs on the phone, right after the shutter fires, before the operator has even lowered the camera from their eye. The goal is not a better blur metric. It is the same metric, moved earlier in the timeline, so a blurry frame can be caught while the operator is still standing in the room instead of three days later when a COLMAP job stalls on missing correspondences.

## The metric, unchanged

Per "Blur detection with OpenCV (variance of Laplacian)" (PyImageSearch), the underlying technique is one line in Python: convolve a grayscale image with the Laplacian kernel, then take the variance of the response. Sharp images produce high variance because they have abundant edges and rapid intensity changes; blurry images produce low variance because edges have been smeared away. The source's own worked example used a threshold of 100.0, with blurry test images scoring 64-83 and sharp ones scoring 200-1000+, and it explicitly warns that this exact number is subjective to image content and needs per-dataset tuning rather than being treated as universal. That caveat matters more on-device than off, because a phone sees far more scene variety in one session (a textured brick wall, then a blank hallway ceiling) than a curated desktop test set does.

The reason the Python reference uses `CV_64F` (64-bit float) rather than 8-bit output is that Laplacian derivatives can be negative, and an unsigned 8-bit buffer would clip those values, corrupting the variance calculation. That constraint carries straight over to Kotlin: whatever accumulator holds the convolution response has to tolerate negative numbers and enough range not to overflow on repeated multiplication, so this port uses `Double` throughout rather than trying to stay in integer math for speed.

## Why this is a manual port, not an OpenCV call

The obvious move is to add the OpenCV Android SDK and call `Imgproc.Laplacian()` plus `Core.meanStdDev()` to get the variance, mirroring the Python call almost verbatim. That is a legitimate choice if the app already ships OpenCV for other reasons. But this book's scope is a routine that runs after *every* shot, on a phone that a solo operator is holding for an hour-long walk through a building, and pulling in the full OpenCV native library for a single 3x3 convolution and a variance is a heavy dependency for a light job. The notes contain no OpenCV Android benchmark to lean on either, so this book does not claim a performance number for it. What the notes do support directly is the plain formula: Laplacian kernel, then variance. That is small enough to write by hand against the luminance plane CameraX already hands you, with no new dependency at all.

```kotlin
import androidx.camera.core.ImageProxy
import kotlin.math.min

object LaplacianBlurScore {

    // 4-neighbor discrete Laplacian: same kernel shape as cv2's default
    // ([[0,1,0],[1,-4,1],[0,1,0]]), applied to 8-bit luma, per
    // "Blur detection with OpenCV (variance of Laplacian)" (PyImageSearch).
    fun score(image: ImageProxy, maxSamples: Int = 480 * 640): Double {
        val yPlane = image.planes[0]
        val buffer = yPlane.buffer
        val rowStride = yPlane.rowStride
        val pixelStride = yPlane.pixelStride
        val width = image.width
        val height = image.height

        // Downsample stride so full-res 12MP+ frames stay cheap; the
        // variance of a Laplacian response is stable under uniform
        // subsampling for this purpose, only the absolute scores need
        // consistent stride across a shoot to stay comparable.
        val stride = sampleStride(width, height, maxSamples)

        var sum = 0.0
        var sumSq = 0.0
        var count = 0

        fun luma(x: Int, y: Int): Int {
            val idx = y * rowStride + x * pixelStride
            return buffer[idx].toInt() and 0xFF
        }

        var y = stride
        while (y < height - stride) {
            var x = stride
            while (x < width - stride) {
                val center = luma(x, y)
                val lap = (luma(x - stride, y) + luma(x + stride, y) +
                        luma(x, y - stride) + luma(x, y + stride) -
                        4 * center).toDouble()
                sum += lap
                sumSq += lap * lap
                count++
                x += stride
            }
            y += stride
        }

        if (count == 0) return 0.0
        val mean = sum / count
        return (sumSq / count) - (mean * mean)
    }

    private fun sampleStride(width: Int, height: Int, maxSamples: Int): Int {
        val totalPixels = width * height
        val ratio = totalPixels.toDouble() / maxSamples
        return min(8, Math.ceil(Math.sqrt(ratio)).toInt()).coerceAtLeast(1)
    }
}
```

Two things in that routine are direct, deliberate parallels to the Python reference, and one is a departure worth naming honestly.

The parallel: the kernel is the same 4-neighbor Laplacian (`[[0,1,0],[1,-4,1],[0,1,0]]`) that OpenCV's default `ksize=1` Laplacian applies, and the final step is exactly variance of that response, matching `cv2.Laplacian(image, cv2.CV_64F).var()` term for term. The accumulator is `Double` for the same reason the source insists on `CV_64F`, negative derivative values must not clip.

The departure: this reads directly from the YUV `ImageProxy` that CameraX's `ImageAnalysis` use case already delivers per frame, using plane 0 (luma) directly, rather than decoding a JPEG and converting to grayscale the way the Python pipeline does against a saved file. That is the correct on-device move, since CameraX exposes luma as a first-class plane and decoding the just-encoded JPEG back to bitmap only to reconvert it to grayscale would be pure waste on every single shot. It also means this routine has to run in the `ImageAnalysis.Analyzer` callback, not as a post-hoc pass over the JPEG on disk, which changes when in the shot lifecycle it fires (see below).

## Where it runs, and the threshold problem it inherits

The notes only support one calibration point from an outside source: the PyImageSearch worked example's threshold of 100.0, with blurry examples in the 64-83 range and sharp ones at 200 and up, and its explicit warning that this number depends on scene content. Nothing in the notes gives a validated indoor-photogrammetry-specific threshold, so this book will not invent one. What it can responsibly give is the shape of the decision, wired for a configurable cutoff rather than a hardcoded constant:

```kotlin
data class BlurVerdict(val score: Double, val isBlurry: Boolean, val threshold: Double)

class BlurGate(private val threshold: Double = 100.0) {
    // ponytail: single global threshold, no per-scene auto-tuning;
    // revisit if a texture-poor room (blank ceiling, plain drywall)
    // starts tripping false positives in practice.
    fun evaluate(image: ImageProxy): BlurVerdict {
        val score = LaplacianBlurScore.score(image)
        return BlurVerdict(score, score < threshold, threshold)
    }
}
```

That single-threshold shortcut is named deliberately rather than hidden, because the honest answer, per the notes, is that no source here validates one universal cutoff for indoor phone capture. A texture-poor surface (a blank ceiling, a plain wall) will naturally score lower on this metric even in perfect focus, simply because there is less edge content to differentiate. That is the same tension the CIPA 3x3 Rules and Pix4D guidance name for overlap requirements in low-texture scenes, just showing up here as a scoring artifact instead of a coverage one, and it is a limit worth carrying forward rather than papering over with a false sense of precision.

Wiring `BlurGate` into the actual shot loop, deciding whether to flag a frame live and whether to prompt a reshoot, is the job of the next two sibling volumes in this shelf: "Flagging and Triggering a Reshoot Mid-Session" covers the in-session UI and retry flow once a frame is scored, and "Building a Pre-Upload Capture Health Check on Device" covers running this same score as a batch sweep over the whole JPG bundle before it ever leaves the phone for the COLMAP machine. This book's job stops at producing a trustworthy number, cheaply, on every frame.

## A self-check worth keeping

Non-trivial logic here is the convolution and stride math, and it is worth pinning with one assertion-based check rather than trusting it by eye:

```kotlin
fun main() {
    // Uniform gray field: no edges anywhere, Laplacian response should be
    // ~0 everywhere, so variance should be ~0.
    val flat = DoubleArray(100) { 0.0 }
    val flatMean = flat.average()
    val flatVar = flat.map { (it - flatMean) * (it - flatMean) }.average()
    assert(flatVar < 1e-6) { "flat field should score near zero" }

    // A checkerboard-like alternating signal should produce large variance
    // relative to a flat field, standing in for a sharp, high-edge frame.
    val sharp = DoubleArray(100) { i -> if (i % 2 == 0) 0.0 else 255.0 }
    val sharpMean = sharp.average()
    val sharpVar = sharp.map { (it - sharpMean) * (it - sharpMean) }.average()
    assert(sharpVar > flatVar) { "alternating field should score higher than flat" }

    println("blur score sanity check passed")
}
```

This is not a test of `LaplacianBlurScore.score()` end to end against a real `ImageProxy` (that needs an instrumented Android test with a fixture image, out of scope here), but it does pin the one property the whole routine depends on: a field with no edges scores near zero, and a field with strong edges scores meaningfully higher. If a future refactor of the stride or accumulator math breaks that ordering, this fails immediately.
