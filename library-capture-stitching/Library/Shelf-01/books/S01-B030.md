# Camera2 Capture Session Basics for a Locked-Exposure App

Every later book in this shelf assumes a working Camera2 session already exists underneath it. Before you can lock exposure, hold a fixed metering region, or step a state machine through a room-by-room shoot, you need the plumbing that opens a camera, wires up a capture session, and gets frames flowing into a still-capture pipeline. This book builds exactly that plumbing and nothing more. Auto-exposure lock and the metering region live in the sibling book "Implementing AE Lock and a Fixed Metering Region in Camera2"; the higher-level per-room workflow lives in "Building the Room-by-Room Session State Machine." This one is the foundation both of those sit on.

Camera2 is the deliberate choice here over CameraX. CameraX is documented by Google as prioritizing compatibility and ease of use over granular low-level access, and for custom capture templates or advanced sensor control it points back to Camera2 as the lower-level alternative it is itself built on (Android Developers, CameraX Configuration Options). An Orbit Capture session needs exactly that granular control: a fixed exposure and white balance held steady across dozens of overlapping frames in one room, which is the whole point of the pipeline described in "From Building to Bundle: The Shape of the Orbit Capture Pipeline." CameraX would get there through `FocusMeteringAction` and best-effort region support; Camera2 gets there by setting `CaptureRequest` keys directly and knowing exactly what each one does.

## The four pieces

A minimal Camera2 still-capture session has four moving parts: the `CameraManager` to enumerate and open a device, a `CameraDevice.StateCallback` to know when the device is actually ready, an `ImageReader` as the surface stills land on, and a `CameraCaptureSession` built from that surface to actually issue capture requests. Nothing here is exotic; it is the same skeleton every Camera2 tutorial uses, but it is worth having it complete and correct in one place since every later book calls into it.

```kotlin
class CaptureSessionManager(
    private val context: Context,
    private val backgroundHandler: Handler
) {
    private val cameraManager =
        context.getSystemService(Context.CAMERA_SERVICE) as CameraManager

    private var cameraDevice: CameraDevice? = null
    private var captureSession: CameraCaptureSession? = null
    private var imageReader: ImageReader? = null

    fun openBackCamera(onReady: () -> Unit, onError: (String) -> Unit) {
        val cameraId = cameraManager.cameraIdList.first { id ->
            val chars = cameraManager.getCameraCharacteristics(id)
            chars.get(CameraCharacteristics.LENS_FACING) == CameraCharacteristics.LENS_FACING_BACK
        }

        val chars = cameraManager.getCameraCharacteristics(cameraId)
        val map = chars.get(CameraCharacteristics.SCALER_STREAM_CONFIGURATION_MAP)!!
        val size = map.getOutputSizes(ImageFormat.JPEG).maxByOrNull { it.width * it.height }!!

        imageReader = ImageReader.newInstance(size.width, size.height, ImageFormat.JPEG, 2)

        if (ActivityCompat.checkSelfPermission(context, Manifest.permission.CAMERA)
            != PackageManager.PERMISSION_GRANTED
        ) {
            onError("Camera permission not granted")
            return
        }

        cameraManager.openCamera(cameraId, object : CameraDevice.StateCallback() {
            override fun onOpened(device: CameraDevice) {
                cameraDevice = device
                createSession(device, onReady, onError)
            }

            override fun onDisconnected(device: CameraDevice) {
                device.close()
                cameraDevice = null
            }

            override fun onError(device: CameraDevice, error: Int) {
                device.close()
                cameraDevice = null
                onError("Camera device error code $error")
            }
        }, backgroundHandler)
    }

    private fun createSession(
        device: CameraDevice,
        onReady: () -> Unit,
        onError: (String) -> Unit
    ) {
        val target = imageReader!!.surface
        device.createCaptureSession(
            listOf(target),
            object : CameraCaptureSession.StateCallback() {
                override fun onConfigured(session: CameraCaptureSession) {
                    captureSession = session
                    onReady()
                }

                override fun onConfigureFailed(session: CameraCaptureSession) {
                    onError("Capture session configuration failed")
                }
            },
            backgroundHandler
        )
    }
}
```

Two things in that listing matter more than they look. First, the `ImageReader` is created before the device is opened, and its surface is the only target passed to `createCaptureSession`. A session is bound to a fixed set of output surfaces for its whole life; you cannot add a preview surface later without tearing the session down and rebuilding it, so decide up front what this session needs to produce. For Orbit Capture that is just full-resolution JPEG stills, not a preview stream, since the operator is walking and shooting on locked exposure rather than composing shots.

Second, everything happens on a background `Handler`, not the main thread. Camera2 callbacks are documented to fire on whatever handler you pass, and `openCamera` will throw if you pass a handler tied to a thread with no looper running. A `HandlerThread` started once and reused for the whole capture session's lifetime is the standard pattern:

```kotlin
val cameraThread = HandlerThread("camera-bg").apply { start() }
val backgroundHandler = Handler(cameraThread.looper)
```

## Building the still-capture request

Once `onConfigured` fires, the session is live but idle. A still capture is a one-shot `CaptureRequest` built from the `TEMPLATE_STILL_CAPTURE` template, targeted at the `ImageReader` surface, and handed to `session.capture()`:

```kotlin
fun captureStill(onImageReady: (Image) -> Unit) {
    val device = cameraDevice ?: return
    val session = captureSession ?: return
    val reader = imageReader ?: return

    reader.setOnImageAvailableListener({ r ->
        r.acquireLatestImage()?.let(onImageReady)
    }, backgroundHandler)

    val requestBuilder = device.createCaptureRequest(CameraDevice.TEMPLATE_STILL_CAPTURE).apply {
        addTarget(reader.surface)
        set(CaptureRequest.CONTROL_MODE, CameraMetadata.CONTROL_MODE_AUTO)
    }

    session.capture(requestBuilder.build(), null, backgroundHandler)
}
```

`TEMPLATE_STILL_CAPTURE` biases the platform's default 3A (auto-exposure, auto-focus, auto-white-balance) behavior toward quality over speed, which is the right starting template for Orbit Capture even though the exposure and white balance will get locked down and overridden in the AE-lock book. This book deliberately leaves `CONTROL_MODE` on `CONTROL_MODE_AUTO` and does not touch `CONTROL_AE_LOCK` or `CONTROL_AWB_LOCK` at all. Those two keys, and why they need to be set together rather than independently, are the entire subject of "Implementing AE Lock and a Fixed Metering Region in Camera2." The one thing worth flagging here, because it explains why that next book exists: Android's own reference notes that AWB and AF behavior when AE is off is device-dependent, and its explicit recommendation is to set AWB/AF to off or lock them before turning AE off, specifically to get consistent behavior across different devices (Android Developers, CaptureRequest reference). A minimal session like this one cannot get that right by accident; it has to be done deliberately, one capture-request key at a time, which is exactly the next book's job.

One gap worth naming plainly rather than papering over: the research behind this shelf could only confirm the exact behavior of `CONTROL_AE_REGIONS` and `CONTROL_AWB_REGIONS` indirectly, through CameraX's documentation of how it converts metering points into those Camera2 fields, not from the Camera2 reference page's own wording on region weighting or maximum region counts. Anyone wiring up the fixed metering region in raw Camera2 should verify that field's exact semantics against the SDK reference or source directly before shipping it.

## Tearing down

A capture session and its device need to be closed in the right order, and need to happen off the calling thread's assumptions about lifecycle timing, typically in `onPause` or when the room-by-room state machine advances past the point where this room's camera is needed:

```kotlin
fun close() {
    captureSession?.close()
    cameraDevice?.close()
    imageReader?.close()
    captureSession = null
    cameraDevice = null
    imageReader = null
}
```

Closing the session before the device avoids the device attempting to deliver results to a session that no longer exists. This `CaptureSessionManager` class, opened once per shoot and closed once the operator finishes the building, is the object the AE-lock book will extend with locked `CaptureRequest` keys, and the object the room-by-room state machine will hold onto as it advances the operator from room to room without ever tearing down and reopening the camera between shots.
