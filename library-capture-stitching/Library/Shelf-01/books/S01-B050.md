# Automating Reshoot Triggers from Blur and Overlap Scores Together

Two sibling volumes in this shelf each build one estimator: "A Field Overlap Estimator: Comparing Consecutive Frames" scores how much a new frame shares with the last accepted one, and the blur side of "Building a Pre-Upload Capture Health Check on Device" scores sharpness per frame. Both output a number. Neither, alone, tells the operator what to do. This book wires the two scores into a single trigger function that the app calls after every frame: it returns a verdict, not a metric, so the operator never has to interpret a chart mid-walkthrough. That handoff from measurement to decision is also the subject of "Flagging and Triggering a Reshoot Mid-Session," which covers the UI side (the toast, the buzz, the shutter lockout); this book covers the decision function underneath it.

## Why the two scores cannot be thresholded independently

Treating blur and overlap as two separate pass/fail gates produces a trigger that is technically correct and practically annoying. A frame can be sharp but have collapsed overlap with its neighbor (the operator turned a corner too fast), or have plentiful overlap but be motion-blurred (the operator was still moving when the shutter fired). Firing two independent alerts for these two failure modes forces the operator to context-switch between "get closer" and "hold still," which is exactly the kind of judgment call this book's scope says the app should absorb instead of the operator.

The fix is a single decision function that takes both scores as input and returns one of three verdicts: `ACCEPT`, `WARN`, or `RESHOOT`. Warn exists because blur and overlap degrade independently but combine multiplicatively in their effect on COLMAP's downstream matching. A moderately soft frame with strong overlap is recoverable (COLMAP's tutorial guidance is that every surface point should appear in at least three images, so one soft frame among several sharp overlapping ones rarely breaks reconstruction). A moderately soft frame with borderline overlap is not recoverable in the same way, because there may be no other frame covering that surface at all.

## The blur estimator, reused

The blur estimator is the variance-of-Laplacian technique from "PyImageSearch — Blur detection with OpenCV": convolve the grayscale frame with the Laplacian kernel and take the variance of the response. Sharp images produce high variance because they have abundant edges and rapid intensity changes; blurry images produce low variance. The source uses `cv2.CV_64F` deliberately rather than an 8-bit output type, because Laplacian derivatives can be negative and an unsigned 8-bit buffer would clip them.

```python
import cv2
import numpy as np

def blur_score(gray_frame: np.ndarray) -> float:
    return cv2.Laplacian(gray_frame, cv2.CV_64F).var()
```

The PyImageSearch source is explicit that its worked threshold of 100.0 is "quite subjective to the contents of the image(s)" and must be tuned per dataset rather than treated as universal. This matters for the combined trigger: a fixed blur threshold copied from a different capture context (their test images were general photography, not room interiors under mixed indoor lighting) will misfire. The trigger function below treats the blur threshold as a per-deployment constant, not a hardcoded literal, precisely because the notes only support "tune it," not a specific indoor number.

## The overlap estimator, reused

The overlap side of this trigger takes the score object built in "A Field Overlap Estimator: Comparing Consecutive Frames" and does not recompute it; it only consumes the number that estimator already produces per new frame relative to the last accepted frame. The threshold this book applies to that number is grounded in two published targets, neither of which is indoor-capture-specific (the research notes for this shelf flag that gap explicitly): Pix4D's best-practices documentation gives a general-case recommendation of at least 75% frontal overlap and 60% side overlap, rising to around 90% for interior reconstruction specifically, while the older CIPA 3x3 Rules require at least 60% overlap between spatially successive photographs (dropping to one-third for convergent, angled pairs). Because Pix4D calls out interiors by name as needing the higher end of that range, and because CIPA's own secondary literature cautions that its 1990s-era numbers are dated relative to modern capture, this book anchors its default floor near Pix4D's interior figure rather than CIPA's general one, and exposes it as a tunable constant rather than a hardcoded belief.

There is a second, less obvious failure mode worth guarding against: overlap that is too high because the operator has stopped translating and is only rotating the phone in place. COLMAP's own tutorial explicitly warns against this ("Do not take images from the same location"), and the structure-from-motion degeneracy literature in these notes explains why: pure rotation between two views is a well-known degenerate configuration where the fundamental matrix is not uniquely determined by point correspondences, so reliable triangulation requires actual translational baseline, not just high frame-to-frame similarity. A naive overlap-only trigger that only checks "is overlap above X%" cannot distinguish a good sequential shot from a stationary pivot, because both produce high overlap scores. The combined trigger below treats extremely high overlap (above roughly 97%) as its own warning condition alongside the low-overlap case, rather than assuming more overlap is always safer.

## The combined trigger

```python
from dataclasses import dataclass
from enum import Enum


class Verdict(Enum):
    ACCEPT = "accept"
    WARN = "warn"
    RESHOOT = "reshoot"


@dataclass
class TriggerConfig:
    blur_min: float = 120.0
    overlap_min: float = 0.75
    overlap_target: float = 0.90
    overlap_max_static: float = 0.97
    blur_warn_margin: float = 1.25
    overlap_warn_margin: float = 0.05


@dataclass
class FrameScores:
    blur: float
    overlap: float


def evaluate_frame(scores: FrameScores, cfg: TriggerConfig) -> Verdict:
    blur_ok = scores.blur >= cfg.blur_min
    blur_soft = scores.blur < cfg.blur_min * cfg.blur_warn_margin

    overlap_low = scores.overlap < cfg.overlap_min
    overlap_borderline = scores.overlap < cfg.overlap_min + cfg.overlap_warn_margin
    overlap_static = scores.overlap > cfg.overlap_max_static

    if not blur_ok and overlap_low:
        return Verdict.RESHOOT
    if not blur_ok:
        return Verdict.RESHOOT
    if overlap_low:
        return Verdict.RESHOOT
    if overlap_static:
        return Verdict.WARN
    if blur_soft or overlap_borderline:
        return Verdict.WARN
    return Verdict.ACCEPT
```

The two unconditional `RESHOOT` branches, blur failing outright, or overlap failing outright, exist because either condition alone means the frame cannot safely anchor a COLMAP match: a genuinely blurred frame degrades the SIFT keypoints it can contribute regardless of how much scene it shares with its neighbor, and a frame below the overlap floor may not share enough scene with any neighbor to be matched at all, independent of its own sharpness. The `WARN` branches are softer: a frame that clears both floors but sits close to either one, or one with suspiciously static (rotation-only) overlap, is accepted into the bundle but flagged so the mid-session UI in "Flagging and Triggering a Reshoot Mid-Session" can surface a lighter-weight nudge instead of a hard stop.

## Hysteresis: why single-frame verdicts are not enough

A trigger that re-evaluates from scratch on every single frame will flap. A brief hand-shake produces one bad blur score, or a fast pass around a corner produces one low-overlap frame; both self-correct on the very next frame. Firing a hard reshoot prompt on a single transient dip trains the operator to ignore the prompt, which defeats the point of automating the judgment call in the first place. The fix is a small rolling window that requires the bad condition to persist before escalating from `WARN` to `RESHOOT`-level UI action, while still recording every individual frame's raw verdict for later diagnostics.

```python
from collections import deque


class SessionTrigger:
    def __init__(self, cfg: TriggerConfig, window: int = 4, persist_threshold: int = 3):
        self.cfg = cfg
        self.window = window
        self.persist_threshold = persist_threshold
        self.history: deque[Verdict] = deque(maxlen=window)

    def submit(self, scores: FrameScores) -> Verdict:
        verdict = evaluate_frame(scores, self.cfg)
        self.history.append(verdict)
        reshoot_count = sum(1 for v in self.history if v == Verdict.RESHOOT)
        if len(self.history) == self.window and reshoot_count >= self.persist_threshold:
            return Verdict.RESHOOT
        return verdict
```

This is the same shape of problem COLMAP's own sequential matcher solves at the reconstruction stage rather than the capture stage: its `overlap` parameter (default 10 consecutive images per the deepwiki notes on COLMAP's feature-matching strategies) matches each frame against a window of neighbors rather than judging any single pair in isolation, precisely because single-pair overlap judgments are noisy. Windowing the capture-time verdict the same way is a deliberate echo of that design, not a coincidence, and it is worth naming to the engineer building the capture tool so the two windowing decisions (capture-time persistence window, reconstruction-time matching window) are not confused with each other or accidentally coupled to the same constant.

## What the notes do not cover

The research notes for this shelf are explicit that no source ties an indoor-specific overlap floor, or a persistence-window size for hysteresis, to solo phone-capture workflows; the Pix4D and CIPA figures are aerial and general-purpose photogrammetry guidance applied here by analogy, and the `window` and `persist_threshold` defaults above are reasonable starting points, not published constants, so an operator tuning this trigger for a specific building type should expect to adjust them empirically rather than treat them as settled.

## A minimal self-check

```python
def demo() -> None:
    cfg = TriggerConfig()
    trigger = SessionTrigger(cfg)

    good = FrameScores(blur=300.0, overlap=0.88)
    blurry = FrameScores(blur=40.0, overlap=0.88)
    low_overlap = FrameScores(blur=300.0, overlap=0.40)
    static_pivot = FrameScores(blur=300.0, overlap=0.99)

    assert evaluate_frame(good, cfg) == Verdict.ACCEPT
    assert evaluate_frame(blurry, cfg) == Verdict.RESHOOT
    assert evaluate_frame(low_overlap, cfg) == Verdict.RESHOOT
    assert evaluate_frame(static_pivot, cfg) == Verdict.WARN

    single_session = SessionTrigger(cfg)
    for _ in range(2):
        assert single_session.submit(blurry) == Verdict.RESHOOT
    assert single_session.submit(good) in (Verdict.ACCEPT, Verdict.WARN)

    print("all assertions passed")


if __name__ == "__main__":
    demo()
```

The `demo` function is the whole test surface this trigger needs: it exercises both hard-fail branches, the static-pivot warn branch, and confirms that the accept case does not spuriously reshoot. Anything more elaborate (a full fixture suite, mocked camera frames) is scaffolding this book's scope does not call for.
