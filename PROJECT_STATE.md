## Orbit Tour — the Kuula replacement (added 2026-07-23)

- **What it is**: a second app in this repo at `tour/index.html`, served by the same `server.py` at `/tour`. Self-hosted 360 photo virtual tours: multi-scene, hotspots, embeds, standalone export. Replaces a kuula.co Pro subscription. Full docs: `docs/TOUR.md`.
- **Engine choice (research-backed, 2026-activity gate)**: Photo Sphere Viewer 5.14.3 + three.js 0.184.0, both vendored under `tour/vendor/` and pinned. Marzipano (archived Apr 2026) and Panolens (archived 2023) were disqualified for inactivity; Pannellum is 2026-active but has no VR/gyro/little-planet/gallery plugins, so it would have meant writing most of Kuula's feature set by hand. No open-source Kuula-clone editor was worth adopting (the one candidate is built on dead Marzipano).
- **Version rules that matter**: all `@photo-sphere-viewer/*` packages are exact-peer-lockstepped, and core 5.14.3 requires three `^0.184.0` which for a 0.x version means 0.184.x ONLY. `three.module.js` is a split bundle that relatively imports `three.core.js` — both must be vendored or the viewer dies on load. Never add `little-planet-adapter` (stale at 5.7.4); core's `fisheye` option is the supported path. See `tour/vendor/VERSIONS.md`.
- **PSV v5 ships ESM only** (no UMD), so the app loads it through an `<script type="importmap">`. That is also why the static export rewrites `/tour/vendor/` to `./vendor/` and not `vendor/` — bare specifiers are invalid as import-map addresses.
- **Storage**: `tours/<tour-id>/tour.json` + `files/` (gitignored, it is user content). Angles are stored in DEGREES in tour.json and converted to radians at the PSV boundary. Media filenames are server-generated hex tokens; the client never controls a filename on disk.
- **Prune grace window**: `prune_tour_files` deletes unreferenced media on save, but skips anything younger than `PRUNE_GRACE_SECONDS` (300). Without that window a debounced autosave firing between an upload and the save that references it silently destroyed the just-uploaded pano — confirmed live, then fixed and covered from both sides in the smoke test.
- **CORS**: the API now echoes only localhost-family origins instead of `*`, because the tours API has DELETE routes. Non-browser clients (the phone app, curl) send no Origin and are unaffected.
- **Tests**: `python tests/tour_smoke_test.py` (30 checks). `python tests/seed_demo_tour.py` generates a 3-scene demo tour with hotspots for eyeballing the viewer without a camera.
- **Build method**: each step was gated by an impeccable-agent report card requiring 93%+ before moving on — foundation 93%, viewer 94%, editor 93%, share/export 96%, and a final whole-product audit at 93% with no blockers. Defects the gates caught and that are now fixed: a data-loss race where autosave pruned a just-uploaded panorama; an invalid import-map path that would have broken every exported tour; a shared delete-arm variable that let one scene row arm while another stayed falsely armed; a settings object captured by reference that undo would have detached; undo restoring a scene whose media a save had already pruned; and custom icons silently dropped on link hotspots.
- **Known gaps vs Kuula Pro** (deliberate, documented): no view analytics, no password-gated tours (a read-only token would be theater while the same port offers unauthenticated edit/delete — the real answer is auth at a reverse proxy), stereo VR is cardboard-style split view rather than a true WebXR session, and no tiled loading for very large panoramas.
- **Non-panoramic photos accepted (added 2026-07-27)**: `preparePano()` no longer rejects non-2:1 images; every readable image becomes a scene. Three new optional per-scene fields, all additive so old tour.json files still load: `pano: { hFov, pitch }` (degrees of sphere covered; absence means a full 360x180 equirect), `geo: { lat, lon, heading }` (EXIF GPS), `size: { w, h }`. Vertical FOV is deliberately not stored — an equirect has one degrees-per-pixel scale on both axes, so `vFov = hFov / (width/height)` and a stored pair could disagree.
- **Coverage is decided at upload in order**: (1) GPano XMP present -> read `FullPanoWidthPixels`/`CroppedAreaImageWidthPixels`/`CroppedAreaImageHeightPixels`/`CroppedAreaTopPixels` for exact coverage, no guessing; (2) else aspect within 4% of 2:1 -> full sphere; (3) else guess `hFov = clamp(round(60 * aspect), 30, min(360, 180*aspect))` on the assumption a phone sees ~60 degrees vertically, marked `ponytail:` in source and corrected by a slider in the editor.
- **PSV trap**: `panoDataFor(scene)` must ALWAYS return a function, never `undefined` — PSV 5.14.3's `setPanorama` keeps the last function-valued `panoData` on `viewer.config` and reuses it when a later call passes none (`psv-core.module.js`, the `if (typeof this.config.panoData !== "function" || typeof options.panoData === "function")` guard), so a full-sphere scene loaded right after a partial one would silently inherit the partial crop. The closure snapshots hFov/pitch VALUES rather than the scene object because undo replaces `doc.scenes` wholesale. Verified live: a 90-degree GPano sphere produced a mesh with `phiLength` 90 deg / `thetaLength` 22.5 deg; uncovered sphere is just absent geometry showing `canvasBackground` (default `#000`). The little-planet intro is skipped automatically when the start scene is partial — no nadir to unfold from.
- **Format conversion**: anything not jpeg/png/webp is re-encoded to JPEG via canvas in-browser before upload (16384px cap), so a HEIC-from-iPhone tour still renders on Windows Chrome. Coverage is measured before the round-trip, so losing XMP in re-encoding costs nothing and the server upload allowlist is unchanged. HEIC cannot be decoded client-side on Windows Chrome at all (`createImageBitmap` fails) — the error names HEIC specifically and tells the user how to get JPEGs off the phone.
- **Build mode linking UI redone**: the one-shot "+ Link hotspot" button is gone. `placing` gained a `{ link: sceneId }` shape that survives click after click and scene switches; a chip row under the toolbar picks the target (ticked if already linked from the current scene), and "Add the way back too" (default on) writes the reciprocal link. Scenes nothing links to, other than the start scene, get a red dot in the scene list.
- **`autoLink()`**: two tiers, prints which ran to the sidebar. With 2+ EXIF GPS fixes it links each scene to its 2 nearest neighbours within 60m both ways, aiming `yaw = wrap180(bearing(from,to) - from.geo.heading)` with no sign flip, because PSV yaw increases left-to-right across the equirect (`textureCoordsToSphericalCoords`) — the same sense as a compass bearing, verified against the vendored source. GPS with no `GPSImgDirection` still picks neighbours but falls back to walking-layout directions (summary says so); no GPS at all chains scenes in list order; photos with no fix chain to their list neighbours so they never drop out. Existing links are never duplicated, and the whole run is one Ctrl+Z via `scheduleSave()`.
- **EXIF/XMP reading is hand-rolled**, ~100 lines, no library vendored: a JPEG APP1 walk to the TIFF block, an IFD walk to tag 0x8825 for the GPS IFD, then tags 1/2/3/4 (lat/lon + hemisphere refs) and 17 (`GPSImgDirection`). Every dereference is bounds-checked because the parser only ever sees the first 256KB of the file. Marked in source as worth replacing with a real parser only if lens data, timestamps, or maker notes are ever needed.
- **New tests**: `node tests/tour_pano_test.mjs` (37 assertions: coverage geometry, GPano XMP both attribute and element forms, the EXIF GPS parser against a hand-built JPEG with known byte offsets plus every truncation of it, and bearing math) lifts the pure helpers straight out of `tour/index.html` rather than duplicating them, and throws if the anchors it slices on are renamed. `python tests/seed_mixed_tour.py` generates one photo of each shape with real EXIF GPS via Pillow (needs `IFDRational`; plain tuples read as extra entries) and a hand-spliced GPano XMP APP1 segment, then uploads to a running server. `tour_smoke_test.py` still passes 30/30.
- **Hotspot drag-to-reposition (added 2026-07-27)**: any hotspot — link, info, or URL — can be dragged onto its spot instead of only moved via the panel's Move button. PSV 5.14.3 ships no draggable markers, so this is a hand-rolled `pointerdown`/`pointermove`/`pointerup`(+`pointercancel`) trio registered on `editorViewer.container` in the CAPTURE phase with `stopPropagation`, which is what stops the viewer rotating under the drag instead. Screen position converts through `editorViewer.dataHelper.viewerCoordsToSphericalCoords({x: clientX - rect.left, y: clientY - rect.top})`; marker DOM ids are `psv-marker-<hotspotId>` (matched via a `MARKER_ID` prefix constant). The document is written once, on release, so undo gets one entry per drag rather than one per pixel (a no-op drag writes nothing). The raycast returns `null` wherever the sphere carries no photo, which on a partial panorama is most of it, so the hotspot holds its last valid spot rather than jumping somewhere invisible. Build mode's click-to-place is unaffected (the drag handler bails out early while `placing` is set).
- **Hotspot shape/size/opacity (added 2026-07-27)**: three new optional per-hotspot fields, `shape`/`size`/`opacity`, all additive so an unstyled hotspot and every pre-existing tour render unchanged. Shapes: Circle, Square, Diamond, Ring, Dot, plus a link-only "Arrow on the floor" (the viewer's own stock floor arrow); Circle is the default for info/URL hotspots, Arrow is the default for links. `lastStyle` carries the last-applied shape/size/opacity onto the next hotspot placed, by hand or via `autoLink()`'s generated links, so a look is chosen once. THE TRAP: opacity can't live on the element for a drawn shape — `ArrowsRenderer.render()` in the virtual-tour plugin overwrites `element.style.opacity` to `"0.5"`/`null` on every frame for any two arrows within `arrowsPosition.linkOverlapAngle` (45°) of each other (its own nearer-arrow dimming), so an element-level fade flickers away the moment two doorways get close. Fix: for a shape we draw, the fade is painted INTO the generated SVG as a `<g opacity="...">` wrapper (`hotspotIcon()`), which the plugin never touches. A link left as the stock floor arrow has no SVG of ours to paint into, so its fade rides the CSS colour channel instead — `arrowColour(h)` sets `arrowStyle.style.color = rgba(255,255,255, 0.8 * opacity)`, because the stock arrow's SVG uses `fill="currentColor"` and nothing in the plugin touches `color`; 0.8 matches the stock alpha in `psv-virtual-tour.css` so full opacity still looks like an untouched tour. Only an uploaded custom icon has nowhere else to put the fade and falls back to element opacity. Also: the floor arrow renders at 80px where a marker renders at 40px, so `ARROW_SCALE = 2` doubles the stored size for arrows so one number means the same apparent size on both.
- **Sample tour seeds once (added 2026-07-27)**: `seed_sample_tour()` in `server.py` used to re-copy the sample tour on every start whenever the `tours/sample-tour` folder was missing, so deleting it did nothing — it came back. It now writes a marker file `tours/.sample-seeded` right after placing the sample and skips seeding whenever that marker (or the tour folder) already exists; deleting the sample is taken as the user being done with it, and deleting the marker file is what brings it back on the next start. The marker can't be mistaken for a tour: `list_tours()` only counts folders holding a `tour.json`, and `TOUR_ID_RE` requires an id to start with a letter or digit, so a leading dot can never be addressed.
- **Image quality (added 2026-07-27)**: JPEG/PNG/WebP uploads are never re-encoded — byte-for-byte as captured, as they always were. Only a format no browser can be relied on to decode (HEIC/HEIF and friends) goes through canvas re-encoding, now at JPEG quality 0.95, capped at `MAX_PANO_WIDTH = Math.min(16384, SYSTEM.maxTextureWidth || 16384)` (16384 on the target laptop) since the viewer would scale a wider texture down anyway. `THUMB_WIDTH` went from 512 to 1024 at JPEG quality 0.86 (~80KB extra per scene) so scene-list thumbnails stay sharp at 2x pixel density. A new optional scene field `converted` records a re-encode (additive; absence means untouched); the sidebar's This-scene note now states the photo's actual pixel dimensions, whether it uploaded untouched or converted, and warns when a photo is wider than `SYSTEM.maxTextureWidth`.
- **`guessNavigableYaws()` / scene `ways` (added 2026-07-28)**: on upload the editor reads a 256x128 thumbnail and scores each column on how far it departs from a local average of its neighbours (a wide circular box filter) — deliberately NOT raw brightness, because a doorway into an unlit room reads darker than the wall while a doorway onto a sunlit deck reads brighter, and one deviation-from-neighbourhood pass catches both. Two bands are sampled: pitch +20 to -15 at full weight, and -20 to -50 at half weight so a puddle can't decide the route alone. Sun/glare is excluded first via a 99.5th-percentile threshold over a sky band, dilated for bloom. Surviving columns become candidate angles stored on the scene as `ways`, kept >=45 degrees apart — the virtual-tour plugin's `linkOverlapAngle` (45°, see the hotspot shape/size/opacity bullet above) dims anything closer anyway, so finer spacing would buy nothing. `autoLink()` and manual build-mode placement both call `snapToWay()` to nudge the placed arrow onto the nearest `ways` entry instead of the raw computed bearing or photo centre. TWO REAL BUGS CAUGHT WHILE BUILDING, neither a test artefact: (a) taking the single brightest pixel as "the sun" meant that under flat overcast the brightest pixel is just sky, so every column got excluded and the feature silently did nothing — fixed by requiring the bright region to exceed the sky level by >=40 before excluding anything; (b) comparing a column only to its own neighbourhood leaves weak echoes either side of a real opening, so one doorway produced three arrows — fixed by requiring a suggestion to score >=0.45 of the strongest column in the photo. HONEST LIMITS: rust bleed, efflorescence, and weld seams read as local brightness anomalies that are not openings, a bigger false-positive source on bridge subjects than on a clean interior; a bright window two metres up a wall scores like a doorway since there is no depth understanding; a scene the heuristic can't read returns no `ways` and linking falls back to the old raw-bearing behaviour, so it is never worse than before. The real answer is per-column floor-boundary regression (HorizonNet and descendants), which needs a neural net — noted as the upgrade path, not built.

The earlier guard checked whether the whole tour had any link at all, so returning later to add a fifth room to an already-linked tour left the new room silently unconnected; it now checks whether the batch that just arrived is unconnected, so every drop gets the same treatment regardless of what came before. - **JS footgun: never test `placing?.link` directly**: `placing` holds either a string (`'link' | 'info' | 'url'`) or an object (`{link: sceneId}` or `{move: hotspotId}`). When `placing === 'link'` (the string), `'link'.link` resolves to `String.prototype.link` — a legacy HTML-wrapper method every string carries — which is a function, hence truthy. A naive `if (placing?.link)` guard therefore mistakes a bare link-hotspot placement for an armed build-mode target and would silently refuse to place on click. `placing?.move` does NOT have this trap (strings have no `.move` method), so it alone was never unsafe, but the fix was made uniform anyway: every such test now goes through `armedTarget()` (`const armedTarget = () => (placing && typeof placing === 'object' ? placing.link : null) || null;`), which checks `typeof placing === 'object'` before touching `.link`. Reintroducing a raw `placing?.link` check anywhere is the exact regression to watch for in review.
- **Viewer switched to `renderMode: '2d'`, and the transition no longer spins (added 2026-07-29)**: the virtual-tour plugin's default `'3d'` lays every link arrow flat on the ground — `ArrowsRenderer.addLinkArrow` builds a `CSS3DObject` and does `object.rotation.set(-PI/2, 0, PI - yaw)` — which reads as a sticker stuck to the path and skews with the floor. `'2d'` uses a `CSS2DObject` instead, so arrows stand upright facing the viewer the way Street View's do; the user asked for exactly this with before/after screenshots and it is now verified visually. - **`transitionOptions` is now explicit, and the forward push is CSS (added 2026-07-29)**: set to `{ effect: 'fade', rotation: false, speed: '20rpm', showLoader: true }`. The plugin's default `rotation: true` swings the camera round to face the link during the crossfade, which is the "spin" the user objected to. Honours `prefers-reduced-motion`. `node-changed` now always resets zoom to `scene.view?.zoom ?? 50` so the push cannot accumulate scene to scene.

## Orbit Studio — the flythrough/splat lane (verified 2026-08-04)

## Coordinate convention rule

Every 3D asset handoff states its up axis explicitly. Pipeline artifacts (gsplat and COLMAP output) are Y-down and the viewer applies the 180 degree X flip. Generated and web-native assets (demo.splat, user-dropped files) are Y-up and are never flipped. A handoff that does not state its up axis is not ready.
